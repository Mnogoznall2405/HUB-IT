# Координация миграций

Снимок графов на `4d4dba1f`: лично выполнен Alembic `heads` (1.20.1, без подключения к БД). Три независимых каталога, один head **на граф**, а не на весь монорепозиторий:

| Граф / конфиг от корня | Head в исходниках | Version table на PostgreSQL |
|---|---|---|
| app/chat — [`WEB-itinvent/backend/alembic.ini`](../WEB-itinvent/backend/alembic.ini), запуск из `WEB-itinvent` | `20261125_0182` | `system.alembic_version` |
| scan — [`scan_server/alembic.ini`](../scan_server/alembic.ini) | `20261120_0005` | `scan.alembic_version` |
| voice — [`voice_server/alembic.ini`](../voice_server/alembic.ini) | `20261004_0007` | `voice.alembic_version` |

Новых подтверждённых резервов на момент снимка нет. Резерв ведётся в затронутом Issue/PR: Task ID, контур, base SHA, владелец, `revision` / `down_revision`, rollout/rollback, результат PG, состояние применения по окружениям с датой и доказательством. Git — канон графа; [реестр релиза](RELEASE_REGISTRY.md) — указатель на фактическое применение. Не считать схему выпущенной по имени файла.

1. Координатор проверяет свежий `main`, открытые PR и незавершённые резервы и выдаёт уникальный ID и parent. По умолчанию один активный schema PR на граф; независимые графы можно менять параллельно, если runtime-контракты не пересекаются. После merge уточнить базу для следующей миграции. Перенумеровывать можно только неподтверждённо применённую ревизию после проверки всех окружений и согласования; при сомнении считать потенциально применённой. Уже выпущенная история не переписывается без отдельного плана и одобрения владельца; обычный путь — forward-fix.
2. Предлагаемый автоматический gate: проверить уникальность `revision` по каталогу (до построения карты), затем Alembic `ScriptDirectory` с предупреждениями о графе как ошибками: существование ссылок `down_revision`/`depends_on`, отсутствие циклов, ровно один ожидаемый head на каталог. Сравнить исходники выпущенных ревизий с проверенной базой и выявить переписывание; отступление документируется отдельно. Запускать на merge-result без app startup/БД, с доверенной статической проверкой либо на изолированном runner без секретов. Исторические ветвления допустимы, если корректно сведены в один head.
3. На disposable PostgreSQL проверить фактическую схему `chat` или legacy `public`, version table, fresh upgrade и upgrade с ожидаемой предыдущей версии/seed. Проверить существование и валидность индексов, FK, объём и сохранность строк, повтор и согласованный downgrade либо восстановление копии. Измерить затронутые блокировки и время. `alembic check` не доказательство корректности на legacy-схеме без её сверки. Не подключать CI к production.
4. На выпуске DBA отдельно фиксирует read-only `current`, проверку объёма, блокировок и свободного места, backup/restore, порядок остановки/старта, простой и точку невозврата. Без разрешения владельца только работа с изолированной копией. Использовать [PM2 runbook](../scripts/pm2/README.md) и конкретный release runbook; не запускать `upgrade` в штатном старте.

У app/chat финальная цепочка `0176 → 0177 → 0178 → 0179 → 0180 → 0181 → 0182`: `0178/0179` относятся к «Моим файлам», `0180–0182` — к Sticker V2. Ранние отчёты с другими номерами относятся к другому дереву. Для актуального production `current` данных этой сверки нет.
