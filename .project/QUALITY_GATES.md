# Ворота качества

Команды, фикстуры и ограничения — в [TESTING.md](../documentation/technical/TESTING.md) и [AGENTS.md](../AGENTS.md). Матрица применяется по затронутому риску, а не по размеру diff. Для каждого gate записать `base/head/merge SHA`, профиль среды, команду, результат и ссылки на артефакты. `SKIPPED`/`NOT TESTED`/`ENVIRONMENT BLOCKED` не равны `PASS`.

| Изменение | Проверки на PR/интеграции |
|---|---|
| Документация / процесс | Diff, ссылки и команды по исходникам, отсутствие секретов и противоречий; не запускать продуктовые suites без причины. |
| Web/API-клиент | Профильные Vitest и lint по затронутым путям, E2E затронутого сценария; при маршрутах, auth, клиенте API или сборке — изолированный production build. Текущий `npm run lint` охватывает только chat, не весь web. |
| Backend / WS / workers | Проверка синтаксиса, профильный HTTP `TestClient`; миграции отдельно. Если меняется async/конкуренция: реально параллельный переход и финальное состояние; WS reconnect/order/duplicates/backpressure, ACK, повтор и рестарт worker по риску. |
| UI/UX | Реальный сценарий на desktop и узком экране; focus/keyboard, тема, loading/error/empty, сохранение контекста и отсутствие overflow. Для визуальных артефактов фиксировать браузер, viewport и SHA. |
| Security | Независимое ревью серверной границы auth/ACL и данных; негативные проверки ролей, cross-user/tenant, сессий и смены прав. Для auth — login/logout/refresh М×вкладок, реплей/истечение, WebAuthn и клиенты по затронутому контракту. Не менять политики под гейт. |
| Performance | Согласованные baseline, результат для пользователя и диапазон шума до правки; [методика A/B](PERFORMANCE_BUDGETS.md). Не требовать A/B для нетронутых hot paths. |
| Миграция | [Проверка графа](MIGRATION_REGISTRY.md); изолированный PostgreSQL на изменённом графе: upgrade от предыдущей реальной версии и на чистой БД, допустимый downgrade/restore, данные, индексы, locks и повтор. SQLite не заменяет PG. |
| Корпоративный ИИ | Изолированный scripted provider, фиксированный seed: маршрутизация, корректность READ/ACT, ACL, подтверждение действий, недоверенные источники, retry/лимиты и telemetry. Для поведенческих флагов — также одинаковый live test-provider A/B на синтетическом holdout без production-секретов, фиксировать model/rounds/tokens и качество. |
| Desktop / Mobile | Desktop Release test/build при WebView2, lifecycle, packaging или auth; Mobile `lint`/typecheck, related Jest, целевой offline/reconnect/push или устройство по риску. Не ослаблять auth для отдельного клиента. |
| Infra / release | Синтаксис и dry-run в изолированном контуре, fail-closed и конфигурация; точный RC, проверка манифеста, порядок выката и откат по [реестру релиза](RELEASE_REGISTRY.md). |

## GitHub Actions: поэтапное предложение, не включено

Фактически есть только [узкий mobile follow-up](../.github/workflows/chat-followup-check.yml) для отдельной push-ветки. Переиспользовать его pinned actions и идею блокировки сетевых тестов, но не менять этот workflow или deployment/ACL в текущем PR. Новые gates сначала рекомендательные.

| Уровень | Проект автоматизации |
|---|---|
| **Быстрый PR** | `pull_request`, классификация риска/путей внутри всегда стартующего workflow, один стабильный итоговый check. Whitespace/conflict markers только на diff, secret scan с редактированным выводом, статические проверки/существующий lint, профильные тесты и изолированный build для затронутого runtime, статический Alembic на schema path. Независимые jobs можно параллелить на разных runners. |
| **Merge** | Пересчитать предполагаемое дерево с актуальным `main`, не принимать только зелёный старый head. Повторить quick и профильные cross-module checks для конфликтных поверхностей. Независимый reviewer + разрешение владельца; при смене base/head решение пересмотреть. Сначала один координатор, нативная merge queue/`merge_group` только если поддерживается и одобрено. |
| **Nightly** | `schedule` и ручной запуск на default branch: полные Web Vitest и профили backend pytest (отдельно bot/voice/scan при нужных зависимостях), расширенные E2E, граф и изолированная PG-матрица, отчёт по flake/baseline и подтверждённому долгу. Полный Playwright включать только после отдельного разрешения. Нет обязательных статус-чеков от nightly. |
| **Release** | Ручной gate для неизменяемого SHA: production build вне live worktree, smoke по модулям, изолированный PostgreSQL, согласованный perf A/B, security review, проверка restore/rollback и решение `GO/NO-GO`. GitHub job не выкатывает приложение. |

Изоляция: отдельный checkout и рабочий каталог на job; loopback, уникальные порты/SQLite state или disposable PostgreSQL DB на запуск; уникальный runtime namespace и cleanup только собственных процессов. Запретить выход к production и не передавать CI production-секреты. Использовать read-only token, pinned actions, `persist-credentials: false`, без выполнения непроверенного PR-кода через `pull_request_target`. Perf — отдельный runner/эксклюзивное окно, без тяжёлых jobs на хосте. Сырые большие результаты — в артефакты с ограниченным хранением и только после обезличивания; в Git — краткое резюме.

Первый пилот: начать с быстрых проверок и Alembic. Проверить на корректном/некорректном diff и на docs-only PR, что пропуск по пути не оставляет pending check. Nightly сначала ручной, с лимитами времени и разбивкой опциональных контуров. Только после повторяемых результатов просить владельца включить required check и независимый review, отдельно согласовать график и канал уведомлений. Статус-дайджест безопасно строить из read-only GitHub metadata в summary; не создавать автозадачи, не закрывать PR и не трогать production.

Сравнивать падения на чистых A/B с одинаковой средой: `новое`, `baseline`, `flake`, `неизвестно` с подписью теста и доказательствами. Одинаковое число падений не означает одинаковую сигнатуру, а один успешный повтор не устраняет flaky-риск. Блокирующая или неизвестная регрессия на критичном пути — `NO-GO`.
