## Один реестр задач, без параллельной таблицы

- Канон для новых несекретных задач — [GitHub Issues](https://github.com/Mnogoznall2405/HUB-IT/issues). Ещё не заведённую задачу координатор регистрирует в согласованном рабочем канале до публикации; если у задачи уже есть PR без Issue, временно используем `PR-<номер>`. Не заводить Issue ради дублирования такого PR. Политика публичного репозитория: внутренние пути рабочих машин, непубличные данные, чувствительные находки и реальные логи — только в одобренном закрытом канале; публично допустим обезличенный итог.
- Запись назначения живёт в Issue или, для существующего PR без Issue, в его плане проверки. В записи: Task ID, исполнитель, направление, статус, ветка, ID worktree (полный путь только приватно), base SHA, резерв файлов/контрактов, зависимости, PR, gate, время обновления и блокеры. Пока задача не назначена, исполнитель пуст; автор коммита и наличие worktree не доказывают активность.
- Статусы: `BACKLOG` → `READY` → `IN_PROGRESS` → `REVIEW` → `APPROVED` → `MERGED` → `RELEASED`; ответвления `BLOCKED` и `CHANGES_REQUESTED` возвращаются в работу после устранения причины. `MERGED` доказывает `main`, `RELEASED` — подтверждённый выкат. Обновлять при переходе статуса, изменении SHA/границ или блокере. Запись без свежего подтверждения сверить с PR, веткой и исполнителем; она не активная автоматически, но резерв не передавать молча.
- При запросе статуса координатор заново сверяет `main`, Issues/PR, проверки на нужном SHA, ветки, схемы и подтверждения выката; если GitHub недоступен, помечает срез устаревшим. Нет обещания фонового мониторинга. Задачи, решения и артефакты не переписываются в статус вручную: снимок даёт ссылки, а для долговечных архитектурных решений используется следующий ADR.

## Чувствительные области и очередь

Здесь «владелец области» — роль независимого ревьюера, не GitHub-право и не назначение человека. Координатор подтверждает резерв до начала работы, проверяя также пересечения по контрактам и фикстурам, а не только совпадение путей.

| Область | Резерв и кто проверяет |
|---|---|
| `AuthContext.jsx`, `api/http.js`, `api/client.js`, `App.jsx`, auth/permissions, WebView2 и mobile session | Резерв auth-контракта; Security + QA, владельцы затронутых клиентов |
| `ChatPageContent.jsx`, `ChatComposer.jsx`, chat REST/WS, outbox | Резерв участка отправки/чтения/reconnect или явная последовательность; Web + Backend/Realtime |
| `MyFiles.jsx`, `components/myFiles/`, файловые API | Один исполнитель на редактируемый экран/контракт или согласованные независимые участки; Web + Backend |
| Глобальные layout/theme/bootstrap, общие API и E2E-фикстуры | Отдельный резерв; профильный владелец плюс ревью затронутых потребителей |
| `appdb/models.py`, `chat/models.py`, Alembic, схемы `scan`/`voice` | Database + владелец домена; порядок ревизий согласует координатор |
| `shared/llm/`, `ai_chat/`, AI worker, tool ACL | AI + Security при изменении данных, прав или действий |
| `.github/workflows/`, `scripts/{iis,pm2,releases}/`, конфигурация и зависимости запуска | DevOps + QA/Security по риску; production и GitHub ACL отдельно разрешает владелец |

1. Работа параллельна только по независимым участкам. Для общих файлов назначить одного интегратора, разделить явно независимые части или поставить задачи последовательно. Не открывать вторую ветку консолидации того же набора изменений. Зависимый PR помечает предшественника и не принимается сам по себе раньше него.
2. Интеграция последовательна: координатор фиксирует `base/head/merge SHA`, проверяет ancestry, сравнивает поведение и тесты обеих сторон, перечисляет разрешения конфликтов. Если перенос был squash/cherry-pick, проверяет patch и семантику: отсутствие ancestry не доказывает отсутствие фикса. После изменения базы или головы обновляет merge-result и затронутые гейты. Старые ветки и PR помечает кандидатами на закрытие/архивирование, но не удаляет и не закрывает без разрешения.
3. Ревьюер сверяет требования, diff, регрессии, SHA и артефакты; автор не принимает собственную работу. Вердикт: `APPROVED`, `APPROVED WITH LIMITATIONS`, `CHANGES REQUIRED`, `BLOCKED` или `REJECTED`. Ограничение описывает риск и владельца; не превращает отсутствующую обязательную проверку в `PASS`. Приоритет задачи: `P0` критическая безопасность/потеря данных/недоступность; `P1` существенный дефект; `P2` заметное улучшение; `P3` второстепенное; `P4` идея. Доказательность: `CONFIRMED`, `SUSPECTED`, `NOT REPRODUCED`, `NOT TESTED`, `ENVIRONMENT BLOCKED`, `FIXED` (с контрольной проверкой).

## Карточка, пригодная как промпт

```
Task ID / название / приоритет / исполнитель / статус:
Цель и польза:
Исходное состояние: base SHA, branch/worktree ID, PR/Issue, наблюдаемая проблема.
Разрешённые пути и контракты / запрещённые изменения / зависимости и резервы:
Ожидаемый результат / требования к реализации:
QA: среда, сценарии, обязательные проверки, критерии приёмки:
Отчёт: diff/baseline/head, команды и результаты, артефакты, риски/блокеры.
Готово, когда: выполнены критерии и передано независимому ревью; права
на публикацию, merge и выпуск указывать отдельно, без подразумеваемого согласия.
```
