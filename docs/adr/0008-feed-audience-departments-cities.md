# ADR-0008: Таргетинг новостей ленты по отделам структурки и городам

## Status

Accepted (2026-09-19)

## Context

Лента (`/feed`, объявления) умеет таргетировать публикации только на всех
(`all`), роли (`roles`) и конкретных сотрудников (`users`):
`hub_service.py` (`_announcement_recipient_users`, `_announcement_visible_to`),
контракт `POST/PATCH /hub/announcements`
(`audience_scope`, `audience_roles`, `audience_user_ids`),
выбор аудитории в `FeedComposerDialog.jsx` и `NativeFeedEditorScreen.tsx`.

Нужна публикация новостей по отделам из структуры компании
(`company_structure`, дерево ZUP-узлов) и городам. Связная информация уже есть:
ZUP-профиль сотрудника (`zup_user_profile_service.py`) даёт `department` +
`city` (`department_location`) со строгим матчингом
(email → логин → уникальное ФИО, двусмысленные личности не резолвятся),
узлы структурки несут `department_codes`,
`address_book_service.build_department_label_resolver` связывает имена
отделов с кодами.

## Decision

1. **Новые скоупы.** `audience_scope`: `departments`, `cities`,
   `departments_cities` (И внутри группы, И между группами).
   Существующие `all/roles/users` и старые публикации не меняются.
2. **Что хранится.** `audience_department_codes[]` (коды ZUP, не id узлов
   и не имена) + `audience_cities[]` (нормализованные `department_location`).
   Переименования узлов и городов таргетинг не ломают. Валидация:
   выбран хоть один отдел/город.
3. **Как сопоставляется.** Отдел публикации (коды) ↔ отдел сотрудника через
   тот же резолвер имён, что использует адресная книга; город — прямое
   сравнение нормализованных названий с `city` ZUP-профиля.
   Автор и модераторы (`announcements.moderate`) видят всегда.
4. **Нераспознанные исключаются.** Сотрудник без сопоставленного ZUP-профиля
   (нет email, тёзка) таргет-новость не видит. Строгость матчинга
   `zup_user_profile_service` не ослабляется ради охвата.
5. **Динамика, не снапшот.** Состав аудитории вычисляется на чтении
   (видимость, получатели, аналитика, push-fanout), поэтому переводы
   сотрудников и новые наймы подхватываются автоматически с лагом ZUP-кэша
   (~5 мин). Резолв только через кэшированные справочники, без I/O в цикле.
6. **Каталоги для пикера.** `GET /hub/users/announcement-recipients`
   отдаёт `departments` (узлы дерева с кодами) и `cities`;
   `recipients_summary`: «N отделов · M городов (K получателей)».

## Матрица видимости

| Сотрудник | all | roles | users | departments | cities | dep+city |
|---|---|---|---|---|---|---|
| Профиль совпал полностью | видит | по роли | в списке | видит | видит | видит |
| Совпал только отдел | — | — | — | видит | нет | нет |
| Совпал только город | — | — | — | нет | видит | нет |
| Профиля нет | видит | по роли | в списке | нет | нет | нет |
| Автор / модератор | видит | видит | видит | видит | видит | видит |

## Consequences

- Контракт `POST/PATCH /hub/announcements` и ответ recipients расширяются;
  требуется миграция колонок (SQLite inline по образцу `audience_*` +
  PG DDL, если hub там) с проверкой на тестовой БД.
- Перевод сотрудника меняет его ленту с лагом ZUP-кэша — фиксируется
  в пользовательской инструкции, не считается багом.
- Тёзки без корпоративного email остаются вне таргет-рассылок до
  устранения двусмысленности в ZUP-кэше.
- Аналитика считает получателей по тем же правилам, что видимость,
  иначе «прочитали» разойдётся с «аудитория».
