# ADR-0010: Нативные WPF-экраны поверх API в HUB Desktop

## Status

Accepted (2026-11-17)

## Context

`desktop/` изначально проектировался как тонкая WPF/WebView2-оболочка портала: бизнес-логика и
экраны — в React-фронтенде, оболочка даёт только Windows-интеграцию (tray, updater, уведомления,
deep links). `desktop/FUNCTIONAL_ROADMAP.md` и `desktop/ROADMAP.md` фиксировали правило «не
дублировать web-экраны на WPF».

Пользователь принял решение развивать Desktop в сторону полностью нативного приложения: быстрый
старт без прогрева WebView2, меньше память, честные окна/уведомления. Это осознанная смена курса,
поэтому правило фиксируется новым решением. Миграция — поэкранная: нативные экраны появляются
рядом с WebView2, который остаётся для ONLYOFFICE-редакторов, звонков и неперенесённых страниц.

Существующий контракт для не-web клиентов уже есть — его использует `mobile-hub` (Expo):
bearer-токены в JSON-ответе login/refresh, заголовки `X-Auth-Client: mobile` и
`X-Client-Device-ID`, `Authorization: Bearer` на REST и WebSocket.

## Decision

1. Нативные экраны живут внутри существующего `Hub.Desktop` (папка `Native/`): переиспользуются
   updater, installer, tray, политики, диагностика. Отдельное приложение не создаётся.
2. API-контракт нативного клиента — ровно mobile: `X-Auth-Client: mobile`,
   `X-Client-Device-ID: desktop-<guid>`, `Authorization: Bearer`. Новых серверных эндпоинтов
   не вводится.
3. Нативная сессия **независима** от WebView2-cookie. Совместное использование web refresh-токена
   невозможно: `/api/v1/auth/refresh` атомарно ротирует пару, а grace-окно допускает один
   повтор — разделение токена привело бы к ревокации всей семьи и разлогину web-сессии.
   Пользователь входит в нативный клиент отдельно (логин/пароль + TOTP); лимит
   `SESSION_MAX_ACTIVE_PER_USER=3` это допускает.
4. Токены хранятся в DPAPI-файле (`CryptProtectData`, CurrentUser) в профиле пользователя;
   refresh — строго single-flight с атомарной заменой пары, как в `tokenStore.ts`.
5. Первый нативный экран — «Мои задачи» (список, детали, переходы по `capabilities` сервера).
   Дальнейшие экраны — отдельными решениями по той же схеме.
6. Общий слой: `Native/Themes/HubTheme.xaml` (единые design tokens вместо дублированной палитры),
   `Native/Api` (HttpClient + session store), `Native/ViewModels` (MVVM), `Native/Views`.

## Consequences

- Нативный клиент не влияет на web-сессию: отдельные токены, отдельный `session_id`.
- Два интерфейса (web + native) временно сосуществуют; нативные экраны покрывают подмножество
  функций портала. ONLYOFFICE и звонки остаются в WebView2.
- Дизайн-система нативных окон централизована в `HubTheme.xaml`; существующие окна постепенно
  переводятся на неё (палитра идентична, перенос безболезненный).
- `desktop/ROADMAP.md`/`FUNCTIONAL_ROADMAP.md` и AGENTS.md (инвариант «Desktop — тонкая
  оболочка») подлежат актуализации по мере роста нативной доли.

## Rejected alternatives

- Чтение WebView2-cookies в нативный HttpClient — ротация refresh ломает web-сессию (см. п.3).
- Отдельное приложение/процесс — дублирует updater, installer, tray и удваивает деплой.
- WinUI 3 / Avalonia / MAUI — новый фреймворк без выигрыша для Windows-only корпоративного
  сценария; WPF на .NET 8 уже в решении и покрывает потребности.
- Wpf.Ui / MahApps.Metro — второй визуальный язык рядом с фирменной тёмной темой; вместо этого
  токены вынесены в общий `HubTheme.xaml`.

## Follow-up condition

Перенос каждого следующего экрана (чат, документы, уведомления) — по мере готовности, без
«большого взрыва». Полная замена WebView2-хоста — отдельный ADR после того, как нативно покрыт
основной пользовательский путь и решена судьба ONLYOFFICE/звонков.
