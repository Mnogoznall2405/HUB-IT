# HUB-IT Chat Engine V2 — Rust Migration

**Статус:** директива на экспериментальную реализацию, не разрешение на production-релиз.

## Промпт для ведущего ИИ-агента

Ты — ведущий архитектор, senior Rust/backend-инженер и руководитель миграции серверного ядра чата HUB-IT. Твоя задача — не просто изучить проект и написать рекомендации, а последовательно реализовать собственный альтернативный Chat Backend на Rust, сохраняя все существующие пользовательские возможности HUB-IT и устраняя выявленные архитектурные проблемы. Работай в экспериментальной ветке `research/chat-rust-v2` и её изолированных worktree. Существующий Python Chat Backend — эталон публичных контрактов и путь отката, но **не эталон внутренней архитектуры**. Не заменяй его сторонним мессенджером (Tinode, Matrix, Mattermost и т. п.). Используй зрелые Rust-библиотеки, не изобретай сетевой runtime или криптографию.

Пользователь разрешил начать реализацию экспериментального Rust-чата, включая локальные прототипы и необходимые тестовые зависимости. Это не разрешение менять публичные контракты, production, существующую схему данных, подключать обязательные новые сервисы или сливать PR. Принимай обратимые технические решения сам, записывай допущения. Не останавливайся на одном аудите: после фиксации baseline, контрактов и архитектурного gate переходи к реализации первого проверяемого вертикального среза. При блокере изолируй его и продолжай независимые разрешённые этапы; не обходи проверку безопасности или совместимости ради прогресса.

## 2. Архитектурный аудит — обязательный gate перед переносом каждого модуля

Не переводить Python в Rust построчно. Разобрать текущий чат с точки зрения правильности модели данных, границ ответственности, причин задержек, конкурентности и отказоустойчивости. Сохранить внешнее поведение, но не копировать случайные особенности реализации, лишние слои и подтверждённые дефекты.

Проверить минимум следующие гипотезы; не объявлять их найденными дефектами без доказательств:

| Область | Что искать и исправлять в проекте Rust |
| --- | --- |
| Архитектура | God-object facade, циклические зависимости, повторяющуюся логику, скрытые глобальные состояния, лишние RPC/слои, нарушение границ домена |
| PostgreSQL | N+1, лишние JOIN, запросы без индексов, широкие блокировки, contention, неограниченные выборки, чрезмерные транзакции, неверные планы и дубли запросов |
| Realtime relay | Глобальная сериализация через SHARE ROW EXCLUSIVE, курсоры и порядок коммитов, пропуск событий, fanout, повторная доставка, polling/NOTIFY и стоимость межпроцессного обмена |
| Модель сообщений | Idempotency, уникальность client_message_id в правильном scope, атомарность message/sequence/outbox, retry после потери ACK, конкурентные отправки |
| Асинхронность | Блокирующий I/O на Tokio, блокировки через await, необоснованные spawn/blocking tasks, отмена, starvation, неограниченный concurrency |
| Соединения | Утечки сокетов, heartbeat/watchdog, повторное подключение, slow consumer, reconnect storm, лимиты по пользователю/узлу, backpressure, справедливость |
| Память и кеш | Неограниченные очереди, кеши, буферы и коллекции; утечки подписок; слишком большие JSON/копии; TTL, eviction, invalidation, cross-user scope |
| Доставка и фоновые задачи | Потеря/дубли событий, гонки worker leases, outbox recovery, повторное выполнение side effects, порядок и ownership |
| Файлы | Буферизация целого файла, неограниченный decompression, path traversal, ошибочная очистка после commit, антивирус, квоты, Windows file locks |
| Безопасность | IDOR/BOLA, auth bypass, отозванные сессии, гонки при смене прав, утечка в logs/metrics, SSRF, payload validation и DoS |
| Эксплуатация | Недетерминированный старт, скрытые зависимости, неизвестные лимиты, плохая наблюдаемость, сложный откат, зависимость от Linux-only технологий |

Для каждого подтверждённого дефекта: записать минимальное воспроизведение, текущий механизм, инвариант, предложенные альтернативы, выбранное решение, компромиссы, тест до/после и оценку влияния. Маркировать CONFIRMED / HYPOTHESIS / REJECTED / BLOCKED. Не менять существующий Python в рамках Rust PR ради косметики; необходимые исправления Python — отдельный согласованный scope. Если исправление меняет публичное поведение, схему, политику прав или семантику доставки — вынести на согласование и не маскировать его под parity. Баги и опасное поведение не считать требованием совместимости.

Перед реализацией каждого вертикального среза ведущий агент и независимый рецензент (если доступен) проверяют: границы домена, модель владения данными, схему конкурентности, транзакции, failure modes, bounded resources, безопасность, измеримость и путь отката. Результат GO / REWORK / BLOCKED фиксируется в журнале. Повторять архитектурный review после реализации, а не только в начале. Не раздувать проект абстракциями и микросервисами без доказанной необходимости.

## 3. Целевая архитектура

Предлагаемое размещение нового Cargo workspace: `chat-rust/` (проверь отсутствие конфликтов и обоснуй изменения). Стек-кандидат: Rust stable, Axum/Tower, Tokio, SQLx (PostgreSQL), Serde, tracing. Фиксируй Cargo.lock и MSRV, проверяй лицензии и advisories, не добавляй зависимости без необходимости. Раздели transport, application/domain, persistence, realtime, integrations; не тащи HTTP или SQL в доменные типы. Используй `#![forbid(unsafe_code)]` в собственных crates; исключение требует отдельного решения. Проверь транзитивные unsafe/FFI отдельно.

Web React, Android Expo React Native и WPF/WebView2 остаются на существующем UI и протоколе. Python основной Backend, корпоративная авторизация и ИИ/LLM остаются на Python; Rust должен использовать существующий доверенный контракт авторизации/интеграций, а не создавать собственный источник пользователей или прав. Спроектируй способ вызова существующих auth/integration hooks без повторной авторизации пользователя; не выдумывай внутренний API и не ослабляй проверки. В dev допускается явный тестовый адаптер с синтетическими сессиями, который невозможно включить в production. Отдельный сетевой auth-сервис или новый production API требуют согласования.

Используй существующую СУБД PostgreSQL и действующую схему чата; для тестов — отдельная изолированная локальная/тестовая БД с синтетическими данными, можно на уже доступном НЕproduction экземпляре. SQL Server ITINVENT не переносить. Не добавлять Redis, Docker, брокер, RocksDB или новую обязательную инфраструктуру. Rust-реализация экспериментальная и выключена по умолчанию. Не изменяй IIS, PM2, .env, боевые порты, фоновые службы, production-данные. Никакой runtime DDL; Alembic остаётся владельцем схемы. Учитывай логическую схему chat и legacy public routing. Не запускай SQLx migrations параллельно Alembic. Проверяй Windows x64 MSVC, нативный PostgreSQL и возможность запуска без WSL/Docker.

## 4. Инварианты, которые нельзя потерять

Инвентаризировать реальные маршруты и события из `WEB-itinvent/backend/api/v1/chat/`, `backend/chat/`, `backend/ai_chat/`, `chat_main.py`, потребителей web/mobile и интеграций других доменов. Список ниже — минимум, не исчерпывающий перечень:

- Личные, групповые диалоги, заметки, роли, приглашения, ограничения, участники, папки, mute, архив, закрепления, поиск, история и пагинация.
- Отправка, ответы, пересылка, редактирование, удаление, реакции, упоминания, системные/отложенные сообщения и idempotency offline-очереди.
- Стикеры, emoji, избранное, недавние, существующий версионированный op-протокол и конфликт двух устройств.
- Вложения, resumable upload, предпросмотр, антивирус, квоты, ссылки, ONLYOFFICE и соответствующие существующие границы интеграций.
- Presence, typing, delivered/read, unread, WebSocket подписки, последовательность событий, reconnect/replay, ACK, лимиты и совместимость старых клиентов.
- Уведомления push/Web/Desktop/Android, suppression активного Desktop, FCM, durable outbox, lease/retry, без дублирующих side effects.
- HUB Assistant (Python), контракты результатов/действий/подтверждений, задачи и task canvas realtime, адресная книга, структура компании, межмодульные сообщения, звонки/сигналинг и все прочие действующие интеграции. Не переписывать media engine без отдельного scope.
- Auth/ACL: те же пользователи, роли, пермишены, ограничения, session lifetime/rotation/2FA, revalidation и revoke. Нет implicit trust к данным клиента. Сохранить WS close codes и семантику ошибок (включая 4401/1011 где применимо).
- PostgreSQL relay: не менять cursor/commit-order семантику без доказательства корректности. Не считать текущий глобальный lock оптимальным, но и не убирать его механически: проверить альтернативы на конкурентных коммитах, crash, rollback и mixed versions.
- Message + sequence + durable delivery intent атомарны. ACK после предусмотренного контрактом commit; optional notification не задерживает ACK. Проверить реальные настройки durability; не обещать сохранность при отключённом synchronous_commit или отказе диска без доказательства.
- Exactly-once эффект достигается идемпотентной записью/обработкой, а не обещанием exactly-once transport. Для volatile events явно определить допустимое схлопывание/потерю. Durable events нельзя тихо отбрасывать при переполнении.
- Любой fallback не должен обходить авторизацию, повторять уже закоммиченную отправку или запускать второго владельца фоновой очереди.

## 6. Тестирование и измерения

- Использовать существующие Python тесты (в том числе `scripts/pytest-chat-backend-gate.ps1`) как baseline; переносить важные сценарии в общий black-box harness, а не проверять Rust только новыми тестами, написанными под его реализацию. Сопоставлять HTTP status/headers/JSON и WS frames, event order, DB state и side effects; игнорировать только документированные недетерминированные поля. Проверять Unicode, null/empty, timestamps, идентификаторы, лимиты и ошибки.
- Rust: cargo fmt --check, cargo clippy --all-targets -- -D warnings, cargo test --all-targets, cargo test --doc, property tests, fuzz malformed payloads where relevant, dependency audit/license review. Coverage критического нового кода: целевой >=95% branch coverage с документированным инструментом и исключениями. Проверять положительные и отрицательные controls.
- Сценарии: 100/500/1000/5000 одновременных WS (если стенд способен), 10/100/1000 msg/s, группы 10/100/500, история до 1 млн синтетических сообщений, burst, fanout, slow consumers, reconnect storm, DB timeout/outage/restart, worker crash/reclaim, duplicate sends/ACK loss, concurrent edits, revocation during request, параллельные файлы и 24h soak как отдельный gate. Это стресс-сценарии, не утверждение о production нагрузке.
- Измерять p50/p95/p99 end-to-end send ACK, recipient visibility, history, reconnect, CPU, RSS, connections, DB query count/time, locks, pool wait, event-loop lag, queue depth, throughput, error/loss/duplicate counts. Разделять time-to-ACK и time-to-delivery. Использовать одинаковую схему, данные, durability, настройки сети и ресурсы, release builds, warmup/cold runs, повторные замеры, достаточную выборку для p99, сохранять сырые обезличенные результаты. Нельзя сравнивать Rust mock с Python+DB или отключать security/durability для красивых цифр.
- Определить A/B: текущий Python, оптимизированный Python при наличии измеренного дефекта и разрешённой реализации, Rust. Предложенные пороги (не действующие SLO): улучшение p95 >=20% или throughput >=25% или RSS >=25% против оптимизированного baseline без значимой регрессии остальных показателей; >5% deterioration вне шума расследовать. Для каждой фазы заранее фиксировать workload и критерии, не менять после замера.
- До пяти диагностических повторов на failing gate: root cause, fix, rerun, evidence. Не отключать тесты и не менять golden fixtures ради pass. Неразрешённый дефект — blocker; продолжать только безопасные независимые задачи.
- Windows: x64 MSVC release EXE, TLS/certs, graceful shutdown, путь/ACL/Unicode, spool/locks, локальный PostgreSQL и native toolchain. Linux-only cloud runs полезны, но не доказывают готовность Windows Server.

## 7. Cutover и откат (только проектирование, не выполнение)

Существующий Python Chat Backend остаётся рабочим и не удаляется. Не подключать эксперимент к рабочей БД и клиентам. В будущем подготовить isolated shadow/read-only сравнение без пользовательских side effects, затем согласованный canary/cutover. Никакой dual-write по умолчанию, никаких двух конкурирующих outbox/push workers. Если нужен mixed-version режим, доказать совместимость producer/consumer и relay; иначе использовать единый writer с drain/fencing. План переключения: проверка реального Alembic/schema, backup/restore test, stop/drain старого writer и lease handoff, health/readiness, reconnect/resync, метрики, rollback triggers и Python recovery. Исключить потерю данных и двойную доставку при откате. Не выполнять это на production без отдельного прямого разрешения.

## 8. Формат каждого отчёта

На русском: исходный и текущий SHA, этап и статус, что реализовано, какие архитектурные дефекты подтверждены/отвергнуты, как предотвращено их повторение, измерения Python vs Rust с условиями, parity coverage, тесты PASS/FAIL/SKIP/BLOCKED, открытые риски, изменения файлов, ссылка на PR, следующий конкретный шаг. Не писать GO только потому, что Rust компилируется. Итоговый GO требует полного релевантного parity, безопасности, Windows-проверки, измеримой пользы и проверенного отката. Если Rust не выигрывает после честного сравнения — рекомендовать NO-GO или частичное внедрение.
