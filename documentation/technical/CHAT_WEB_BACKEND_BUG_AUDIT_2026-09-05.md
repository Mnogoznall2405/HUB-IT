#### B3 — P1: участие проверяется до блокировки при редактировании и удалении

Файл: [service.py](../../WEB-itinvent/backend/chat/service.py), `delete_message` (2586), `edit_message` (2675).

Оба метода сначала вызывают `_require_membership`, затем `_lock_conversation_for_write`. Если между ними вступило в силу исключение участника, право участия не проверяется повторно. В delete повторно загружается роль для группы, но отсутствие active membership не запрещает удаление собственного сообщения. В edit достаточно совпадения автора.

Детерминированный probe: создать группу, отправить сообщение от пользователя 2, в точке получения блокировки установить его `left_at` и выполнить flush; затем продолжить реальный метод. Обе операции приняты: `REMOVED_MEMBER_EDIT_ACCEPTED`, `REMOVED_MEMBER_DELETE_ACCEPTED`. Это модель порядка конкурирующих операций на SQLite, не настоящий параллельный прогон PostgreSQL.

Исправление: использовать уже принятый в групповых операциях порядок lock → membership/authorization. Регрессия должна моделировать исключение до выдачи блокировки и проверять отказ и неизменность сообщения. Production-права не ослаблять.

Это подтверждённое расхождение входного API и сохранения данных. Наличие поля ввода такого комментария именно в текущем web-диалоге этим тестом не подтверждено. Не заменять исходное содержимое молча и не удалять принимаемые поля без проверки потребителей. Регрессия: HTTP-параметры → service → сохранённый/возвращённый результат.

#### F3 — P2: голосовое сообщение не сохраняется для повтора при ошибке отправки

Файлы: [useChatUploadsController.js](../../WEB-itinvent/frontend/src/pages/chat/useChatUploadsController.js), `handleVoiceRecordingComplete` (121); [useVoiceRecorder.js](../../WEB-itinvent/frontend/src/components/chat/useVoiceRecorder.js), обработчик `recorder.onstop` (304–320).

Регрессия: offline → восстановление сети → повтор того же файла в исходную беседу, плюс смена беседы.

## B1. Пересылка обходит удаление вложения

**Файлы:** [chat_forward_materializer.py](../../WEB-itinvent/backend/chat/chat_forward_materializer.py), строки 61–63, 81–85, 116–131; [service.py](../../WEB-itinvent/backend/chat/service.py), `delete_message` (2585), `forward_message` (2404).

**Причина:** materializer проверяет только `source_message is None`, затем читает вложения и копирует физические файлы. Признак `is_deleted` не проверяется. Мягкое удаление сохраняет файлы; прямое скачивание удалённого сообщения уже запрещено, но новая пересланная копия имеет собственное доступное вложение.

**Воспроизведение:** пользователь 1 отправляет `private.txt`, удаляет своё сообщение; пользователь 2, остающийся участником беседы, вызывает `forward_message` с ID удалённого сообщения. Затем `get_attachment_for_download` для новой копии возвращает исходные байты `private`. ID можно сохранить до удаления. Не требуется доступ к чужой беседе или обход проверки участия.

**Результат probe:** `DELETED_ATTACHMENT_RECOVERED_BY_FORWARD`.

**Влияние:** серверная семантика удаления не соблюдается. Это восстановление доступа средствами API, а не сохранённая ранее локальная копия пользователя.

**Предлагаемое исправление:** отклонять удалённый источник до чтения содержимого и копирования вложений, используя принятую ошибку отсутствующего сообщения. При реализации отдельно проверить гонку удаления с пересылкой. Сохранить проверки участия; не заменять их проверкой только ID.

**Регрессия:** удалить текст и файл; новая пересылка каждого должна завершиться отказом, без нового сообщения и файлов. Контроль: обычная пересылка доступного сообщения продолжает работать.

## B2. Частично скопированные вложения не очищаются при ошибке materializer

**Файлы:** [chat_forward_materializer.py](../../WEB-itinvent/backend/chat/chat_forward_materializer.py), строки 47, 116–131 и возврат результата; [service.py](../../WEB-itinvent/backend/chat/service.py), строки 2421, 2430–2437, 2468–2474.

**Причина:** materializer создаёт собственный `written_paths`. Внешний сервис получает список только после успешного возврата функции. Если копирование второго файла выбрасывает исключение, присваивание результата не происходит; внешний `except` очищает свой первоначальный пустой список. Первый скопированный файл остаётся без записи нового сообщения. Сам `copy2` также может оставить частичный файл до добавления пути в список.

**Воспроизведение:** исходное сообщение содержит два текстовых вложения. Первый `copy2` выполняется реально; второй заменён исключением `OSError('simulated disk failure')`. После отказа API количество новых физических файлов относительно снимка перед пересылкой — один.

**Результат probe:** `FAILED_FORWARD_LEAKED_FILES=1`.

**Влияние:** повторные неудачные пересылки расходуют диск; сохраняются ненужные копии содержимого.

**Предлагаемое исправление:** materializer должен сам очищать созданные пути при исключении либо получать общий список cleanup от вызывающего кода. Регистрировать целевой путь до копирования, чтобы охватить частично записанный файл. Чистить только файлы текущей операции.

**Регрессия:** ошибка на втором вложении и ошибка после частичной записи первого; после отказа состояние каталога совпадает с исходным, новое сообщение отсутствует. Успешный путь сохраняет все вложения.

## F1. Восстановление файлов после ошибки теряет контекст ответа

**Файл:** [useChatFileSending.js](../../WEB-itinvent/frontend/src/components/chat/useChatFileSending.js), строки 104–110, 395–413, 424–426, 459–461.

**Причина:** перед отправкой сохраняется `draftReplyMessage`, а UI вызывает `setReplyMessage(null)`. После ошибки snapshot содержит только `items`, `caption`, `asFiles`. Восстановление открывает файлы и подпись, но не возвращает reply-контекст. Следующий `sendFiles` получает `replyMessage = null`.

**Воспроизведение:** ответить файлом на сообщение `quoted`; первая отправка завершается сетевой ошибкой; восстановить форму и повторить отправку. Harness исполняет исходный хук, подменяя React primitives и API; setters и rerender моделируются явно.

**Результат probe:** `FILE_RETRY_REPLY_IDS=quoted,NONE`.

**Влияние:** повтор отправляет обычное сообщение вместо ответа, хотя файлы и подпись восстановлены.

**Предлагаемое исправление:** включить исходный reply-контекст в snapshot восстановления. Восстанавливать его только в исходной беседе и при отсутствии более нового выбора ответа; не затирать текущий пользовательский ввод.

**Регрессия:** React renderHook с реальным состоянием: ошибка → восстановление → повтор сохраняет `reply_to_message_id`; отдельный случай защищает более новый выбранный ответ.

## F2. Асинхронная подготовка файлов не привязана к беседе

**Файлы:** [useChatFileSending.js](../../WEB-itinvent/frontend/src/components/chat/useChatFileSending.js), строки 113–199 и 374–378; [useChatUploadsController.js](../../WEB-itinvent/frontend/src/pages/chat/useChatUploadsController.js), строки 35–42, 81–118.

**Причина:** `queueSelectedFiles` ожидает `prepareChatUploadFiles`, затем без проверки исходного conversation ID устанавливает общий `selectedUploadItems`. Контроллер хранит одну форму на экземпляр страницы. `sendFiles` выбирает получателя из текущего `activeConversationId`, а не из контекста подготовки.

**Воспроизведение на уровне хука:** начать подготовку в A; до завершения сменить prop на B, сохраняя экземпляр; завершить подготовку; вызвать отправку. Подготовленные файлы отправляются в B.

**Результат probe:** `PREPARED_IN_A_SENT_TO=B`.

**Ограничение:** harness доказывает отсутствие защиты при смене беседы, но не доказывает, что обычный клик по списку доступен поверх открытого модального окна подготовки. В браузере нужно проверить переходы через роутинг/историю и другие действия, меняющие активную беседу. До этого не считать подтверждённой отправку не тому адресату в реальном UI.

**Предлагаемое исправление:** захватить conversation ID и generation операции до await; результат применять только к исходному контексту либо сохранять черновик отдельно для исходной беседы. Та же проверка нужна для подготовки отредактированного изображения и сброса редактирования, которые также применяют результат после await.

**Регрессия:** deferred preparation + rerender A→B, включая A→B→A; завершение старой операции не заполняет новую форму. Проверить unmount во время подготовки.
