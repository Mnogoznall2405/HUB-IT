## Закрытие N1–N5 по запросу «исправь»

Все пять пунктов ниже исправлены в исходниках. Последующие разделы сохраняют результаты исходной диагностики; их маркеры воспроизведения описывают версию до исправления.

- **N1:** общий сериализатор строит содержание предпросмотра из пересланной копии (текст, вложения и task snapshot); от оригинала сохраняются ID происхождения и имя автора. Новые текстовые правки и имена файлов из исходной беседы не раскрываются. Для удалённой копии forward preview не возвращается. Миграция не нужна.
- **N2:** форма восстановления сохраняет объект одной попытки загрузки. Перед complete в нём фиксируется session ID; после неопределённого ответа повтор вызывает complete той же сессии, без повторной загрузки и создания новой сессии. При fallback multipart сохраняется отдельный ключ идемпотентности. Новый намеренный пакет получает новую попытку. Chunk upload остаётся прежним. Состояние попытки хранится в памяти страницы, не переживает перезагрузку.
- **N3:** toggle reaction получает блокировку беседы, затем проверяет участие и признак удаления сообщения. Реакция на tombstone отклоняется. Уже существующие reaction rows массово не удалялись.
- **N4:** поколение выбора инвалидируется при смене выбранных ID, беседы и unmount. Поздний delete/clipboard completion не очищает новый выбор. Для всего пакета delete фиксируется исходная беседа.
- **N5:** после удаления папки используется актуальный фильтр, а не старое замыкание. Переход в personal остаётся только если удалённая папка всё ещё выбрана; после unmount переход не выполняется.

## Что исправлено в этом проходе

- **B3 предыдущего отчёта:** `edit_message` и `delete_message` теперь блокируют беседу перед проверкой участия. Регрессии моделируют исключение перед выдачей блокировки, требуют отказа и неизменности сообщения.

Несколько ошибочных записей сохраняются по порядку. Повтор сохраняет исходный File, audio-метаданные и `client_message_id`.
- Ключ передаётся в существующий multipart endpoint, который уже поддерживает идемпотентность. Запросы с явным ключом используют multipart; обычные загрузки продолжают использовать upload sessions. Backend-схема и миграции не изменены. Записи сохраняются в памяти страницы, не переживают её закрытие/перезагрузку.

## Исправление ошибочной классификации B4

Предыдущее утверждение «комментарий пересылки теряется — это баг» было неполным. Существующий [test_forward_message_preserves_markdown_body_format](../../tests/test_chat_search_reply_and_settings_service.py) явно требует, чтобы legacy-параметры `body/body_format` не заменяли оригинал. Текущие web/native вызывающие места пересылают исходное сообщение без такого комментария. **B4 снят с очереди ошибок**; runtime-поведение оставлено прежним. Новая функция комментария к пересылке потребовала бы отдельного продуктового решения.

### N1. Предпросмотр пересылки читает текущую версию оригинала

**Код:** [chat_serialization.py](../../WEB-itinvent/backend/chat/chat_serialization.py), `_build_forward_previews` (615): запрос оригиналов по `forward_from_message_ids`; [service.py](../../WEB-itinvent/backend/chat/service.py), `_message_reference_preview_payload`: тело предпросмотра берётся из текущего исходного сообщения.

**Сценарий:** A и B имеют исходную беседу. A пересылает текст `shared version` в группу с C; C не состоит в исходной беседе. Затем A редактирует оригинал на `later private revision`. При чтении целевой группы C получает старое тело копии, но `forward_preview.body` уже содержит `later private revision`.

**Probe:** `FORWARD_PREVIEW_LEAKS_LATER_PRIVATE_REVISION`. Проверены реальное создание, пересылка, редактирование и `get_messages(current_user_id=3)`.

**Влияние:** в целевой беседе раскрывается новая версия текста, которую туда не пересылали. Проблема возникает без знания ID закрытой беседы и без прямого запроса к ней.

**Предложение:** строить содержимое preview из сохранённой пересланной копии/снимка. Происхождение и автора сохранять отдельно от чтения текущего тела оригинала. Не считать наличие пересланной копии разрешением читать будущие правки источника.

**Регрессия:** пользователь без участия в источнике не видит новую правку после пересылки. Проверить повторную пересылку, удалённый источник и файлы/названия задач. Если решение потребует новых полей, отдельно оценить миграцию; сейчас она не выполнялась.

### N2. Обычный повтор файлов теряет идентичность завершённой загрузки

**Код:** [chatFileUploads.js](../../WEB-itinvent/frontend/src/api/chatFileUploads.js), `sendFiles`: каждый вызов создаёт upload session, а ошибка `completeUploadSession` выходит наружу; [useChatFileSending.js](../../WEB-itinvent/frontend/src/components/chat/useChatFileSending.js), `sendFiles`: восстановленные обычные файлы отправляются новым вызовом без идентификатора предыдущей сессии. Стабильный ключ в текущем исправлении предусмотрен для voice-записей.

**Сценарий:** сервер сохранил сообщение на complete, но ответ потерян. Пользователь нажимает повтор в восстановленной форме. Клиент создаёт новую сессию, загружает файлы и выполняет второй complete.

**Probe:** исполнен исходный API-модуль с mock session endpoint; первый complete моделирует commit и затем network error, второй успешен. Получено `ORDINARY_UPLOAD_RETRY_SESSIONS=2 COMMITTED_MESSAGES=2`. Это модель сервера; реальная потеря пакета в production не создавалась.

**Предложение:** сохранять исходный session ID до разрешения неопределённого результата и повторять/проверять complete той же сессии либо сквозной ключ одной отправки. Сохранять chunk-resume больших файлов; не переводить все большие файлы на multipart без оценки.

**Регрессия:** потерянный ответ complete → ручной повтор → ровно одно сообщение; намеренная следующая отправка того же файла должна создать новое сообщение.

### N3. Реакции разрешены для удалённого сообщения

**Код:** [service.py](../../WEB-itinvent/backend/chat/service.py), `toggle_reaction` (1774): проверяются участие и существование строки, но не `is_deleted`.

**Сценарий/probe:** автор удаляет сообщение; второй участник вызывает toggle reaction по сохранённому ID. Сервер возвращает `action='added'`: `REACTION_ADDED_TO_DELETED_MESSAGE`.

**Влияние:** удалённое сообщение остаётся доступным для изменения реакций через API, независимо от того, скрывает ли UI соответствующий пункт меню. Прямое раскрытие удалённого текста этим probe не показано.

**Предложение:** отклонять реакцию на tombstone; отдельно проверить согласованность с удалением при конкурентных запросах. Регрессия: после удаления нет новой reaction row; обычное добавление/снятие реакции остаётся работоспособным.

### N4. Поздний delete сбрасывает новое выделение

**Код:** [useChatSelectedMessageActions.js](../../WEB-itinvent/frontend/src/components/chat/useChatSelectedMessageActions.js), `deleteSelectedMessages`, финальный `clearSelectedMessages()` после await. Аналогичный безусловный сброс есть в `copySelectedMessages` после clipboard await, но отдельный clipboard-probe не проводился.

**Сценарий:** запустить удаление выбранного в A, перейти в B и выбрать другие сообщения, завершить запрос A. Старый callback очищает текущее выделение B.

**Probe:** исходный хук, deferred delete и смена active ref: `DELETE_A_CLEARS_SELECTION_IN=B`. Достижимость через реальный UI отдельно не проверена.

**Предложение:** очистка только при совпадении исходного поколения выбора и беседы. Изменение состояния сообщения A при успешном delete сохраняется. Регрессия должна также защитить новый выбор в той же беседе.

### N5. Удаление старой папки перехватывает новую навигацию

**Код:** [useChatFolderMutationsController.js](../../WEB-itinvent/frontend/src/pages/chat/useChatFolderMutationsController.js), `handleDeleteChatFolder` (45–59): после await сравнивается захваченное `conversationFilter`, а затем вызывается `handleActiveFolderChange('personal')`.

**Сценарий:** удалять активную folderA, переключиться на folderB до ответа. Замыкание всё ещё видит folderA и переводит текущий экран в personal.

**Probe:** `DELETE_FOLDER_A_RESETS_NEW_FOLDER_B_TO=personal`; исходный хук исполнялся с deferred API и rerender с новым фильтром, без реального браузера.

**Предложение:** после ответа проверять актуальный выбранный фильтр или поколение навигации. Если удаляемая папка всё ещё активна, переход в personal нужен; если пользователь уже ушёл — сохранить его выбор.
