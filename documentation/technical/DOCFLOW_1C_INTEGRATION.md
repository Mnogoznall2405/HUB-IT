# Интеграция с 1С Документооборот

## Назначение

Раздел `/docflow` показывает пользователю его персональные задания из информационной базы 1С Документооборот. Это отдельный интеграционный модуль: задания 1С не копируются в `hub_tasks`, поэтому статусы, маршруты согласования и права доступа остаются под управлением 1С.

Текущий этап намеренно работает только на чтение. Создание документов, согласование, отклонение и выполнение заданий включаются после проверки метаданных и доступных действий конкретной конфигурации `docflow`. Универсального безопасного метода записи для произвольной конфигурации 1С нет.

## Поток данных

1. Пользователь открывает страницу «Документооборот» и вводит личные логин и пароль 1С.
2. Backend проверяет их прямым подключением к заранее настроенной базе. Клиент не может передать другой сервер, имя базы или текст запроса.
3. После успешной проверки пароль шифруется выделенным серверным ключом и сохраняется в `app.docflow_credentials`.
4. При чтении заданий пароль расшифровывается непосредственно перед вызовом 1С и передаётся в изолированный дочерний COM-процесс.
5. Запрос 1С всегда содержит ограничение по `ПараметрыСеанса.ТекущийПользователь`. Дополнительная авторизация и видимость документов определяются самой 1С.
6. Список получает только типизированные краткие сведения. Полная карточка и список файлов загружаются по требованию при открытии задания.
7. Перед каждой выдачей карточки или файла backend повторно проверяет одновременно ссылку задания, текущего исполнителя 1С и владельца файла. Пароль и шифротекст никогда не входят в API-ответы.

COM-вызовы выполняются через скрытые Windows worker-процессы, ограниченные очереди с тайм-аутом и автоматической заменой зависшего дочернего процесса. Разрешены только операции `test_connection`, `tasks`, `task_detail`, `file_export` и `metadata`; произвольные запросы и методы из HTTP недоступны. Успешно авторизованные COM-соединения повторно используются только внутри назначенного изолированного процесса; размер LRU-кэша ограничивается конфигурацией. Ключ к сессии — process-local HMAC от учётных данных: открытый пароль не сохраняется в ключе кэша и не журналируется.

## API

Все маршруты имеют префикс `/api/v1/docflow`, требуют активную HUB-сессию и возвращают `Cache-Control: no-store`.

| Метод | Маршрут | Назначение | Право |
|---|---|---|---|
| `GET` | `/profile` | Состояние персонального подключения без пароля | `docflow.read` |
| `POST` | `/profile/test` | Проверка введённых данных без сохранения | `docflow.read` |
| `PUT` | `/profile/credentials` | Проверка и сохранение зашифрованных данных | `docflow.read` |
| `DELETE` | `/profile/credentials` | Удаление персональных данных подключения | `docflow.read` |
| `GET` | `/tasks` | Задания текущего пользователя из live 1С | `docflow.read` |
| `GET` | `/tasks/{task_ref}` | Полная карточка и файлы задания текущего исполнителя | `docflow.read` |
| `GET` | `/tasks/{task_ref}/files/{file_ref}/content` | Оригинал файла после проверки задания и владельца | `docflow.read` |
| `GET` | `/tasks/{task_ref}/files/{file_ref}/preview/pdf` | PDF-предпросмотр через общий конвертер HUB-IT | `docflow.read` |
| `GET` | `/metadata` | Диагностика типов заданий и реквизитов | `docflow.admin` |

Пользовательские ошибки содержат безопасный код и correlation ID, но не содержат connection string, COM-исключение или секреты.

## Конфигурация

Секреты задаются только через защищённую конфигурацию процесса и не коммитятся в репозиторий.

| Переменная | Назначение |
|---|---|
| `DOCFLOW_CREDENTIALS_KEY` | Выделенный Fernet-ключ шифрования персональных паролей; рекомендуется для multi-host |
| `DOCFLOW_CREDENTIALS_KEY_LEGACY` | Предыдущий ключ на время контролируемой ротации |
| `DOCFLOW_1C_SERVER` | Упорядоченный список узлов 1С: клиент подключается к ним по одному и переходит к следующему только при недоступности |
| `DOCFLOW_1C_REF` | Фиксированное имя информационной базы |
| `DOCFLOW_1C_QUERY_TIMEOUT_SECONDS` | Максимальное время одного COM-вызова; production default — 90 секунд из-за медленного первого входа |
| `DOCFLOW_1C_BRIDGE_WORKERS` | Число параллельных изолированных COM-worker; один логин стабильно направляется в один worker |
| `DOCFLOW_1C_MAX_CACHED_CONNECTIONS_PER_WORKER` | Верхняя граница LRU-кэша авторизованных COM-сессий на worker |
| `DOCFLOW_1C_BRIDGE_QUEUE_LIMIT` | Число ожидающих вызовов на один worker перед отказом по перегрузке |
| `DOCFLOW_1C_FILE_MAX_BYTES` | Верхняя граница оригинала, который разрешено выгрузить из 1С во временный файл backend; по умолчанию 50 МБ |
| `DOCFLOW_FILE_VOLUME_ROOTS` | Allowlist точных UNC-корней файловых томов 1С; несколько значений разделяются `;` |
| `DOCFLOW_FILE_VOLUME_MAPPINGS` | Allowlist сопоставлений `путь-в-1С=>доступный-путь`, если имя сервера из 1С должно заменяться контролируемым DNS-алиасом или IP |
| `DOCFLOW_FILE_USE_PROCESS_IDENTITY` | Читать UNC под Windows identity процесса backend; разрешается только для управляемой сервисной учётки с минимальными правами |
| `DOCFLOW_FILE_AD_USER` / `DOCFLOW_FILE_AD_PASSWORD` / `DOCFLOW_FILE_AD_DOMAIN` | Выделенная сервисная AD-учётная запись только для чтения файловых томов |
| `DOCFLOW_FILE_USE_LDAP_SYNC_CREDENTIALS` | Явно разрешает вместо выделенной учётки использовать существующие `LDAP_SYNC_USER` / `LDAP_SYNC_PASSWORD`; по умолчанию выключено |

Имена типа задания, реквизитов и параметра сеанса задаются переменными `DOCFLOW_1C_TASK_*` и `DOCFLOW_1C_SESSION_USER_FIELD`, перечисленными в `.env.example`. Значения проходят строгую проверку идентификаторов до формирования текста запроса.

Для текущей базы `docflow` read-only проверкой подтверждены тип `ЗадачаИсполнителя` и реквизиты `ТекущийИсполнитель`, `ДатаНачала`, `СрокИсполнения`, `Автор`, `ПредметСтрокой`, `Описание`, `РезультатВыполнения`, `СостояниеБизнесПроцесса`, `Важность`, `ПринятаКИсполнению`, `ДатаИсполнения`. `Выполнена` и `БизнесПроцесс` являются стандартными полями платформы и могут отсутствовать в перечислении пользовательских реквизитов метаданных.

Вложения читаются из `Справочник.Файлы` только при совпадении `ВладелецФайла` с бизнес-процессом уже авторизованного задания либо с одним из документов в табличной части процесса `Предметы`. Перед выдачей конкретного файла backend повторяет ту же проверку владельца, поэтому произвольная ссылка на чужой файл не принимается.

Сначала содержимое текущей версии запрашивается штатным интерфейсом БСП `РаботаСФайлами.ДвоичныеДанныеФайла`. Если версия имеет тип «В томах на диске», а штатный вызов не может прочитать содержимое, разрешён контролируемый fallback на UNC. Backend получает `ПутьКФайлу` и `Том.ПолныйПутьWindows`, требует точного совпадения корня с `DOCFLOW_FILE_VOLUME_ROOTS` либо левой частью `DOCFLOW_FILE_VOLUME_MAPPINGS`, отвергает абсолютные и содержащие `..` относительные пути, затем читает ресурс под явно выбранной сервисной identity. Правая часть mapping является единственным разрешённым фактическим корнем и не берётся из HTTP или данных пользователя. Персональные AD-пароли пользователей для этого не принимаются и не сохраняются. Оригинал копируется потоком с лимитом размера во временный каталог, отдаётся пользователю и удаляется после ответа; осиротевшие временные файлы очищаются через 15 минут. Для PDF, изображений и текста используется общий frontend-просмотр вложений, для Word/Excel — существующий LibreOffice/PDF-конвертер HUB-IT.

Дополнительной read-only проверкой подтверждено, что объект `ЗадачаИсполнителя` предоставляет платформенный метод `ВыполнитьЗадачу`, а `РезультатВыполнения` имеет тип `Строка`. В базе присутствуют разные бизнес-процессы (`Согласование`, `Утверждение`, `Ознакомление`, `Исполнение` и другие), поэтому одного универсального текста результата недостаточно для безопасных кнопок «Согласовать»/«Отклонить». Перед записью нужно определить тип процесса и допустимые результаты конкретного задания, затем вызывать отдельную allowlisted команду с idempotency key и post-write проверкой.

Если `DOCFLOW_CREDENTIALS_KEY` задан, используется Fernet с поддержкой контролируемой ротации через legacy-ключ. Если ключ не задан на Windows, backend использует DPAPI в области текущей служебной учётной записи: PostgreSQL получает только версионированный шифротекст, а расшифровать его может тот же Windows-пользователь на том же сервере. При смене служебной учётной записи или переносе backend на другой сервер сначала следует настроить Fernet-ключ и пересохранить пользовательские данные.

Для multi-host production ключ `DOCFLOW_CREDENTIALS_KEY` следует создавать в корпоративном хранилище секретов и передавать всем backend-процессам при запуске. Его нельзя хранить рядом с дампом PostgreSQL: раздельное хранение ключа и шифротекста является обязательной границей защиты.

## Хранилище и аудит

Миграция `20260728_0072` создаёт:

- `app.docflow_credentials` — одна зашифрованная учётная запись на пользователя HUB;
- `app.docflow_audit_events` — события проверки, сохранения и удаления без логинов, паролей и шифротекста.

Удаление подключения физически удаляет строку с шифротекстом. Смена пароля создаёт новую версию зашифрованных данных. Ошибка аутентификации помечает профиль как `invalid`, недоступность 1С — как `unavailable`; успешное чтение возвращает состояние `valid`.

## Ввод в эксплуатацию

1. Применить Alembic-миграцию до запуска новой версии backend.
2. Проверить, что все PM2-процессы работают под одной Windows-учётной записью, либо передать единый `DOCFLOW_CREDENTIALS_KEY` через production secret store.
3. Проверить доступ backend-сервера к кластеру 1С и наличие `V83.COMConnector`/pywin32.
4. Выдать выделенной сервисной AD-учётке только `Read/List` одновременно в Share ACL и NTFS ACL для каждого корня из `DOCFLOW_FILE_VOLUME_ROOTS`. Доступ к административному ресурсу вроде `DOC$` без этих прав не подразумевается.
5. Администратору сохранить собственное подключение через UI и вызвать `/metadata`.
6. Сопоставить фактический тип задания, исполнителя, признак завершения, срок, автора и предмет через переменные окружения.
7. Проверить входящие, завершённые и все задания под двумя тестовыми пользователями с разной видимостью в 1С, затем открыть и скачать файлы из каждого разрешённого тома.
8. Только после этого проектировать отдельные типизированные команды записи для каждого подтверждённого действия 1С с повторной проверкой прав и защитой от повторного выполнения.

Реальные пароли пользователей нельзя передавать через issue, чат разработки, параметры командной строки или журналы. После случайной публикации пароль необходимо сменить в 1С до production-проверки.

## Пилот действий и поручений (2026-07-29)

Контур записи реализован, но остаётся выключенным по умолчанию. Для действий одновременно требуются `docflow.act`, `DOCFLOW_WRITE_ENABLED=1`, ID пользователя в `DOCFLOW_WRITE_PILOT_USER_IDS`, тестовый префикс заголовка, HMAC-ключ состояния и точное правило в `DOCFLOW_ACTION_RULES_JSON`. Для создания дополнительно требуются `docflow.create`, `DOCFLOW_CREATE_ENABLED=1` и ID пользователя в `DOCFLOW_CREATE_PILOT_USER_IDS`.

Подтверждённые read-only инвентаризацией метаданные текущей конфигурации:

- тип задания `ЗадачаИсполнителя`;
- бизнес-процессы `Исполнение`, `Ознакомление`, `Согласование`, `Утверждение` и `Поручение`;
- процесс `Поручение` содержит исполнителя, контролёра, срок, важность, название, описание и табличную часть `Предметы`;
- предмет поддерживает ссылки `ВнутренниеДокументы`, `ВходящиеДокументы` и `ИсходящиеДокументы`;
- исполнитель и контролёр имеют тип `Пользователь` 1С.

Тип процесса задания определяется через `Метаданные()` самой ссылки/объекта. Это важно для внешнего COM-соединения 8.3.27: глобальный английский псевдоним `TypeOf` там не экспортируется. Если тип или отпечаток конфигурации не распознан, карточка остаётся только для чтения.

Новые маршруты:

| Метод | Маршрут | Назначение | Право |
|---|---|---|---|
| `GET` | `/inbox-summary` | Отдельный счётчик входящих 1С без ложного нуля | `docflow.read` |
| `POST` | `/tasks/{task_ref}/actions` | Проверенное действие с `Idempotency-Key` и `state_token` | `docflow.act` |
| `GET` | `/commands/{command_id}` | Только проверка неопределённой команды, без replay | `docflow.act` |
| `GET` | `/assignments/capability` | Состояние пилота создания | `docflow.create` |
| `GET` | `/assignments/documents` | Поиск доступных документов трёх фиксированных типов | `docflow.create` |
| `GET` | `/assignments/assignees` | Поиск активных, неслужебных пользователей 1С | `docflow.create` |
| `POST` | `/assignments` | Создание и запуск одного процесса `Поручение` | `docflow.create` |
| `GET` | `/assignments/commands/{command_id}` | Проверка результата создания без повторной записи | `docflow.create` |

Перед записью команда фиксируется в `app.docflow_commands`. Комментарии и описания в локальном журнале не сохраняются: в request hash входят только их SHA-256. Для создаваемого поручения backend заранее выделяет UUID процесса и передаёт его через `УстановитьСсылкуНового`; поэтому после тайм-аута состояние можно безопасно проверить по известной ссылке. Автоматического повторного выполнения нет.

COM вынесен во внутренний loopback-шлюз `itinvent-docflow-gateway` на `127.0.0.1:8013`. Публичный HTTP не принимает логины, пароли, тексты запросов или имена методов 1С: шлюз получает только HUB user ID и типизированную allowlisted-команду, сам загружает зашифрованные персональные данные и удерживает sticky-сессию в ограниченном пуле. Миграция `20260729_0073` создаёт журнал идемпотентных команд.

В текущей персональной сессии read-only smoke подтвердил поиск входящих и исходящих документов и активных исполнителей. Запрос списка `ВнутренниеДокументы` запрещён правами самой 1С, поэтому этот тип пропускается для данного пользователя, а остальные результаты продолжают возвращаться. Это не обходится сервисной или AD-учётной записью.
