# Перенос техники между базами ITINVENT

Действие «В другую базу» вызывает `POST /api/v1/equipment/transfer/to-db`.
Требуется `database.write`; исходная база определяется существующим request scope,
целевая — явным `target_db`. Инвентарный номер в целевой базе создаётся заново,
прежний сохраняется в карточке и истории. Интеграция не меняет данные 1С.

## Сохранность данных

Поддерживается атомарный перенос пакета между базами одного SQL Server через
целевое подключение. Оно должно иметь права чтения и изменения в обеих базах.
Перенос между разными SQL Server блокируется до изменений.

В пакет входят карточки, CI_HISTORY, обслуживание DEV_SERVICE, комментарии
техники, DOCS/DOCS_LIST, MOVES/MOVES_LIST, комментарии документов и вложения FILES.
Типы документов сопоставляются по CI_TYPES с CI_TYPE=10, типы техники — с CI_TYPE=1.
Модель сопоставляется по категории CI_TYPE, имени, целевому типу TYPE_NO и
производителю VENDOR_NO (производитель предварительно сопоставляется по имени).
Одноимённая модель другого типа или производителя не используется. Локация
сопоставляется по имени и целевому филиалу через LOC_BRANCH; при отсутствии
создаётся отдельная локация с правильной связью. Явно выбранная локация другого
филиала блокирует пакет, включая случай отсутствия BRANCH_NO в LOCATIONS.
Документ и перемещение, общие для нескольких выбранных позиций, копируются один раз.
В целевой базе создаются только связи с перенесённой техникой; оригинальный PDF
сохраняется целиком, без изменения подписи, текста и перечисленных в нём позиций.

Вложения техники выбираются по `(CI_TYPE=1, ITEM_ID=ID техники)`, документы —
по `(CI_TYPE=10, ITEM_ID=DOC_NO)`. Совпадение числовых ID разных типов не даёт
права копировать или удалять чужой файл.

Перед записью проверяются схемы, полнота BLOB, читаемость PDF и неподдерживаемые
связи. Рассчитывается SHA-256 исходных файлов. Генерация нового PDF происходит
без открытой SQL-транзакции. Затем источник повторно читается под блокировками:
карточки, история, файлы, общие связи и используемые записи справочников должны
совпасть со снимком. Проверяются также типы и производители моделей из истории.
Добавление несвязанного сотрудника или другой неиспользуемой записи не отменяет пакет.
Изменение источника, получателя или следующего инвентарного номера отменяет перенос.

В транзакции копируются записи и файлы, создаётся новый акт и его PDF. Перед
удалением исходной техники содержимое и миниатюры скопированных файлов сравниваются
побайтно. Ошибка вставки, проверки, удаления или записи журнала откатывает пакет
в обеих базах. Исходные заголовки документов и их PDF остаются архивными оригиналами;
связи с неперенесёнными позициями не удаляются. Общие FIELDS/FIELDS_LINKS не удаляются.

## Ограничения

Пакет блокируется, если выбранная техника связана с INVENT_LIST, TASKS_LIST,
JOBS_LIST, CARTRIGES_REPLACES или имеет значения дополнительных полей FIELDS_VALUES.
Для этих отношений требуется отдельное согласование правил переноса. Их данные
сохраняются в источнике. Документ без вложений, файл с пустым BLOB, повреждённый
или зашифрованный PDF также блокирует пакет; сообщение указывает причину.
Строковый FIELDS_VALUES.ITEM_ID сравнивается через TRY_CONVERT(int, ITEM_ID),
поэтому ведущие нули, пробелы и знак плюса не обходят блокировку дополнительных полей.

## Повторы, скачивание и задача приёмки

Клиент сохраняет `operation_id` при повторе одинакового запроса после ошибки.
Сессии переноса используют `sp_getapplock` в обеих базах в едином порядке;
конкурирующий запрос получает 409 и может быть повторён.

Журнал результата находится в ADDINFO нового акта: маркер `HUB_DB_TRANSFER_V1`,
ключ операции, SHA-256 параметров и результат. Он фиксируется той же транзакцией,
что перенос и удаление. Повтор с тем же ключом и параметрами возвращает результат
без повторного копирования; изменение параметров даёт 409. Новые таблицы и
миграции для журнала не нужны.
При копировании исторического акта переносится пользовательский текст ADDINFO,
а служебный журнал старого переноса остаётся только в исходном архивном акте.
При чтении журнала сверяются точный ключ, база назначения и DOC_NO оригинального
акта. Это исключает неоднозначность при обратном переносе и поддерживает ранее
созданные копии журналов без изменений production-данных.

Новые PDF хранятся в FILES целевой базы с описанием `HUB transfer receipt PDF v1`.
Скачивание и явная отправка на email используют точный FILE_NO через
`/transfer/to-db/{target_db}/files/{file_no}` и соответствующий `/email`, с правом
`database.write`. Они не зависят от процесса, временного реестра или локального
файла генератора. Исходные PDF открываются штатным API файлов документов.
Доступ разрешён администратору, пользователю текущей целевой базы или автору
конкретной операции из текущей исходной базы. Для последнего случая сверяются
ID автора, обе базы, DOC_NO и FILE_NO в журнале. Для старых журналов без ID автора
используется CREATE_USER_NAME акта. Чужая операция или повреждённый журнал не
дают межбазового доступа; download и email возвращают 403 до отправки файла.

Необязательная задача приёмки создаётся после фиксации переноса. Её результат
дописывается в журнал. Повтор переноса никогда не создаёт вторую задачу. Если
backend остановился между созданием задачи и записью результата, интерфейс
просит проверить существующие задачи перед ручным созданием; сохранность
техники и PDF от этого этапа не зависит.

## Проверки и выпуск

- `tests/test_e2e_equipment_db_transfer.py`: реальные API и сервис на изолированных
  SQLite-базах, соединённых ATTACH; адаптируются SQL Server синтаксис и session lock.
  Проверяются файлы, коллизии ID, общие акты, история, откат, повторы, гонка,
  скачивание и email после очистки реестра, права и неподдерживаемые связи;
  одноимённые модели разных типов/производителей, филиалы локаций, числовые
  строковые ID полей, обратные переносы, старые журналы и изменения справочников.
- `tests/test_e2e_transfer_act_pdf.py`: существующая генерация/скачивание PDF.
- Из frontend: `E2E_LOCAL=1 npx playwright test --config e2e/db-transfer.config.js`.
  Запускается локальный Vite; все API перехватываются браузерным тестом.
- Проверочная сборка только вне live `dist`.

SQLite-проверки не подтверждают SQL Server session lock и реальную межбазовую
транзакцию. Перед production-выпуском необходим такой прогон на выделенных
тестовых SQL Server базах, включая сбой после DELETE и параллельный перенос.
Проверка production-схем и HAS_PERMS_BY_NAME является только read-only preflight.
Деплой и стандартный backend restart требуют отдельного согласования.
