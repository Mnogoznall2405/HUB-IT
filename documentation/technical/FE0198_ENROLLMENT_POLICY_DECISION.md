# FE-0198 — политика обязательной регистрации trusted device: решение для владельца

Статус: **требуется решение владельца**. Дата: 2026-11-25. Кандидат: `integration/hub-it-release-candidate`.

## Вопрос

Является ли регистрация trusted device (passkey) для внешних пользователей **обязательной политикой безопасности** или **рекомендованным UX-шагом**?

## Факты (проверено в коде и конфигурации)

1. **Серверной enforcement-границы нет.** `get_current_user` (`backend/api/deps.py:97-148`) проверяет валидность токена/сессии/неотозванности устройства, но не требует наличия trusted device. `is_token_device_valid` безусловно пропускает сессии без device_id (`trusted_device_service.py:288-291`). Middleware по network_zone отсутствует. Прямой доступ к API с валидной внешней сессией без enrolled-устройства технически возможен — клиентский gate обходится trivially (curl).
2. **Универсальная обязательность невозможна архитектурно**: production-политика `AUTH_PASSKEY_ALLOW_INTERNAL=0` запрещает passkey во внутренней зоне — если бы enrollment был обязателен для всех, внутренние пользователи не смогли бы войти вообще. Клиентский gate потому и scoped только на external-зону.
3. **Реальная серверная «экономика» уже работает**: внешняя сессия без passkey живёт 30 минут idle (`SESSION_IDLE_TIMEOUT_MINUTES=30`, `session_service.py:310-321`), trusted/passkey — 7 дней. Обход клиентского диалога не даёт ничего сверх короткой сессии, которую пользователь уже легитимно имеет.
4. **Клиентский gate** (Login.jsx/App.jsx, коммит `6387fa80`) — честный UX/posture-контроль: переживает F5, deep-link отбрасывается на /login, unsupported-устройства проходят по resolver-политике. Он не является и не может являться security-границей.

## Варианты решения

### Вариант A — принять текущую модель (рекомендуется)
Классифицировать enrollment как **рекомендованный шаг с экономическим enforcement** (30-минутные сессии для незарегистрированных). Клиентский диалог — UX-двигатель adoption. Дополнительно ничего не требуется; риск обхода диалога эквивалентен нулю, т.к. обходящий уже имеет валидную сессию и не получает никаких новых прав.

### Вариант B — mandatory-политика с серверным enforcement (если бизнес требует)
Требует отдельной реализации (вне scope этого релиза):
- limited-scope сессии: external-сессия без trusted device получает scope/claim `device_enrollment_pending`;
- middleware/dependency отклоняет такие сессии на всех роутах кроме enrollment-эндпоинтов (passkey registration, auth refresh, logout);
- матрица исключений: unsupported-платформы (resolver `unsupported`), onboarding, 2FA flow;
- server-side per-zone политика конфигурируемой (env `AUTH_DEVICE_ENROLLMENT_POLICY=off|external_required`).
Оценка объёма: backend middleware + матрица роутов + E2E на обход + миграции не требуются. Риски: lockout пользователей с утерянным/сменённым устройством — нужен recovery-путь (админский reset или step-up через 2FA/пароль с временным окном).

## Рекомендация

Вариант A для текущего релиза: никакого ослабления существующей защиты нет, а mandatory-политика (B) — отдельная продуктовая задача с recovery-дизайном. **Решение за владельцем.**
