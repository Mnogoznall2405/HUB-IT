# HUB Assistant: восстановление результата и подтверждение почты

Обычный HUB Assistant; поведение OpenCode не изменяется. Реализация: `backend/ai_chat/service.py`, `action_cards.py`, `backend/chat/chat_thread_read_store.py`, `realtime_side_effects.py`, `event_outbox_service.py` и frontend chat controllers.

## Состояния

- Run `completed` означает завершение обработки запроса агентом. Это не подтверждение отправки письма.
- Action `pending` — черновик, требующий подтверждения. `executing` — подтверждение принято и операция выполняется; повторное нажатие не начинает новую отправку.
- Для почтового action `confirmed` требуется явный `ok=true` от почтового сервиса либо сохранённый успешный результат mail ledger. Это не доказательство получения письма адресатом.
- `failed` с `result.send_outcome=unknown` означает неопределённый исход. Его нельзя считать доказанным отсутствием отправки и нельзя автоматически повторять. UI предлагает проверить Sent.
- Сервер проверяет TTL и полномочия независимо от состояния открытой вкладки. Даты действий сериализуются с явным UTC offset; naive datetime из SQLite означает UTC.

## Данные и отображение

Карточка — существенная часть результата. Lightweight bootstrap загружает её пакетно; hydration возвращает актуальную карточку вместе с read/delivery/reaction данными. При попадании bootstrap в cache карточки перечитываются из APP, а membership проверяется заново. Удалённое сообщение не раскрывает связанную карточку.

AI-ответ имеет стабильный `client_message_id=ai-run:<run_id>`. В `result_json` сохраняются `result_message_id`, `result_delivery_enqueued` и признак `action_attachment_pending`. HTTP status и WS передают идентификатор результата; status также содержит время создания run. Это добавочные поля, старые потребители сохраняют совместимость.

Frontend не показывает preview рядом с уже доступным результатом того же run и не отмечает текущий этап завершённым. События предыдущих запусков и устаревшие статусы отбрасываются; история этапов нового run начинается заново. Более старая версия той же карточки не откатывает её состояние после подтверждения. Pending/executing карточки освежаются ограниченной hydration и при возврате фокуса; истечение TTL отключает отправку и в открытой вкладке.

## Доставка и восстановление

Готовые viewer-specific `chat.message.created` jobs записываются до необязательных уведомлений и сводок. `chat.message.metadata.refresh` — внутреннее задание существующего outbox, не клиентское событие. Dispatcher вычисляет conversation/unread summaries и записывает дочерние jobs с устойчивыми dedupe keys. Ошибка сводки повторяется штатным outbox и не удерживает готовую карточку.

APP и chat остаются отдельными транзакционными контурами. Глобальная атомарность и exactly-once доставка не обещаются. Повтор события допускается; UI объединяет его по ID.

Существующий AI worker выполняет `repair_result_deliveries` при запуске и раз в минуту. Один проход рассматривает до 50 последних run за сутки. Успешные результаты с маркером доставки пропускаются; незавершённые run восстанавливаются только после существующего stale threshold. Проверяется текущий доступ пользователя к AI-диалогу.

Recovery находит сохранённое сообщение по явной связи или стабильному client ID, восстанавливает привязку action и публикацию. Для действующего почтового черновика без ответа создаёт один ответ с тем же устойчивым client ID. Он не вызывает LLM, бизнес-инструменты или отправку почты. Новая публикация обогащения использует суффикс `:repair`, чтобы уже доставленное первоначальное событие без карточки не поглотило восстановление. Отменённые run не выбираются для восстановления; удалённое сообщение не пересоздаётся.

Если прерванный run восстановлен, его не выдают за полностью успешно выполненный: сохранённый результат доступен, а прерывание отражается в состоянии run. Случаи старше окна восстановления и более ранние версии сообщений без связей требуют отдельного ограниченного разбора; массового переписывания истории нет.

## Подтверждение отправки

Условный переход `pending → executing` сохраняется. Отредактированные payload/preview фиксируются в этой же транзакции до внешнего вызова, чтобы recovery не сверял отправленное содержимое с прежним черновиком.

Поля редактора и выбор вложений блокируются на время отправки: содержимое, которое пользователь видит как подтверждаемое, не меняется во время выполняющейся операции.

AI отправляет `idempotency_key=ai-action:<action_id>` и `require_idempotency=true` в существующий MailService. Для этого вызова ledger обязателен независимо от общего опционального флага почтового UI. Остальные вызывающие стороны сохраняют прежнее значение параметра по умолчанию. Нового сервиса или таблицы эта правка не вводит: используется существующий `app.mail_send_idempotency`.

Чтение/повтор подтверждения восстанавливает `confirmed` только по единственному успешному ledger result соответствующего пользователя и ключа. Зависшее executing старше пяти минут без такого доказательства становится неопределённым исходом; оно не возвращается автоматически в pending. Последующий ledger success может уточнить результат. Сетевой вызов в процессе такого чтения не выполняется.

Общий запрос «Давай ещё раз» после связанной неопределённой/выполняющейся отправки не создаёт новый черновик через LLM: агент предлагает проверить исходную операцию. Явные самостоятельные новые запросы не блокируются как повтор старой задачи.

Если браузер теряет HTTP-ответ подтверждения, frontend перечитывает состояние через hydration, не повторяя POST отправки. При недоступности проверки показывает неизвестный исход без активной кнопки отправки. Редактор закрывается при неизвестном результате, оставляя карточку с действием «Проверить в почте»; запоздавшая ошибка не закрывает другой уже открытый редактор.

## Проверки и выпуск

- HTTP/worker: `tests/test_e2e_ai_draft_reliability.py`, bootstrap anchor, watchdog, mail send idempotency/timeouts и event outbox suites.
- UI: chat model/controller/composer/message tests; native Playwright `chat-ai-reliability.spec.js`, `chat-ai-mail-open.spec.js`, `chat-ai-drafts.spec.js`, `chat-state-recovery.spec.js`.
- Persisted AI E2E seed включается только локальным `E2E_LOCAL=1 E2E_AI_RELIABILITY=1`. Реальные письма не отправляются; seed подменяет outbound mail и использует только тестовую БД.

Выпуск требует отдельного разрешения. До него проверить наличие существующей таблицы ledger и актуальную схему APP, выделить только согласованные изменения из грязного дерева и сохранить rollback. Новая миграция этой правкой не добавлена. Не запускать runtime DDL.

Перезапускаются только согласованные процессы, реально загружающие изменённые модули: AI worker и chat/outbox runtime, а при embedded chat/mail — соответствующий backend. Старый dispatcher не обрабатывает новый внутренний metadata job, поэтому нужен согласованный выпуск producer и consumer. Использовать штатные PM2 scripts; заранее учесть их состав, включая возможный рестарт Scan в backend script. Frontend публикуется в IIS отдельно, с проверкой SHA-256 и сохранением web.config/service worker по release-процедуре.

Rollback возвращает код и frontend artifacts, сохраняя историю, pending actions, outbox и mail ledger. Уже отправленные письма не отменяются откатом. Не сбрасывать unknown/executing в pending и не удалять записи для повтора операции.
