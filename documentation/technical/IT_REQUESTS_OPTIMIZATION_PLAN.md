# План оптимизации раздела «ИТ — заявки на МПЗ»

Статус: реализовано локально, без deployment/PM2/IIS

Дата: 29.08.2026

Область: `WEB-itinvent` frontend/backend и read-only интеграция с 1С `buh20`

## 0. Результат реализации

- Добавлен process-local snapshot с TTL 300 секунд, single-flight, cooldown
  ручного refresh, stale-on-error и snapshot-bound cursor.
- Поиск, вкладки, этап, просрочка, фильтр склада и пагинация выполняются по
  снимку без повторных COM-запросов.
- Добавлены канонический склад назначения, предупреждение о расхождении,
  понятный `current_state`, документы внутри шагов пути и объединённые
  `item_groups`.
- Frontend сгруппирован по складам; склад показан в карточке, повторный chip
  этапа и отдельная хронология удалены, позиции сведены в один адаптивный блок.
- Read-only сверка 29.08.2026: в снимке 46 ИТ-заявок;
  `00ЦБ-000132-ИТ` имеет итоговый этап `fulfilled`, 4 исходные строки,
  4 уникальные позиции и четыре агрегированных связанных документа.
- Локальная серия на живой 1С: холодный отдельный bridge process — 26 763,7 мс,
  внутреннее чтение и построение снимка — 2 357,0 мс; cache-hit списка из 25
  заявок p50 2,56 мс / p95 3,03 мс, поиска p50 0,43 мс / p95 0,69 мс,
  detail p50 0,65 мс / p95 0,75 мс. В серии поиска был один максимум
  3 828,38 мс, поэтому p99 и причина единичного выброса требуют наблюдения
  после отдельной публикации.
- Проверка Chromium с mock API: при ширине 320 px и CSS-эквиваленте масштаба
  200% горизонтального переполнения нет; карточка имеет видимый focus outline
  3 px и основную touch-зону высотой 96 px.

## 1. Целевой результат

Раздел должен отвечать на три вопроса без чтения повторяющихся технических
данных:

1. На какой склад назначения идёт заявка.
2. Что сейчас происходит со всей заявкой.
3. Какая номенклатура и в каком общем количестве заказана.

Основное представление списка — группы по складам назначения. Внутри каждой
группы находятся компактные карточки заявок. В карточке сразу видны склад,
номер, требуемая дата, понятное описание текущего состояния, общий путь и
состав заявки.

Этап остаётся единым для всей заявки. Поступление на склад означает, что заявка
доставлена. Строки номенклатуры не получают отдельные этапы: они являются
составом одной поставки.

## 2. Что подтверждено в текущей реализации

### 2.1. Путь данных

- HTTP API находится в `WEB-itinvent/backend/api/v1/warehouse_1c.py:344`.
- Запрос проходит через `Warehouse1CService`, allowlist process bridge и
  долгоживущий изолированный COM child-process.
- Process bridge выполняет запросы последовательно, ограничивает очередь,
  прерывает зависший COM-процесс по timeout и не допускает запись в 1С.
- Один список сейчас состоит из девяти set-based запросов: заголовки, строки,
  назначения закупщиков, пять видов связанных документов и резервы.
- Это не N+1 по заявкам, но каждый поиск, фильтр и следующая страница повторяют
  весь набор запросов.

### 2.2. Фактическое узкое место

`query_it_requests()` в
`WEB-itinvent/backend/services/warehouse_1c_it_requests.py:799` сначала читает и
полностью рассчитывает до 1000 заявок, затем в Python применяет поиск, вкладку,
этап и просрочку, и только после этого берёт страницу из 25 элементов.

Один read-only контрольный прогон 28.08.2026 занял **29 331,8 мс** и вернул
первые 10 заявок. Это одиночный baseline, а не p95. Все первые 10 заявок имели
одинаковый `warehouse_ref`, что подтверждает наличие склада назначения уже в
данных списка.

Следствия текущей схемы:

- debounce поиска в 350 мс не помогает 1С: новый текст запускает новый полный
  проход, а уже начатый COM-вызов нельзя надёжно отменить;
- переключение вкладки, этапа, просрочки и пагинации снова читает тот же массив;
- автообновление списка и открытой карточки выполняет два обращения;
- для list response полностью строятся `positions` и `timeline`, после чего они
  удаляются перед отправкой;
- offset cursor не привязан к версии данных, поэтому обновление 1С между
  страницами теоретически может дать повтор или пропуск.

### 2.3. Дублирование интерфейса

Сейчас одно состояние повторяется в трёх местах:

- цветной chip этапа;
- линия пути заявки;
- отдельная хронология документов.

Каждая позиция также повторяет одинаковые поля «заказано», «в резерве»,
«запланировано», «поступило», хотя бизнес-этап уже определяется для заявки
целиком. Склад назначения есть в API списка, но показывается только в полной
карточке.

## 3. Принятые продуктовые правила

1. **Склад назначения — первый уровень группировки.** Не подразделение и не
   закупщик.
2. **Этап общий для заявки.** Позиции не показывают собственную шкалу движения.
3. **Любое подтверждённое поступление закрывает поставку.** Заявка получает
   состояние «Доставлено на склад» и переходит в историю.
4. **Путь и документы объединяются.** У каждого шага пути раскрываются
   подтверждающие документы; отдельная повторная хронология по умолчанию не
   показывается.
5. **Одинаковые позиции объединяются.** Количество суммируется по точному ключу
   номенклатуры, характеристики и единицы измерения.
6. **1С остаётся source of truth.** HUB хранит только краткоживущий read-only
   снимок для быстрого чтения и ничего не записывает в 1С.
7. **Первая оптимизированная версия — без Redis, PostgreSQL и миграций.** Снимок
   живёт в долгоживущем process bridge; после перезапуска безопасно строится
   заново.

## 4. Склад назначения

### 4.1. Каноническое определение

Основной источник:

- `Заявка.Склад` → `warehouse_ref`, `warehouse_name`.

Fallback применяется только если склад в заявке пустой или равен «Все склады»:

- используется склад-получатель из плана перемещения или поступления;
- fallback разрешён, только если все найденные документы указывают на один
  `destination_ref`;
- источник сохраняется как `request`, `documents` или `unknown`.

Если склад заявки и склад-получатель в связанных документах различаются,
заявка не переносится молча в другую группу. Она остаётся в группе склада из
заявки и получает предупреждение «Проверить склад назначения».

Пустые и неоднозначные значения собираются в отдельную группу «Склад не
указан».

### 4.2. Порядок групп

Для активных заявок:

1. Склады с просроченными заявками.
2. Склады с ближайшей требуемой датой.
3. Остальные по названию.

Внутри склада: просроченные, затем ближайшая требуемая дата, затем более новая
заявка. В истории: последняя фактическая поставка по убыванию.

### 4.3. Представление

Заголовок группы содержит:

- название склада;
- количество активных заявок;
- количество просроченных;
- ближайшую требуемую дату.

Название склада дополнительно остаётся в каждой карточке заявки. Это нужно для
результатов поиска, мобильного экрана и случаев, когда заголовок группы ушёл за
границу прокрутки.

## 5. Единое представление заявки

### 5.1. Карточка в списке

Порядок информации:

1. Номер заявки и склад назначения.
2. Строка **«Сейчас: …»** с конкретным объяснением:
   - «Ожидает назначения закупщика»;
   - «Закупщик: Иванов И.И.»;
   - «Заказ оформлен у поставщика …»;
   - «Перемещение запланировано на склад …»;
   - «Доставлено на склад …, 03.07.2026».
3. Одна линия пути с точками.
4. Требуемая дата и предупреждения о просрочке/расхождении.
5. Первые наименования и общее число уникальных позиций.

Отдельный chip с названием того же этапа удаляется. Остаются только независимые
предупреждения: «Просрочено», «Проверить данные», «Склад не совпадает».

### 5.2. Полная карточка

Верхний блок содержит только общие данные заявки:

- номер, склад назначения и текущий понятный статус;
- даты заявки, требования и фактической поставки;
- подразделение, инициатор, ответственный;
- закупщик, поставщик, итоговая стоимость;
- комментарий заявки.

Следом показывается общий путь. Документы 1С прикрепляются к соответствующим
точкам и раскрываются по кнопке «Документы этапа». Для документа показываются
номер, дата, поставщик/закупщик, маршрут и сумма. Повторять весь список
номенклатуры в каждом документе по умолчанию не нужно.

Если промежуточный документ не найден, но более поздний этап подтверждён, точка
не окрашивается как найденная. Под ней показывается «Документ в 1С не найден».
Это исключает ложное впечатление полной цепочки.

### 5.3. Объединённый состав

Вместо набора больших `PositionCard` используется один блок «Состав заявки».

Ключ объединения:

```text
(nomenclature_ref, characteristic_name, unit_name, cancellation_bucket)
```

Для строки показываются:

- наименование;
- характеристика, если есть;
- суммарное количество;
- единица измерения;
- отменённое количество и причина, если применимо.

Технически сохраняются `source_line_count` и исходные `line_key`, но в обычном
интерфейсе они скрыты. Заголовок блока показывает, например:
«9 строк в 1С · 7 уникальных позиций».

Поля «заказано», «зарезервировано», «запланировано», «поступило» убираются из
каждой строки. Их подтверждают общие шаги и документы заявки. При количественном
противоречии показывается одно предупреждение уровня заявки с раскрываемой
диагностикой, а не шесть повторяющихся колонок.

На широком экране состав отображается компактной таблицей. При узкой ширине
каждая строка перестраивается в двухрядный элемент: наименование сверху,
количество и характеристика снизу. Горизонтальной прокрутки при 320 px и 200%
быть не должно.

## 6. Оптимизация backend

### 6.1. Immutable snapshot в process bridge

Добавить отдельный `ItRequestsSnapshotStore` внутри долгоживущего COM
child-process:

- TTL по умолчанию — 300 секунд;
- полный набор из девяти запросов выполняется один раз на поколение снимка;
- параллельные запросы объединяются single-flight: только один обновляет 1С;
- остальные получают последнюю успешную версию с `stale=true` и
  `refreshing=true`;
- если первого снимка ещё нет, один запрос ждёт построения в пределах текущего
  timeout; остальные не запускают дополнительные COM-проходы;
- при ошибке 1С предыдущий снимок сохраняется, ошибка и возраст возвращаются в
  метаданных;
- перезапуск bridge автоматически очищает снимок и не требует миграций.

Нужно сохранить режим in-process compatibility: тот же store должен работать
при отключённом bridge и быть потокобезопасным для существующего COM pool.

### 6.2. Разделение summary и detail

При построении снимка один раз рассчитываются:

- компактный `request_summary` для списка;
- полный `request_detail` для открытия карточки;
- группировка складов и счётчики;
- нормализованная поисковая строка каждого summary.

List API больше не строит полный detail заново и не удаляет из него `positions`
и `timeline`. Открытие уже попавшей в снимок заявки не вызывает 1С. Для заявки,
которой нет в текущем снимке, остаётся точечная read-only загрузка по
`request_ref`, после чего detail кратковременно добавляется в cache.

### 6.3. Поиск

Поиск выполняется только по снимку и не обращается к COM. Индексировать нужно:

- точный номер заявки;
- название и ref склада;
- номенклатуру и характеристики;
- подразделение;
- инициатора и ответственного;
- закупщика и поставщика.

Для объёма до 1000 заявок достаточно один раз подготовить `search_blob` и
нормализованные токены; новый сложный поисковый движок не нужен. Правила:

- регистр и повторяющиеся пробелы не учитываются;
- точное совпадение номера получает первый приоритет;
- несколько слов должны находиться все, независимо от порядка;
- пустой и односимвольный запрос не запускают отдельную обработку 1С.

### 6.4. Cursor и сортировка

Заменить чистый offset на непрозрачный snapshot-bound cursor, содержащий
`snapshot_id` и позицию внутри неизменяемого снимка. Это сохраняет стабильный
порядок страниц без повторов и пропусков, пока действует один snapshot.

Если snapshot сменился между страницами, API возвращает явный признак
`snapshot_changed`; frontend начинает выдачу заново и сохраняет выбранную
заявку. Неполный срез нельзя выдавать за полный: `truncated` и причина остаются
в контракте.

### 6.5. Наблюдаемость

Добавить агрегированные метрики без содержимого заявок:

- `snapshot_refresh_ms` и время каждого из девяти этапов чтения;
- количество заголовков, строк и событий;
- cache hit/miss/stale;
- время фильтрации и сериализации;
- queue wait process bridge;
- число coalesced запросов;
- возраст последнего успешного снимка и последняя безопасная ошибка.

Не логировать номенклатуру, комментарии, ФИО и данные подключения.

## 7. API-контракт

Существующие маршруты сохраняются:

- `GET /api/v1/warehouse-1c/it-requests`;
- `GET /api/v1/warehouse-1c/it-requests/{request_ref}`.

В список добавить:

- фильтр `warehouse_ref`;
- `warehouse_groups` со счётчиками по всему отфильтрованному снимку;
- `snapshot_id`, `age_seconds`, `stale`, `refreshing`, `last_success_at`;
- стабильный snapshot-bound cursor;
- `destination_warehouse` и `current_state` в каждом summary.

Кнопка «Обновить» может передавать `refresh=true`, но backend применяет
single-flight и минимальный cooldown 30 секунд, чтобы несколько пользователей
не создавали повторные полные проходы.

Detail возвращает:

- общие данные заявки;
- `destination_warehouse` с источником и признаком расхождения;
- `current_state`;
- путь, где у каждого шага есть агрегированные документы;
- `item_groups` вместо повторяющихся presentation-полей каждой строки;
- диагностические расхождения отдельным массивом.

Старые поля оставить на один совместимый релиз, пометить внутренне как legacy и
удалить после перевода frontend и тестов.

## 8. Изменения frontend

1. Добавить фильтр склада из `warehouse_groups`.
2. Группировать загруженные элементы по `destination_warehouse.ref`; при
   пагинации дополнять уже открытую группу, а не создавать повторный заголовок.
3. Сделать заголовок текущей группы sticky только внутри прокручиваемого списка
   на широком экране; на телефоне оставить обычный поток.
4. Показывать склад в каждой карточке.
5. Заменить StageChip и дублирующую хронологию на `current_state` и один общий
   journey.
6. Заменить набор PositionCard на один `RequestItemsTable` с адаптивными
   строками.
7. Сохранять предыдущие данные при stale/error; рядом со временем показывать
   «Обновляются» или «Данные на …».
8. Не запрашивать detail повторно, если его `snapshot_id` совпадает с текущим и
   карточка уже загружена.
9. Сохранить клавиатурную навигацию, `aria-current="step"`, видимый фокус и

## 10. Проверки и критерии приёмки

### Backend

- первый cache miss выполняет девять set-based запросов, повторные поиск,
  фильтры и страницы — **ноль COM-запросов** до обновления снимка;
- десять одновременных запросов вызывают только один refresh;
- ошибка refresh возвращает предыдущие данные со `stale=true`;
- без предыдущего снимка ошибка остаётся понятной `502`, а не пустым списком;
- поиск по номеру, складу и номенклатуре не зависит от регистра и порядка слов;
- cursor не дублирует и не пропускает заявки внутри одного snapshot;
- склад из заголовка, fallback, unknown и mismatch покрыты отдельно;
- объединение одинаковых позиций суммирует количество и сохраняет отмену;
- detail отсутствующей в снимке заявки делает фиксированный набор запросов без
  N+1.

### Frontend

- склады отображаются отдельными группами и сразу видны в карточках;
- выбор склада, поиск, этап и просрочка работают совместно;
- состояние заявки не повторяется chip, journey и timeline одновременно;
- состав показывает уникальные позиции и суммарное количество;
- load more дополняет существующую группу;
- stale/error сохраняют предыдущий результат;
- нет параллельных auto-refresh запросов;
- клавиатура, 320 px, 200%, тёмная тема и мобильный маршрут проходят тесты.

### Целевые показатели

После получения измеримого baseline:

- cache-hit списка/поиска: p95 backend ≤ 300 мс;
- cache-hit detail: p95 backend ≤ 300 мс;
- не более одного полного чтения 1С за 5 минут на backend instance;
- повторный поиск и переключение фильтров не увеличивают bridge queue;
- размер list response страницы из 25 заявок не больше текущего;
- холодный refresh не должен быть медленнее текущего baseline более чем на 10%,
  пока отдельные 1С-запросы не оптимизированы доказательно.

Показатель 29 331,8 мс нельзя считать p95 и нельзя использовать как итоговое
доказательство ускорения: до/после сравниваются одинаковыми сериями прогонов и
на одинаковом объёме данных.

## 11. Сверка с 1С

Read-only приёмка выполняется минимум на:

- `00ЦБ-000161-ИТ` — многострочная заявка и объединённый состав;
- `00ЦБ-000132-ИТ` — поступление и финальный этап;
- заявка с несколькими одинаковыми строками;
- заявка без склада;
- заявка с несовпадением склада заголовка и документа;
- отменённая заявка и заявка с количественным противоречием.

Для каждой сверяются `request_ref`, `warehouse_ref`, количество исходных строк,
сумма объединённых позиций, текущий этап и номера подтверждающих документов.

## 12. Не входит в эту работу

- запись или проведение документов в 1С;
- ручные статусы и комментарии HUB;
- Redis, новый broker или отдельный сервис;
- обязательная PostgreSQL-миграция для cache;
- изменение прав доступа;
- изменение бизнес-правила «поступило на склад — доставлено»;
- деплой, рестарт PM2 и публикация IIS без отдельного разрешения.
