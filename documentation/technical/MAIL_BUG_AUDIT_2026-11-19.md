# Аудит почты HUB — 2026-11-19

Проверено текущее рабочее дерево: Exchange/EWS и FastAPI, веб-почта, нативный HUB Desktop и Expo-клиент Android. Это отчёт о диагностике, не список выложенных изменений. Код, настройки, реальные ящики и прод не менялись.

**Итог: 18 открытых находок — 11 воспроизведены локально, 7 подтверждены трассировкой кода.** Первыми исправить безвозвратное удаление цепочки в Android, гонку повторной отправки и отмену переноса. Отдельно перечислены прежние исправления и вопросы, на которые локальные проверки не отвечают.

- **R** — механизм воспроизведён на локальной фикстуре; это не подтверждение инцидента в проде.
- **S** — поведение подтверждено по коду и цепочке вызовов; сквозной сценарий не запускался.
- **P1** — риск необратимой потери или дублирования; **P2** — неверная операция, скрытая неполнота или серьёзный сбой рабочего сценария; **P3** — ограниченный сценарий либо проблема диагностики.
- Ссылки ведут к проверенным строкам текущего рабочего дерева; номера могут сдвинуться после правок.

## Открытые дефекты

### MAIL-01 · P1 · R — Android может безвозвратно удалить цепочку после подтверждения обычного удаления

- **Где:** [подтверждение по видимым строкам](../../mobile-hub/src/mail/useMailSelection.ts#L273-L292), [расширение цепочки и выбор режима удаления](../../mobile-hub/src/mail/useMailSelection.ts#L145-L181).
- **Воспроизведение:** открыть «Удалённые» в режиме цепочек, выбрать цепочку с одним письмом и нажать «Удалить». Диалог обещает переместить письма в «Удалённые». После подтверждения выполнился запрос `permanent: true` с ID письма. Проверка вызвала реальный хук, подставив диалог и API; запрос не уходил на сервер.
- **Причина:** диалог считает только строки отдельных писем. Фактические письма извлекаются из цепочки после подтверждения, и `runBulk` сам повышает режим удаления до необратимого.
- **Критерий исправления:** сначала определить состав операции; письмо из корзины можно удалить навсегда только после явного подтверждения именно для этого набора. При сбое раскрытия цепочки ничего не удалять без переоценки состава.

### MAIL-02 · P1 · R — два повторных запроса могут одновременно получить право отправить одно письмо

- **Где:** [чтение записи и переход `failed → processing`](../../WEB-itinvent/backend/services/mail_send_idempotency.py#L338-L377). Ранее отмечено как DMAIL-04.
- **Воспроизведение:** в тестовой SQLite создать запись отправки и перевести её в `failed`. Два независимых соединения прочитали эту запись до обновления (барьер после чтения). Оба вызова `claim` с одним ключом вернули `proceed`. На Exchange ничего не отправлялось; на PostgreSQL тест не запускался.
- **Причина:** переход основан на ранее прочитанном статусе, а запись обновляется без проверки, что другой запрос не захватил её первым. Уникальность при первоначальном `INSERT` не покрывает этот переход.
- **Критерий исправления:** из двух одновременных попыток только одна получает `proceed`; второй запрос получает текущий исход. Проверить две независимые сессии на тестовом PostgreSQL. Отдельно проверить переход из `reserved`, не считать его доказанным этим тестом.

### MAIL-03 · P2 · R — веб ошибается в результате переноса и не может его отменить

- **Где:** [массовый перенос](../../WEB-itinvent/frontend/src/components/mail/useMailBulkActions.js#L85-L113), [перенос перетаскиванием](../../WEB-itinvent/frontend/src/components/mail/useMailBulkActions.js#L153-L183), [отмена](../../WEB-itinvent/frontend/src/components/mail/mailMoveUndo.js#L29-L53), [новый ID на сервере](../../WEB-itinvent/backend/services/mail_message_actions.py#L203-L215).
- **Воспроизведение:** выбрать два письма из разных папок в общей выдаче. Для одного вернуть новый ID после переноса, для другого — ошибку. Веб сообщил о двух перемещённых письмах. При отмене вызвал перенос по старому ID первого письма в открытую папку; фикстура вернула ошибку, письмо осталось в назначении.
- **Критерий исправления:** показывать число реальных успехов и ошибок; отменять только успешные операции по новому ID и в исходную папку каждого письма. Проверить те же инварианты для переноса одного письма, перетаскивания и переноса из панели чтения.

### MAIL-04 · P2 · R — отмена массового переноса в Android возвращает письма в открытую, а не в исходную папку

- **Где:** [запись данных отмены](../../mobile-hub/src/mail/useMailSelection.ts#L230-L248), [применение отмены](../../mobile-hub/src/screens/mail/NativeMailInboxScreen.tsx#L521-L537).
- **Воспроизведение:** во входящих выбрать два результата поиска по всем папкам — из архива и отправленных — и переместить их. Локальный хук сохранил оба новых ID, но записал единственный `sourceFolder: inbox`; обработчик отмены использует его для всех ID. Реальное состояние ящика не менялось.
- **Критерий исправления:** связать каждый новый ID с его исходной папкой и отдельно обработать ошибки отмены. Проверить также смешанный набор при мягком удалении, где тот же обработчик выполняет обратный перенос.

### MAIL-05 · P2 · R — цепочка без писем из архива сохраняется в кэше как полная

- **Где:** [источник списка папок](../../WEB-itinvent/backend/services/mail_service.py#L2494-L2510), [кэш и компоновка цепочки](../../WEB-itinvent/backend/services/mail_service.py#L4476-L4528).
- **Воспроизведение:** через локальный FastAPI `TestClient` открыть цепочку в области «Все папки». Подставный архив падает при обходе дерева, письмо во входящих доступно. Ответ: `200`, одно письмо, `conversation_complete: true`. После имитации восстановления архива второй запрос вернул то же одно письмо без попытки обойти архив.
- **Причина:** поиск уже передаёт сведения о пропущенных папках, а получение цепочки использует путь, который их отбрасывает. Это **не** ранее исправленный сбой загрузки тела найденного письма.
- **Критерий исправления:** не помечать результат полным и не записывать его в кэш полных цепочек при сбое обхода; повтор после восстановления включает архивное письмо. Операции над целой цепочкой не должны считать такой ответ полным.

### MAIL-06 · P2 · R — «Прочитано / непрочитано» для цепочки действует лишь в пределах окна

- **Где:** [действие над цепочкой](../../WEB-itinvent/backend/services/mail_service.py#L3556-L3594), [бюджет сканирования](../../WEB-itinvent/backend/services/mail_conversation_finder.py#L54-L82).
- **Воспроизведение:** на локальном маршруте `POST /mail/conversations/{id}/read` с `folder_scope=all` задать бюджет 2 и два совпадения цепочки: одно в начале входящих, второе в архиве. Ответ `200`, `ok=true`, `changed=1`, `failed=0`; старое письмо осталось непрочитанным. Обратное действие использует тот же общий метод.
- **Критерий исправления:** изменить статус всей цепочки в запрошенной области либо честно сообщить о частичном результате; не обновлять счётчики как для полностью обработанной цепочки. Сохранить границы «Текущая папка» и «Все папки».

### MAIL-07 · P2 · R — «Отметить всё прочитанным» сообщает об успехе после сбоя

- **Где:** [чтение папки бэкендом](../../WEB-itinvent/backend/services/mail_message_actions.py#L167-L186), [обработка результата в отфильтрованном веб-списке](../../WEB-itinvent/frontend/src/components/mail/useMailMarkAllRead.js#L76-L112).
- **Воспроизведение:** локальный маршрут `POST /mail/messages/mark-all-read` после таймаута обхода папки вернул `200`, `ok=true`, `changed=0`, `failed=0`: сбой заменён пустым списком. Отдельно локальный веб-хук получил `succeeded=0`, `failed=2`, но показал «Отмечено как прочитанное: 2». В режиме цепочек веб также считает успешным сам факт ответа, а не результат внутри него.
- **Критерий исправления:** отличать пустую папку от ошибки обхода; показывать подтверждённое количество успехов и ошибки, не подменять явный ноль числом выбранных строк.

### MAIL-08 · P2 · R — отдельный фильтр «Текст письма» теряет старые совпадения

- **Где:** [построение ограничений EWS](../../WEB-itinvent/backend/services/mail_message_listing.py#L119-L162), [выбор быстрого запроса](../../WEB-itinvent/backend/services/mail_message_listing.py#L174-L242).
- **Воспроизведение:** два последних письма без нужного текста, старое письмо с совпадением только в теле; бюджет 2. При одинаковой фикстуре обычный `q` вернул старое письмо, явный `body_filter` — пустую выдачу с `search_limited=true`. Условие в локальной модели EWS работает; поведение конкретного сервера и индекса по этому сценарию не измерялось.
- **Причина:** `body` входит в серверную рестрикцию для общего запроса, но не для отдельного фильтра. Последний проверяется при обходе ограниченного окна кандидатов.
- **Критерий исправления:** проверить ограничение по телу на согласованном тестовом Exchange, сохранить проверку отображаемого текста и честный fallback. Старое совпадение доступно для поля «Текст письма» в списках писем и цепочек без увеличения клиентского кэша.

### MAIL-09 · P2 · R — Android теряет область «Все папки» при действиях с цепочкой

- **Где:** [область запроса списка](../../mobile-hub/src/mail/useMailList.ts#L127-L144), [раскрытие выбранной цепочки](../../mobile-hub/src/mail/useMailSelection.ts#L97-L122), [загрузка и отметка при открытии](../../mobile-hub/src/screens/mail/NativeMailConversationScreen.tsx#L125-L151).
- **Воспроизведение:** в локальном хуке выбора для списка «Все папки» выбрать цепочку; API раскрытия запрошен с `folderScope: current`. В результате письмо в другой папке не входит в набор действия. Сам экран цепочки тоже явно задаёт `current` при чтении и отметке; это подтверждено трассировкой, не запуском навигации на устройстве.
- **Критерий исправления:** переносить область и выбранный ящик из списка в детали и управляющие операции. Сценарий с цепочкой только в архиве при открытых «Входящих» должен работать без перехода в архив.

### MAIL-10 · P3 · R — сервер молча пропускает пустой файл при пересылке и удержании вложений черновика

- **Где:** [чтение файлового вложения](../../WEB-itinvent/backend/services/mail_message_content.py#L49-L64), [подготовка вложений пересылки и черновика](../../WEB-itinvent/backend/services/mail_service.py#L3821-L3886).
- **Воспроизведение:** передать выбранное вложение `empty.txt` с содержимым `b''`, используя `exchangelib.FileAttachment` и подставной протокол. Подготовка скачивания вернула имя и 0 байт; оба сборщика вложений вернули пустой список, хотя ID файла явно выбран.
- **Критерий исправления:** отличать корректный файл длиной 0 от недоступного содержимого. Если отправлять такие файлы нельзя, сообщать об этом явно и до отправки, а не выбрасывать их молча.

### MAIL-11 · P2 · S — защита от повтора почтовой ИТ-заявки не подключена в Android

- **Где:** [форма Android](../../mobile-hub/src/screens/mail/NativeMailInboxScreen.tsx#L666-L689), [POST без ключа](../../mobile-hub/src/api/mailApi.ts#L651-L658), [приём ключа на сервере](../../WEB-itinvent/backend/api/v1/mail.py#L2221-L2260).
- **Проверка кода:** сервер, веб и нативный Desktop уже поддерживают ключ. Android блокирует только одновременное нажатие, но следующий POST после таймаута не содержит `Idempotency-Key`. Вероятный результат при принятой Exchange первой попытке — повторная заявка; этот Android-сценарий сквозным тестом не воспроизводился.
- **Критерий исправления:** один ключ на повтор неизменённой заявки, новый ключ для нового действия; тест с имитацией таймаута после принятия, без реальной отправки.

### MAIL-12 · P2 · S — Android не сообщает о недоступных папках в поиске

- **Где:** [метаданные ответа бэкенда](../../WEB-itinvent/backend/services/mail_message_listing.py#L403-L414), [обработка предупреждений в Android](../../mobile-hub/src/mail/useMailList.ts#L252-L259).
- **Проверка кода:** сервер возвращает `skipped_folders` отдельно от `search_limited`; Android показывает только предупреждение о лимите. При `skipped_folders > 0` и `search_limited=false` приложение не объясняет, что пустая выдача может быть следствием сбоя папки.
- **Критерий исправления:** показать обе причины неполноты отдельно, в том числе при пустом ответе. Проверить отсутствие предупреждения после успешного повторного запроса.

### MAIL-13 · P2 · S — локальная ошибка после принятия письма Exchange всё ещё может вернуть ошибку отправки

- **Где:** [код после успешного EWS](../../WEB-itinvent/backend/services/mail_service.py#L5084-L5144). Остаток DMAIL-02.
- **Проверка кода:** при исключении, например на инвалидации кэша, сервер пытается записать `sent`, но затем журналирует `failed` и выбрасывает ошибку. С тем же ключом и рабочим журналом повтор уже не должен отправить ещё раз — это исправленная часть. Без ключа, при смене ключа либо при сбое хранения исхода такой ответ может подтолкнуть к дублю. Инъекцию сбоя в локальный журнал в этом проходе не делали.
- **Критерий исправления:** успешный EWS не превращать в ложный отказ из-за ошибки локального учёта; проверить HTTP-ответ, статус журнала и единственный вызов отправки при повторе.

### MAIL-14 · P3 · S — нативная ветка EWS-ответа теряет идентификатор сверки отправки

- **Где:** [развилка threaded reply / обычное письмо](../../WEB-itinvent/backend/services/mail_send_pipeline.py#L250-L280). Прежний DMAIL-06.
- **Проверка кода:** обычное письмо получает `Internet-Message-ID` из журнала отправок. Нативная ветка ответа вызывается раньше и не получает этот идентификатор. Это недостаток сверки неизвестного исхода, не доказательство повторной отправки; поведение реального Sent здесь не проверялось.
- **Критерий исправления:** определить надёжный идентификатор для сверки каждого режима отправки и подтвердить его на тестовом Exchange.

### MAIL-15 · P3 · S — отмена HTTP-отправки трактуется как «не отправлено», хотя сервер может продолжать

- **Где:** [классификация отмены](../../WEB-itinvent/frontend/src/components/mail/mailSendOutcome.js#L60-L73), [жизненный цикл задачи Exchange](../../WEB-itinvent/backend/api/v1/mail.py#L434-L477). Прежний DMAIL-07.
- **Проверка кода:** веб классифицирует `ERR_CANCELED` без ответа как `NOT_SENT`; отмена ожидания HTTP не гарантирует отмену уже запущенного синхронного вызова. Конкретное сообщение интерфейса при уходе с экрана не проверялось.
- **Критерий исправления:** различать отмену до отправки запроса и отмену после начала обработки; во втором случае не обещать, что письмо не отправлено.

### MAIL-16 · P3 · S — догрузка Android берёт смещение из числа видимых строк

- **Где:** [отправляемое смещение и удаление дублей](../../mobile-hub/src/mail/useMailList.ts#L119-L145), [слияние страниц](../../mobile-hub/src/mail/useMailList.ts#L213-L226), [поля ответа](../../mobile-hub/src/api/mailApi.ts#L94-L105).
- **Проверка кода:** клиент вычисляет `offset` как `items.length` и не использует `next_offset`. После дедупликации или локального удаления строк это число не обязано совпадать с позицией сервера; возможны повторное чтение страницы или неверная догрузка. Сценарий с изменяющимся ящиком на устройстве не запускался.
- **Критерий исправления:** хранить смещение из ответа в рамках ключа выдачи, сбрасывать его вместе с фильтром и тестировать страницы с пересечением и локальным обновлением.

### MAIL-17 · P2 · R — лента уведомлений кэширует неполную выдачу после сбоя одного ящика

- **Где:** [выбор кэша и обход ящиков](../../WEB-itinvent/backend/services/mail_service.py#L4134-L4194), [запись результата](../../WEB-itinvent/backend/services/mail_service.py#L4217-L4237).
- **Воспроизведение:** в сервисе локально подставить два ящика. Второй вернул таймаут, первый — одно письмо. Результат записался как обычный общий ответ. После имитации восстановления второго ящика следующий запрос вернул кэшированное письмо первого и ни один ящик не перечитал. Длительность на реальном сервере не измеряли; код задаёт TTL в пределах 10–30 секунд.
- **Причина:** обход кэша определён только по входному списку пропуска, а ошибки, обнаруженные в самом запросе, не запрещают запись частичного ответа.
- **Критерий исправления:** не заменять общий успешный снимок заведомо частичным; повтор после восстановления должен снова проверить отсутствовавший ящик. Не путать кратковременную задержку ленты с потерей письма в Exchange.

### MAIL-18 · P3 · S — Desktop меняет счётчик открытой папки при действии с письмом из другой папки

- **Где:** [локальное применение массового действия](../../desktop/Hub.Desktop/Native/ViewModels/MailViewModel.cs#L3609-L3669), [выбор счётчика](../../desktop/Hub.Desktop/Native/ViewModels/MailViewModel.cs#L3678-L3687).
- **Проверка кода:** в общей выдаче Desktop разрешает массовые отметки и перенос. После операции он складывает дельты всех писем и применяет их к `_currentFolder`, даже если среди выбранных писем нет писем этой папки. Например, отметка архивного письма может временно уменьшить счётчик входящих. Следом запрашивается дерево папок; если обновление успешно, оно может исправить счётчик. Этот сценарий на WPF не запускался.
- **Критерий исправления:** применять изменения только к фактическим папкам успешно обработанных писем; отдельно проверить смену папки, пока ответ операции ещё не пришёл.

## Дополнение 2026-11-20 — семантика пагинации exchangelib и параллельный поиск

### MAIL-19 · P1 · подтверждено на живом ящике — срезы queryset exchangelib теряют страницы поиска

- **Где:** `backend/services/mail_message_listing.py` — старый цикл `qs[offset:offset+limit]` и его вариации.
- **Факты (замерено на рабочем ящике, 16 почтовых папок):**
  - `qs[0:250]` на одиночной папке вернул 300 элементов (серверная страница), `qs[250:500]` — ещё 300 с пересечением 50. То есть срез игнорирует `stop` и отдаёт `page_size` элементов от `offset`.
  - На `FolderCollection` срез `qs[250:500]` вернул **0**, хотя итератор того же queryset выдал 250+250 разных элементов — offset-навигация по коллекции сломана.
  - Повторный срез на уже прочитанном queryset тоже возвращает 0.
- **Следствие:** код вида `page = qs[a:a+limit]; if len(page) < limit: stop` читал ровно одну серверную страницу и обрывался — это подтверждённая причина, почему старые письма «не искались»: нефильтрованный проход видел ~300 новейших элементов папки.
- **Исправление:** один `iter()` на queryset + `itertools.islice` последовательно; навигация смещениями запрещена (см. комментарии в коде).

### MAIL-20 · P1 · подтверждено — поток `FolderCollection` не отсортирован глобально

- **Факты:** при `.order_by("-datetime_received")` в первых 400 элементах смешанного потока встречались нарушения порядка даже внутри одной папки.
- **Следствие:** ранняя остановка по границе timestamp («хвост старше N-го совпадения») безопасна **только** для однопапочного потока; на `FolderCollection` она теряет результаты. Кап убран из батч-пути, оставлен в `scan()`/`scan_parallel`, где поток серверно отсортирован по папке.

### Переделка сканирования (2026-11-20)

- `scan_parallel`: задача — страница папки, а не папка целиком; переочередь в конец гарантирует, что каждая папка читает первую страницу до второй страницы любой папки (та же честность, что у последовательного `deque`). Первая страница папки ограничена честной долей бюджета `remaining // folders_left`, дальнейшие — полным `batch_size`.
- `scan_batches` (`FolderCollection`) оставлен только для ящиков с числом папок > `multi_folder_batch` (по умолчанию 25): там один FindItem на батч реально дешевле. Порог настраивается параметром билдера.
- Баг честности: при кириллическом запросе досмотр пропускается, но быстрый проход вызывался с `supplement_follows=True` — папка, отклонившая серверный фильтр, молча терялась. Теперь флаг равен фактическому `supplement_needed`.
- Живые замеры (ящик, 16 папок): «заявка» 5.4 с холодная / 3.4 с тёплая (`limited=True` — кап плотных папок), «Муртаев» 1.5 с (`limited=False`), ASCII `murtaev` 13.7 с — досмотр упирается в дедлайн, результат 0 правдоподобен.
- **Ограничение:** латинские адресные запросы по-прежнему платят нефильтрованным досмотром (~6–10 с на большом ящике); дедлайн мягкий — зависшие страницы в полёте не прерываются.

### MAIL-42 · P3 · исправлено 2026-11-21 — лексикографическое сравнение `received_at` ломалось на разных тайзонах

- Три сайта сравнивали ISO-строки `received_at`/`last_received_at` оператором `>`: `mail_service.list_notification_feed` (сортировка агрегированного feed по всем ящикам), `mail_notification_service._should_emit` (`received_newer`), `mail_conversation_payloads` (выбор последнего сообщения в ветке + сортировка списка бесед). EWS `datetime_received` сериализуется в ISO со смещением (`+03:00` и т.п.): `"10:00+03:00" > "08:00+00:00"` строкой, хотя по UTC первое старше. У пользователя с ящиками на серверах в разных тайзонах (или сообщениями через границу DST): top-item feed мог указывать на более старое письмо → пуш о не том сообщении, а `received_newer=False` при фактически более новом письме → пропущенное уведомление (`last_message_changed` без `received_newer` не триггерит, если метки не равны).
- Фикс: `received_at_epoch()` в `mail_message_listing.py` — `fromisoformat` с заменой `Z`, naive → UTC, непарсибельное → `-inf`; применён во всех трёх сайтах (сортировки — epoch + строковый tie-break; `_should_emit` — epoch-сравнение, пустой baseline → `-inf` сохраняет прежнюю семантику).
- Тесты: `test_should_emit_when_newer_message_arrives_with_older_wall_clock_tz` (10:00+03:00 → 08:00+00:00 — раньше пропускалось) и `test_should_not_emit_when_older_message_arrives_with_newer_wall_clock_tz` (обратный случай).
