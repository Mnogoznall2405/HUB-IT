# План улучшения mobile-hub APK

Дата: 2026-09-04.

Основание: `MOBILE_HUB_APK_AUDIT_MAP.md` и текущее рабочее дерево. План не разрешает deployment, рестарт production или изменение auth policy. Каждый этап — отдельный минимальный вертикальный срез с тестами и измерением результата.

## Цель

Сделать нативный APK предсказуемым в четырёх режимах:

1. быстрый безопасный запуск online;
2. быстрый безопасный запуск offline через настроенную биометрию;
3. мгновенные локальные переходы и показ ранее открытых данных без сети;
4. отсутствие лишних запросов, подвисаний списков и неоправданно большого release-файла.

## Предлагаемые критерии

Это цели для измерения на согласованном Android-устройстве, а не текущие подтверждённые показатели:

- cold start p95 до защищённого экрана: не более 2,5 с при рабочей сети;
- offline cold start p95 до biometric gate: не более 1,5 с;
- cached route TTI p95: не более 500 мс;
- локальный переход без сети: реакция интерфейса до 100 мс;
- длинные списки: JS/UI не ниже 55 FPS в типовом scroll;
- не более одного согласованного запроса счётчиков при старте/resume;
- никакого полного `/chat/conversations` только ради badge;
- arm64 release: целевой размер не более 46 МиБ, если парк устройств допускает arm64-only.

## Этап 0. Baseline и защитные тесты

До оптимизации:

1. выбрать контрольное Android API 33+ устройство;
2. измерить 20 cold и 20 warm запусков, p50/p95;
3. измерить PSS после запуска, после списка чатов и медиа-диалога;
4. посчитать HTTP-запросы старта, resume и перехода по push;
5. зафиксировать JS/UI FPS для адресной книги, задач, почты и чата;
6. разобрать JS bundle через Expo Atlas;
7. сохранить размер APK и распределение по ABI/native libs.

Автотесты до изменений должны фиксировать текущие контракты auth, logout, snapshots, offline-очередей, push route и непрочитанных счётчиков.

## Этап 2. Единое состояние связи и счётчиков

### Connectivity state

Ввести один агрегированный статус:

```text
offline | local-ready | api-checking | api-online | realtime-degraded | auth-required
```

- успешный REST/auth означает, что HUB online;
- WebSocket показывает качество realtime отдельно;
- бесконечного spinner нет: после bounded timeout выводится понятное состояние и доступно повторное действие;
- локальная навигация, back, tabs и анимации не блокируются сетью.

### UnreadCoordinator

Объединить навигацию, Android badge и Dashboard вокруг одного источника:

- один single-flight snapshot счётчиков;
- события coalesce в окно 500–1000 мс;
- resume не запускает три независимых контура;
- chat badge использует `/chat/unread-summary`, а не полный список диалогов;
- nav и системный badge подписываются на одно локальное состояние;
- тесты reconnect, duplicate events, foreground и push action.

### Срез 2A. REST/realtime presentation и общий unread snapshot — выполнено кодом

- валидированная auth/REST-сессия сразу переводит общий HUB-индикатор в «На связи», даже пока WebSocket ещё подключается;
- отказ realtime при рабочем REST отображается как «На связи · без мгновенных обновлений»;
- nav, Dashboard и Android launcher badge делят один permission-aware snapshot с коротким bootstrap cache и single-flight;
- стартовая загрузка сокращена с семи счётчиковых/dashboard HTTP-вызовов до четырёх, без загрузки полного списка диалогов;
- realtime и явные пользовательские refresh обходят bootstrap cache, локальное изменение mail unread сразу пересчитывает launcher badge;
- физическая проверка переходов online/offline/realtime-degraded на Android остаётся обязательной.

## Этап 3. Полный offline-контракт — базовый runtime реализован

Целевая форма declarative-реестра модулей вместо разрозненного списка scope:

```ts
type OfflineModuleDescriptor = {
  id: string;
  listScope?: string;
  detailScope?: string;
  preload?: () => Promise<void>;
  validate: () => Promise<'complete' | 'partial' | 'missing' | 'corrupt'>;
  sensitivity: 'normal' | 'confidential';
  mutationPolicy: 'blocked' | 'queued' | 'local-only';
};
```

Текущий runtime уже централизует permission-aware список обязательных scope и хранит отдельный зашифрованный coverage manifest. Полный переход на `OfflineModuleDescriptor` остаётся архитектурным улучшением и не блокирует проверяемую готовность существующих модулей.

Порядок покрытия:

1. Лента: список и ранее открытая запись — выполнено 2026-09-02; стандартный список входит в подготовку, локальный поиск/фильтры и сохранённая карточка с комментариями работают без сети;
2. Инвентарь: выполнено 2026-09-02; подготовка постранично сохраняет полный каталог оборудования каждой доступной базы в атомарных зашифрованных shards, поиск, QR и открытие любой карточки из каталога работают локально, а ранее открытая карточка дополнительно сохраняет загруженные вкладки;
3. Мои файлы: выполнено 2026-09-02; метаданные списка и квота сохраняются, карточка позволяет явно закрепить файл в постоянном app-private каталоге и удалить только локальную копию, зашифрованный manifest изолирован по пользователю и проверяет размер/срок хранения;
4. Структура компании: выполнено 2026-09-02; дерево входит в подготовку, открытые подразделения сохраняют сотрудников, поиск по сохранённым данным работает локально;
5. Пароли и МФУ включены по умолчанию; их offline-кэш не добавляется без отдельной модели защиты данных. Остальные canary-модули — только после включения для пользователей.

Реализовано 2026-09-04: persistent manifest изолирован по `userId` и хранит по модулю `complete/partial/failed`, `loaded`, `total`, единицу измерения, ревизию, время успешного сохранения, время последней попытки и очищенную от URL/секретов причину ошибки. Настройки показывают этот прогресс отдельно от общей готовности scope.

Адресная книга проверяется только специализированным reader: manifest + все shards + количество элементов. Наличие одного manifest-файла не считается готовностью.

Полные каталоги адресной книги и Инвентаря обновляются local-first без блокировки интерфейса: после входа, при восстановлении сети, на foreground и через Android BackgroundTask. Автоматическое обновление ограничено интервалом шесть часов; Android определяет фактический момент фонового запуска по сети, заряду и системным ограничениям. Неуспешная или неполная загрузка не заменяет последнюю целую локальную ревизию.

Готовность offline теперь считается по всем обязательным scope, доступным текущему пользователю. Наличие одной сохранённой страницы означает частичную готовность, а настройки явно показывают недостающие разделы. Payload обязательного снимка проверяется по контракту; для Инвентаря отдельно требуются корректный стартовый список и полный catalog snapshot каждой доступной базы.

Файловый слой разделён на:

- временный cache, который может очистить Android;
- persistent app-private storage для успешно открытых/скачанных вложений Chat, Mail, Tasks, 1С ДО, Feed и Инвентаря, а также для явно закреплённых файлов «Моего диска». Файлы изолируются по пользователю, записываются через `.part`, проверяются перед commit и очищаются пользователем/logout. Содержимое файла не загружается целиком в JS для дополнительного шифрования; защита at-rest опирается на приватное хранилище и шифрование устройства Android. Поведение при нехватке места и восстановлении процесса остаётся частью физической Android-приёмки.

## Этап 4. Быстрый auth и переход из уведомления

Без ослабления безопасности:

1. разделить состояния `secure gate ready` и `server session validated`;
2. при подтверждённом offline не ждать два сетевых timeout перед предложением биометрии;
3. не показывать cached identity до успешного biometric unlock;
4. 401/403 по-прежнему очищает недействительную сессию;
5. pending deep link сохраняется до unlock и открывается сразу после него;
6. transport error не превращается в logout;
7. после восстановления сети выполняется тихая серверная валидация и revalidate открытого модуля.

Проверки: online, DNS failure, captive portal, airplane mode, expired refresh, revoked device, cold push, killed process и возврат из background.

### Срез 4A. Завершение inline-ответа из Android-уведомления — выполнено кодом

- исходное RemoteInput-уведомление сразу обновляется с тем же Android identifier/tag, поэтому системный индикатор ввода закрывается штатным способом;
- состояния «Отправка ответа…», а затем «Ответ отправлен», «Ответ сохранён» либо «Ответ не отправлен» заменяют одну и ту же карточку без гонки между dismiss и финальным notify;
- операции Expo Notifications ограничены 1,5 с, а полный сетевой этап быстрого ответа — 8 с; при зависании точный текст уходит в очередь повторной доставки;
- завершение background action больше не ждёт сетевой badge-reconcile или зависший `clearLastNotificationResponseAsync`; эти некритичные операции запускаются отдельно от системного RemoteInput;
- offline-очередь и повторная отправка сохранены, `clientMessageId` остаётся идемпотентным;
- добавлены регрессии на раннюю замену карточки, ошибку Expo API, зависший REST Promise, badge-reconcile, dismiss и notification cleanup;
- физическая проверка inline reply на Android остаётся обязательной перед release.

### Срез 4B. Быстрый cold start и переход из push — выполнено кодом

- если Android уже сообщает подтверждённый offline, bootstrap не запускает `/auth/me` и сразу показывает безопасный login/biometric gate;
- cached identity по-прежнему не раскрывается до успешного biometric unlock;
- `/auth/me`, refresh, повтор запроса и короткий transport-retry делят единый бюджет 5 секунд вместо отдельных полных таймаутов;
- 401/403 по-прежнему очищают недействительную сессию, а transport timeout сохраняет локальные credentials для offline unlock;
- некритичные push-token, badge и offline-queue синхронизации запускаются в первый idle-период после начального render, поэтому не конкурируют с переходом по уведомлению;
- добавлены регрессии на известный offline, общий timeout budget, cold push destination и idle scheduling;
- физические p50/p95 и cold push route TTI остаются обязательными перед release.

### Срез 5A. Обслуживание cache медиа чата — выполнено кодом

- cleanup использует один полученный список файлов вместо двух последовательных `Directory.list()`;
- первый media hit выполняет один контрольный проход, последующие hit в течение 5 минут не сканируют каталог;
- новая загрузка накапливает size delta и запускает внеочередное обслуживание после 16 МиБ, поэтому лимит не зависит только от времени;
- глобальная очередь допускает максимум три одновременные preview-загрузки; запрос, отменённый до получения слота, удаляется из очереди без сетевого вызова;
- ошибка best-effort cleanup не превращает существующий cache-hit в ошибку загрузки изображения;
- детерминированный тест зафиксировал сокращение двух последовательных cache-hit с четырёх обходов каталога до одного;

## Матрица приёмки

Каждый срез проходит:

1. узкие unit/component tests;
2. `npm run lint`;
3. `npm run test:ci -- --silent`;
4. `npx expo-doctor` для dependency/build изменений;
5. Android export;
6. physical smoke на API 33+;
7. повтор baseline с p50/p95, request count, PSS и FPS;
8. проверку dark/light, 360 dp, font scale 100/125/150%, TalkBack и клавиатуры для изменённого UI.

Release считается готовым только при зелёных автоматических проверках, physical smoke и подтверждённом upgrade поверх предыдущего APK.
