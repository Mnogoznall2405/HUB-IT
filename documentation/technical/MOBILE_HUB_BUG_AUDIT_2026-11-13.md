# Аудит мобильного приложения mobile-hub: найденные дефекты

Дата: 13.11.2026  
Объект: `mobile-hub/` (Expo/React Native, версия 1.1.81)  
Режим: read-only, код и контракты не изменялись.

## 1. Итог

Проверен код мобильного клиента и его контракты с backend в части авторизации, offline-кэша, чата/realtime, почты, задач, ленты, настроек и инвентаря. Найдено **14 функциональных дефектов** (6 высоких, 8 средних) и 7 пограничных замечаний.

Самые важные:

1. **Офлайн-подготовка почты и задач не работает по назначению** — подготовка пишет снимок под одним ключом, а экраны читают под другим (разный `limit`). UI при этом сообщает «сохранено».
2. **Выход из аккаунта не гарантирован** — локальные токены и данные стираются только после трёх сетевых вызовов (до 90 с); при убийстве процесса сессия восстанавливается.
3. **На общем устройстве вход по отпечатку может открыть аккаунт предыдущего пользователя** — 2FA-вход другого пользователя не отзывает старый биометрический credential.

## 2. Метод и ограничения

- Анализ статический: чтение кода, сверка mobile ↔ backend (`WEB-itinvent/backend`).
- Приложение не запускалось, APK не собирался, устройство/эмулятор не использовались, тесты не выполнялись.
- Поэтому все пункты имеют статус «подтверждено кодом», но не «воспроизведено на устройстве». Для пунктов, зависящих от поведения стека/freeze, это указано отдельно.
- Production, БД, `.env`, IIS/PM2 не затрагивались.

## 4. Высокий приоритет

### MB-01. Офлайн-подготовка почты и задач пишет снимки под другим ключом

**Где:**
- `mobile-hub/src/offline/nativeOfflinePreparation.ts:51,55,271,275,403,419`
- `mobile-hub/src/screens/tasks/NativeTasksInboxScreen.tsx:47,244,247`
- `mobile-hub/src/mail/useMailList.ts:32,140,143`
- `mobile-hub/src/cache/nativeSnapshotCache.ts:411-454`

**Причина.** Ключ коллекции — это `JSON.stringify` фильтров вместе с `limit`. Подготовка использует `limit: 200`, экраны — `limit: 40` (задачи) и `50` (почта). Остальные поля совпадают, поэтому ключи не равны. `readNativeCollectionSnapshot` ищет только точный ключ и fallback не делает.

```ts
// nativeOfflinePreparation.ts
const TASK_PAGE_SIZE = 200;
const MAIL_PAGE_SIZE = 200;
const signature = JSON.stringify({ ...request, offset: 0 });
```

```ts
// NativeTasksInboxScreen.tsx
const PAGE_SIZE = 40;
const signature = JSON.stringify({ ...request, offset: 0 });
```

**Сценарий.** Настройки → Приложение → «Подготовить автономный режим» → дождаться «Почта/Задачи сохранены» → отключить сеть → открыть «Почту» или «Задачи». Экран показывает «Нет подключения и сохранённых данных», хотя подготовка отчиталась об успехе.

**Влияние.** Ключевая офлайн-функция не работает; пользователь уверен, что данные есть. Для почты и задач это основной сценарий использования без сети.

**Исправление.** Один общий источник `PAGE_SIZE` для подготовки и экрана; не включать `limit` в ключ (хранить его отдельно) либо читать снимок по «фильтрам без пагинации». Добавить тест полного цикла: подготовка → offline → экран.

### MB-02. Logout ждёт три сетевых вызова до локального стирания

**Где:** `mobile-hub/src/auth/logout.ts:49-68,81-84`, `mobile-hub/src/auth/AuthContext.tsx:741-756`, `mobile-hub/src/screens/menu/NativeMenuScreen.tsx:167-169`.

**Причина.** `endMobileSession` последовательно и с обычным таймаутом 30 с вызывает `revokeNativePushToken`, `revokeMobileBiometricSession` и `authApi.logout`. Только после этого в `finally` очищаются токены, биометрия и офлайн-кэш. `AuthContext.logout` выставляет `user = null` после завершения, а меню переходит на логин в `.finally`.

**Сценарий.** Пользователь нажимает «Выйти» в сети с captive portal/зависшим аплинком. Запросы висят до 30 с каждый (до 90 с суммарно). Пользователь закрывает приложение. Токены и кэш не удалены; следующий холодный старт восстанавливает сессию.

**Влияние.** «Выход», который не состоялся. На общем устройстве или при увольнении это доступ к почте, чату и офлайн-данным.

**Исправление.** Сначала локальное стирание (или параллельно с сетевыми вызовами), ограниченный общий таймаут, durable-маркер «logout начат» по образцу `hubit_credentials_revoked`. Серверные вызовы — best-effort после локальной очистки.

### MB-03. 2FA-вход другого пользователя сохраняет чужой биометрический credential

**Где:** `mobile-hub/src/auth/AuthContext.tsx:545-589` против `:602-637`; `mobile-hub/src/auth/biometricAuth.ts:112-119`.

**Причина.** В `login()` есть проверка владельца отпечатка: если `enrolledBiometricUserId !== signedInUserId`, вызывается `disableBiometricLogin()`. В `verifyTwoFactor` и `verifyTwoFactorSetup` этой проверки нет: `persistLoginResult` сохраняет токены нового пользователя, а `biometricEnabled` и credential старого остаются.

**Сценарий.** Общий планшет. Пользователь A включил вход по отпечатку. Сессия A истекла (credential по дизайну сохраняется). Пользователь B входит логином/паролем + TOTP. Сессия B истекает. На экране входа остаётся кнопка «Войти по отпечатку»; отпечаток A возвращает токены A и открывает кэш A.

**Влияние.** Смена аккаунта без пароля и доступ к данным предыдущего пользователя. Требует общего устройства, но это реальный корпоративный сценарий.

**Исправление.** Вынести проверку владельца в общий `persistLoginResult`/`finalizeLogin`, применять её и в 2FA-ветках. Дополнительно при старте сравнивать `getBiometricLoginUserId()` с `sessionUserId` и отключать биометрию при несовпадении.

### MB-04. Редактирование задачи меняет срок на 18:00 и может сдвинуть дату

**Где:** `mobile-hub/src/screens/tasks/NativeTaskDetailScreen.tsx:103-105,478,554-557,574-577`; `mobile-hub/src/tasks/taskFormat.ts:66-83`.

**Причина.** В форме редактирования только дата. `taskDueDateInput` берёт первые 10 символов ISO-строки, а `normalizeDueDate` всегда возвращает `${date}T18:00:00`. `saveEdit` всегда отправляет `due_at`, даже если дата не менялась.

**Сценарий.** Задача создана в web со сроком `2026-11-20T10:00`. На мобильном пользователь меняет только название и сохраняет — срок становится `2026-11-20T18:00:00`. Если сервер вернул момент с `Z`, `slice(0, 10)` может взять UTC-дату, и задача переедет на другой день.

**Влияние.** Незаметное изменение официального срока, неверные напоминания и статус «просрочено». Web сохраняет исходное время.

**Исправление.** Если дата не изменилась, отправлять исходный `due_at`; добавить поле времени или не трогать время при редактировании. Дату парсить в локальной зоне, а не `slice` от ISO.

### MB-05. Тред теряет подписку на комнату после ухода с вкладки «Чат»

**Где:** `mobile-hub/src/screens/chat/useThreadRealtime.ts:113,282`; `mobile-hub/src/lifecycle/AppLifecycle.tsx:252-259`; `mobile-hub/src/chat/chatSocket.ts:371-392,295-296`.

**Причина.** При уходе с вкладки «Чат» `AppLifecycle` вызывает `chatSocket.disconnect({ clearSubscriptions: true })`, который очищает `conversationIds`. Экран треда остаётся смонтированным, его effect не перезапускается (зависимости не меняются). При возврате `connect()` переподписывает только то, что осталось в множестве. У инбокса есть повторная подписка на `status === connected`, у треда — нет.

**Сценарий.** Открыть диалог → перейти на «Задачи» → вернуться в «Чат» на тот же экран. Новые сообщения могут не приходить, реакции/прочтения/онлайн «замирают». При прямом deep-link в тред (без инбокса под ним) сообщения не приходят совсем до переоткрытия.

**Влияние.** Тихая деградация чата, расхождение непрочитанных.

**Исправление.** В `useThreadRealtime` на переходе в `connected` повторять `subscribeConversation(conversationId)` (как в `useInboxData`), либо не очищать подписки треда при смене вкладки. Проверить на устройстве возврат из фона и из другой вкладки.

### MB-06. `hubRealtimeSocket` залипает при зависшем рукопожатии

**Где:** `mobile-hub/src/realtime/hubRealtimeSocket.ts:251-305,362-377`.

**Причина.** `connect()` выходит, если `this.socket` существует и не `CLOSED`. На `onerror` сокет не закрывается и не обнуляется, watchdog рукопожатия отсутствует; heartbeat стартует только в `onopen`. В чат-сокете такой watchdog и `abandonSocket` есть.

```ts
socket.onerror = () => {
  if (this.socket === socket) this.emitStatus('error');
};
```

**Сценарий.** «Чёрная дыра» в сети, captive portal или зависший TLS при старте: `onopen`/`onclose` не приходят. Любой повторный `connect()` игнорируется.

**Влияние.** Realtime задач, почты, 1С и бейджа уведомлений мёртв до перезапуска приложения; чат при этом может работать и маскировать проблему.

**Исправление.** Таймаут рукопожатия (10–15 с) с принудительным `close/abandon`, сброс `this.socket` в `onerror`, повторный `connect` по таймауту. Тест с «зависшим» WebSocket.

## 5. Средний приоритет

### MB-07. Код 4403 навсегда выключает hub-realtime

**Где:** `mobile-hub/src/realtime/hubRealtimeSocket.ts:27,369-371,397-402`.

4403 входит в `NON_RECONNECTABLE_CLOSE_CODES`, `onclose` ставит `reconnectEnabled = false`, а `resume()` подключается только при `reconnectEnabled`. Временный 403 (IP-allowlist, смена сети) убивает realtime до перезапуска. При этом `client.ts:218-226` декларирует, что 403 — ограничение сети, сессия жива и реконнект продолжается.

**Исправление.** Не считать 4403 фатальным: backoff + повтор на `resume`/смене сети; согласовать с политикой 403.

### MB-08. Собственные read-receipts помечают свои сообщения прочитанными

**Где:** `mobile-hub/src/chat/chatState.ts:233-242`; `mobile-hub/src/screens/chat/useThreadRealtime.ts:177-183`; backend `WEB-itinvent/backend/chat/realtime_publisher.py:496-505`.

Сервер публикует `chat.message.read` всей комнате и кладёт `reader_user_id`. Клиент его не проверяет и применяет дельту ко всем своим сообщениям с индексом ≤ прочитанного.

**Сценарий.** В личном чате A отправил «привет», B ответил «здравствуй». A открывает чат и читает сообщение B. Собственное «привет» получает статус «Прочитано», хотя B его не открывал.

**Исправление.** Игнорировать событие, если `reader_user_id === currentUserId`; обновлять только сообщения, отправленные текущим пользователем, и только по чужому чтению. Для групп — считать `read_by_count` по чужим reader_id, а не копировать счётчик прочитанного сообщения.

### MB-09. Перекрытый экран треда помечает входящие прочитанными

**Где:** `mobile-hub/src/screens/chat/NativeChatThreadScreen.tsx:490-504`; `mobile-hub/src/screens/chat/useThreadRealtime.ts:150-153`; focus-эффект `NativeChatThreadScreen.tsx:529-537`.

`markRead` проверяет только `AppState === 'active'`, но не то, что тред активен. `useFocusEffect` уже ведёт `getActiveNativeChatConversationId()`, но `markRead` его не использует. Перекрытый тред остаётся смонтированным и подписанным; новое сообщение в нём помечается прочитанным.

**Сценарий.** Открыт чат A → приходит push по чату B → B открывается поверх A → новое сообщение в A помечается прочитанным, хотя пользователь его не видел.

**Влияние.** Пропадают непрочитанные, бейдж и папка расходятся; собеседник видит «Прочитано».

**Исправление.** В `markRead`/`applyMessage` проверять `getActiveNativeChatConversationId() === conversationId`. Проверить на устройстве с `freezeOnBlur`.

### MB-10. Быстрый ответ из push теряется при 4xx

**Где:** `mobile-hub/src/notifications/notificationBackgroundTask.ts:163-172`; `mobile-hub/src/notifications/notificationActionFeedback.ts:124-126`.

В очередь ответ попадает только при `isRetryableOfflineError`. На 400/403 (slow mode, закрытая отправка, нет `chat.write`) вызывается `showReplyFailed`, а текст нигде не сохраняется; исходное push-уведомление уже заменено.

**Влияние.** Пользователь теряет набранный ответ, кнопки «Повторить» нет.

**Исправление.** Сохранять текст в pending-replies при любой ошибке (или открывать экран ответа с текстом), различать «нет сети» и «сервер отклонил», давать повтор.

### MB-11. Входящий share задачи перезаписывается старым черновиком

**Где:** `mobile-hub/src/screens/tasks/NativeTaskCreateScreen.tsx:142,148-161`; `mobile-hub/src/drafts/useNativeFormDraft.ts:21-35`.

Share применяется на монтировании. Черновик восстанавливается позже, когда `loadingRefs` становится `false`, и безусловно вызывает `restore(saved)`, заменяя заголовок, описание и файлы.

**Сценарий.** У пользователя есть незавершённый черновик создания задачи. Он делится текстом/файлом в HUB-IT; после загрузки справочников старый черновик затирает переданные данные.

**Исправление.** Применять share после восстановления черновика и с приоритетом над ним; либо очищать черновик при incoming share. Тест: черновик + share.

### MB-12. Локальный черновик ответа переживает сохранение и перезаписывает серверный

**Где:** `mobile-hub/src/screens/mail/NativeMailComposeScreen.tsx:331-354,401,543-546,661-669`.

После успешного автосохранения обновляется только `lastSavedFingerprintRef`, локальная сессия не очищается. При закрытии без несохранённых изменений `attemptClose` просто уходит назад. При повторном открытии ответа `restoreLocal` выполняется после `initializeFromSource` и подставляет старый локальный текст; автосохранение может записать его в тот же серверный `draftId`.

**Влияние.** Тихая потеря правок черновика, сделанных на другом устройстве.

**Исправление.** Очищать локальную сессию после подтверждённого серверного сохранения; при наличии серверного черновика не восстанавливать локальный без сравнения ревизии/времени.

### MB-13. Backend молча вырезает `absences` и `/monitoring`

**Где:** `mobile-hub/src/preferences/preferenceNormalizers.ts:3-26`; `WEB-itinvent/backend/services/settings_service.py:25-51,137-141,170-177`; `mobile-hub/src/dashboard/DashboardScreen.tsx:318`.

- `dashboard_sections`: мобильный клиент разрешает `absences`, backend `DASHBOARD_SECTION_KEYS = ("attention","tasks","communication","news")` — секция отбрасывается. При ответе PATCH `refreshPreferences` перезаписывает локальный кэш, и блок «Отсутствуют сегодня» исчезает.
- `mobile_bottom_nav_items`: мобильный клиент предлагает `/monitoring`, в `MOBILE_BOTTOM_NAV_ITEM_PATHS` его нет — пункт не сохраняется, меню откатывается к дефолту.

**Влияние.** Настройки выглядят сохранёнными, но не применяются; мобильная фича фактически отключена контрактом.

**Исправление.** Либо добавить ключи на backend (с миграцией/совместимостью), либо убрать их из мобильного UI. Добавить контрактный тест mobile ↔ `/settings/me`.

### MB-14. Лента и инвентарь не обновляются при возврате

**Где:** `mobile-hub/src/screens/feed/NativeFeedInboxScreen.tsx:271-273,374-383`; `mobile-hub/src/screens/feed/NativeFeedPostScreen.tsx:420-430`; `mobile-hub/src/screens/database/NativeEquipmentDetailScreen.tsx:623-632`; `mobile-hub/src/screens/database/NativeDatabaseScreen.tsx:571-580`.

Нет `useFocusEffect`/realtime-инвалидации. После редактирования карточки оборудования список показывает старые статус/расположение, а офлайн-снимок карточки не обновляется. В ленте после чтения/реакции/закладки и возврата остаются старые счётчики, а созданная публикация не появляется.

**Исправление.** Обновлять список/снимок при возврате (focus) или точечно патчить кэш после мутации. Для ленты — обновлять активный фильтр после действий.
