## 1. Зафиксированные решения

- EAS Build, Expo Push Service и `EXPO_TOKEN` не используются.
- APK собирается локально через `npm run build:apk:local` и публикуется штатным `scripts/mobile/publish-apk.ps1` в `/desktop-updates/mobile/preview/`.
- Уведомления отправляются backend HUB-IT напрямую через Firebase Cloud Messaging HTTP v1.
- Основной бизнес-интерфейс остаётся общим с адаптивной web-версией, а Android-оболочка предоставляет нативные функции, безопасность, системные интеграции и offline lifecycle.
- PWA и браузер не должны получать APK-only поведение и не должны ломаться при развитии Android-клиента.

## 2. Разрешённый рабочий контур

В рамках реализации этого плана разрешено:

- локально собирать новые APK с обязательным увеличением `version` и `versionCode`;
- публиковать прошедший проверки APK в существующий внутренний mobile feed с backup текущего manifest, SHA-256 и post-check скачивания;
- использовать существующие выделенные тестовые учётные записи;
- создавать отдельные тестовые учётные записи, если сценарий нельзя безопасно проверить существующей учёткой;
- выполнять login, 2FA, logout, biometric opt-in, Chat, почту, задачи, уведомления и остальные пользовательские сценарии тестовой учёткой;
- деактивировать созданные тестовые учётки после приёмки, сохраняя связанные PK и историю согласно правилам проекта;
- выполнять локальные сборки, тесты и device-smoke на подключённом Android.

Ограничения:

- не использовать реальные пользовательские пароли, переписку и документы в тестах;
- не хранить тестовые пароли, TOTP secrets, cookies, Firebase private keys и signing keys в Git, плане, логах или APK feed;
- production `.env`, PM2/IIS, база данных и backend меняются или перезапускаются только после отдельного preflight, rollback-плана и post-check;
- публикация APK не считается успешной установкой или пользовательской приёмкой до проверки на физическом устройстве.

## 3. FCM: два разных файла

### 3.1. Клиентский `google-services.json`

Назначение: связать конкретный Android APK с Firebase-проектом и дать Firebase SDK параметры для получения нативного FCM registration token.

Требования:

- Android-приложение в Firebase регистрируется с точным package name `ru.zsgp.hubit.mobile`;
- файл скачивается из Firebase Console для этого Android-приложения;
- перед каждой чистой локальной сборкой путь передаётся только через `EXPO_GOOGLE_SERVICES_FILE`;
- `app.config.ts` передаёт путь в `android.googleServicesFile`, а `expo prebuild` размещает конфигурацию в генерируемом Android-проекте;
- файл не хранится в репозитории; после сборки исходный файл остаётся в защищённом локальном каталоге;
- изменение Firebase-проекта или client config требует новой сборки APK.

Пример безопасного запуска без вывода содержимого файла:

```powershell
$env:EXPO_GOOGLE_SERVICES_FILE = 'C:\ProgramData\HUB-IT\Secrets\Firebase\google-services.json'
npm run build:apk:local
```

`google-services.json` содержит клиентские идентификаторы и сам по себе не разрешает backend отправлять push. Его нельзя заменять service-account JSON.

### 3.2. Серверный service-account JSON

Назначение: дать доверенному backend HUB-IT право получать короткоживущий OAuth 2.0 access token и вызывать FCM HTTP v1 `messages:send`.

Требования:

- использовать отдельный service account того же Firebase/Google Cloud проекта;
- выдать только необходимую роль Firebase Cloud Messaging API Admin (`roles/firebasecloudmessaging.admin`);
- включить Firebase Cloud Messaging API (HTTP v1) в проекте;
- ключ хранить только на сервере в защищённом каталоге с доступом для учётной записи backend;
- private key никогда не помещать в APK, Git, mobile feed, frontend, логи или сообщения;
- для HUB-IT использовать путь через `FCM_SERVICE_ACCOUNT_FILE`, а не многострочный `FCM_SERVICE_ACCOUNT_JSON`;
- `FCM_PROJECT_ID` должен совпадать с `project_id` client config и service-account файла;
- предусмотреть отзыв и ротацию ключа; старый ключ удалять только после проверки нового.

Целевая production-конфигурация хранит только ссылки, а не содержимое секрета:

```dotenv
FCM_PROJECT_ID=<firebase-project-id>
FCM_SERVICE_ACCOUNT_FILE=C:\ProgramData\HUB-IT\Secrets\Firebase\hubit-fcm-service-account.json
FCM_SERVICE_ACCOUNT_JSON=
```

## 4. Как проходит уведомление

1. После входа приложение проверяет Android permission на уведомления.
2. После согласия создаёт notification channel и вызывает `getDevicePushTokenAsync()`.
3. Android/Firebase возвращает нативный FCM registration token конкретной установки.
4. APK по авторизованному API регистрирует token и стабильный `device_id` в HUB-IT.
5. Backend сохраняет активную регистрацию в `app.native_push_tokens`.
6. Chat, задачи, почта или системное событие ставит доставку после успешной бизнес-транзакции.
7. Backend получает OAuth access token из server service account и вызывает FCM HTTP v1.
8. Android показывает уведомление в фоне; нажатие открывает безопасный внутренний маршрут HUB-IT.
9. При ротации FCM token приложение регистрирует новый и отзывает старый. При logout регистрация текущего устройства отзывается.

#### Реализованный offline-контур версии 1.1.4

Offline не является полной локальной копией сервера. Это защищённый режим чтения последнего успешно загруженного состояния:

1. Пользователь один раз проходит обычный вход и 2FA, затем добровольно включает вход по отпечатку.
2. APK хранит снимок пользователя и случайный 256-битный ключ в Android SecureStore с обязательной биометрической проверкой.
3. При работе онлайн web-клиент шифрует этим ключом разрешённые GET-ответы и сохраняет их в IndexedDB с TTL, лимитом размера и числом записей.
4. Service Worker заранее сохраняет `/index.html` и текущие JS/CSS assets. APK при offline cold start открывает именно каноническую оболочку `/index.html`, а не некэшируемый SPA-маршрут вроде `/mail`.
5. До запуска React bridge безопасно восстанавливает разрешённый requested path через `history.replaceState`, после чего API-клиент читает только расшифрованные данные текущего пользователя.
6. Все POST/PUT/PATCH/DELETE в offline-сессии блокируются. Отправка письма, сообщения и переходы задач не имитируют успех и не ставятся в скрытую очередь.
7. При возврате сети WebView передаёт APK безопасный текущий маршрут. APK повторно создаёт серверную web-сессию, открывает тот же маршрут, а интерфейс ненавязчиво показывает зелёное подтверждение и автоматически скрывает его.
8. Серверный `401/403` отзывает локальный biometric credential; сетевой сбой сам по себе пользователя не разлогинивает.

Обязательные условия: биометрия должна быть включена после 2FA, приложение должно хотя бы один раз успешно открыть портал онлайн, а нужная страница и её данные должны быть предварительно загружены. Незагруженные данные без сети недоступны — интерфейс обязан показывать cache miss/stale, а не пустой экран.

## 8. Качество и тестовые учётки

Для каждого release candidate:

1. Увеличить `version` и `versionCode`, сформировать краткий changelog.
2. Выполнить TypeScript, mobile Jest, Expo dependency check, Expo Doctor и релевантные backend/frontend тесты.
3. Собрать APK локально с защищённым Firebase client config и постоянной подписью.
4. Проверить package, SDK, version, signing certificate, размер и SHA-256 через Android build tools.
5. Установить как clean install и upgrade на физический Android 13+.
6. Тестовой учёткой пройти login → 2FA → biometric opt-in → Chat → почта → задачи → offline → logout.
7. Проверить клавиатуру во всех текстовых полях, системные панели, поворот/resize, back navigation, загрузку и открытие файлов.
8. Пройти FCM-матрицу на двух устройствах в foreground/background/killed state.
9. Проверить, что PWA и обычный браузер сохранили прежнее поведение.
10. Только после зелёной приёмки сделать backup feed manifest, опубликовать APK и выполнить внешний HTTPS/hash post-check.

Тестовая учётка должна иметь минимально достаточные права. Для проверки разных ролей создавать отдельные аккаунты: обычный пользователь, руководитель/исполнитель задач и администратор только когда административный сценарий входит в текущую приёмку.

## 9. Критерии стабильного продукта

- [ ] 20 последовательных cold start без crash/blank screen.
- [ ] 20 циклов background/foreground без потери сессии и двойной навигации.
- [ ] 50 тестовых уведомлений каждого основного типа без потерь, дублей и неверных deep links при исправной сети.
- [ ] Корректная работа двух устройств, ротации token и logout одного устройства.
- [ ] Нет перекрытых клавиатурой полей на Chat, почте, задачах и настройках.
- [ ] Offline cache недоступен другому пользователю и очищается по policy/logout.
- [ ] Upgrade сохраняет настройки, сессию и кэш; rollback-путь документирован.
- [ ] APK подписан постоянным release key, hash и manifest feed совпадают с внешне скачанным файлом.
- [x] Backend/frontend/PWA regression зелёный в затронутых областях; физическая web/device приёмка остаётся отдельной.
- [ ] Физическая приёмка зафиксирована отдельно от факта сборки и публикации.
