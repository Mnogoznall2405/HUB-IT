# HUB-IT Mobile — план нативного интерфейса Chat

| Поле | Значение |
|---|---|
| Статус | Preview 1.1.8 собран и прошёл preflight; публикация заблокирована внешним подтверждением, device acceptance ожидается |
| Дата | 2026-08-23 |
| Область | Android-приложение `mobile-hub` |
| Владелец | HUB-IT product / engineering |

## Краткое решение

Перевести маршруты `/chat` и `/chat/:conversationId` в APK на нативный React Native UI. Существующие Chat API, WebSocket, авторизация и серверная бизнес-логика остаются общими для web, Desktop и mobile.

Это осознанное исключение из прежней границы «бизнес-разделы открываются в WebView»: **только Chat становится нативным**, остальные разделы пока продолжают работать через responsive web. Старые архитектурные документы нужно синхронизировать в первой фазе реализации.

Nekogram используется только как референс UX: композиция диалога, группировка сообщений, жесты, контекстные действия и характер плавности. Код, графические ресурсы, брендинг и другие материалы Nekogram не копируются.

Актуальный разрыв с web и обязательные жесты/папки: [MOBILE_HUB_NATIVE_CHAT_GAP_ROADMAP.md](./MOBILE_HUB_NATIVE_CHAT_GAP_ROADMAP.md).

## Текущее состояние реализации

Нативный MVP реализован 2026-08-23:

- добавлены нативные inbox и thread с loading/error/offline-состояниями;
- backend DTO нормализуются в одном mobile-слое (`body`/`sender` → модель интерфейса);
- подключены cursor-пагинация inbox/thread, focused deep link, realtime merge/dedup и optimistic send;
- реализованы reply/edit/delete/reactions/forward, поиск по диалогу, фото/файлы и системное открытие вложений;
- добавлены группировка, даты/unread-разделитель, кнопка новых сообщений, swipe-to-reply и черновики по диалогу;
- исправлен нижний anchor инвертированного списка: собственные и realtime-сообщения остаются над композером после отправки, изменения его высоты и открытия клавиатуры;
- интерфейс приведён к Telegram/Nekogram-паттернам без копирования кода или assets: семантическая светлая/тёмная тема, вложения внутри поля и компактные сообщения;
- постоянное троеточие у сообщений убрано: меню открывается нажатием/удержанием, свайп вправо отвечает, свайп влево пересылает;
- добавлены mute/settings, read receipts, presence, локальное закрепление сообщения, задачи, стикеры, emoji, упоминания, карточки AI-действий и управление группой/участниками;
- стабилизированы обработчики `FlatList` при вводе, финальная newer-страница двигает read cursor, а поиск явно сообщает об отсутствии результатов;
- TalkBack получает автора, время, состояние доставки сообщения и семантический прогресс upload/download;
- все жесты имеют видимую альтернативу, touch targets не меньше 44 dp, поддержан Android reduced motion;
- навигация из портала и push переводит Chat в native по умолчанию;
- `EXPO_PUBLIC_NATIVE_CHAT_ENABLED=false` остаётся быстрым rollback на web route;
- web fallback доступен с обоих нативных экранов;
- полный mobile Jest regression (67 suites, 225 тестов) и lint пройдены; Expo dependency check и Expo Doctor в этом прогоне заблокированы правами sandbox на пользовательские cache-каталоги;
- dual-ABI preview APK 1.1.8 (`versionCode=10`) собран и прошёл локальный аудит/preflight; публикация не выполнена из-за отклонённого внешнего разрешения на запись в IIS;
- физическая Android-приёмка и performance baseline ещё не выполнены.

## Зачем это делаем

Текущий переход в web-чат обеспечивает функциональную совместимость, но ограничивает качество мобильного взаимодействия: управление клавиатурой, жесты над сообщением, сохранение позиции списка, системный выбор файлов и согласованную работу при смене состояния приложения.

Нативный Chat должен:

- ощущаться частью Android-приложения, а не встроенной страницей;
- сохранить функциональные контракты существующего HUB-IT Chat;
- стабильно работать с длинными ветками и realtime-событиями;
- внедряться поэтапно, без обязательной переделки backend;
- иметь безопасный возврат на текущий web-чат.

## Цели

- Нативные список диалогов, экран переписки, композер и действия над сообщениями.
- Плавная прокрутка и короткие прерываемые анимации без визуального шума.
- Realtime с переподключением, дедупликацией, сохранением порядка и корректным unread-состоянием.
- Текст, ответы, реакции, редактирование, удаление, пересылка, фото и файлы.
- Корректные push/deep link, foreground/background и восстановление сессии.
- Измеримое сравнение производительности с текущим WebView на одном устройстве и наборе данных.

## Не входит в первую версию

- Перевод остальных бизнес-разделов APK на native.
- Новый backend, отдельная база, Redis или брокер сообщений.
- Копирование интерфейса Nekogram/Telegram один в один.
- Полная замена web-чата: браузер и Desktop продолжают использовать существующий React UI.
- iOS-релиз.
- Тёмная тема, если к старту реализации приложение всё ещё официально поддерживает только светлую.
- Новая библиотека анимаций или виртуализации до измерения базовой реализации на `FlatList`.

## Принципы UX/UI

1. **Telegram-подобная поверхность, HUB-IT по сути.** Продуктовое решение 2026-08-23: нативный Chat использует собственную палитру `mobile-hub/src/theme/chatTokens.ts`, близкую к Telegram, чтобы экран ощущался привычным мессенджером. Это исключение только для Chat: остальные разделы остаются на теме HUB-IT. Сущности, права, терминология и данные — HUB-IT без изменений. Код, графические ресурсы и брендинг Telegram/Nekogram по-прежнему не копируются.
2. **Контент важнее декора.** Сообщение, автор, статус и время читаются раньше вторичных действий.
3. **Действие подтверждается сразу.** Нажатие, отправка, реакция и начало загрузки получают мгновенный визуальный отклик.
4. **Анимация не блокирует управление.** Переход можно прервать новым жестом или навигацией.
5. **Жесты имеют альтернативу.** Reply по свайпу также доступен из меню; реакции и удаление не зависят только от жеста.
6. **Длинная история не меняет поведение экрана.** Загрузка старых сообщений не должна сдвигать текущую позицию.
7. **Состояние соединения видно, но не мешает.** При offline/reconnect пользователь читает уже загруженное и понимает судьбу отправки.

## Пользовательские сценарии

- Пользователь видит актуальные диалоги, unread-счётчики и последнее сообщение.
- Пользователь открывает диалог и сразу попадает к последней непрочитанной или целевой записи.
- Пользователь отправляет сообщение и видит состояния `отправляется → отправлено → ошибка`.
- Пользователь отвечает свайпом или через контекстное меню.
- Пользователь добавляет реакцию, редактирует, удаляет и пересылает сообщение в пределах своих прав.
- Пользователь отправляет фото или файл, видит прогресс и может повторить неудачную загрузку.
- После потери сети события догружаются без дублей и нарушения порядка.
- Нажатие на push открывает нужный диалог или конкретное сообщение.
- После возврата из background сохраняются черновик и разумная позиция чтения.

## Функциональный объём

### MVP

**Список диалогов**

- аватар, название, последнее сообщение, время, unread и mute-состояние;
- состояния loading, empty, error и offline;
- pull-to-refresh и постраничная загрузка;
- переход в личный и групповой чат;
- создание нового личного диалога из существующего каталога пользователей.

**Экран переписки**

- начальная загрузка, догрузка старых сообщений и переход к целевому сообщению;
- группировка соседних сообщений одного автора;
- разделители дат и непрочитанных сообщений;
- текст, системные сообщения, изображения и файлы;
- reply-preview и переход к цитируемому сообщению;
- индикатор новых сообщений и кнопка возврата вниз;
- realtime-вставка, изменение и удаление без полного refetch;
- optimistic send, retry и защита от дубликатов.

**Композер и действия**

- многострочный ввод, отправка и сохранение черновика на диалог;
- reply, edit и cancel для активного режима композера;
- выбор фото/файла, прогресс загрузки и ошибка;
- long press с доступными по правам действиями;
- реакции и удаление/редактирование своих сообщений;
- свайп к reply с однократной haptic-отдачей на пороге срабатывания.

**Интеграция приложения**

- системная кнопка Back и предсказуемое закрытие клавиатуры;
- push/deep link в диалог;
- suspend/resume существующего WebSocket при смене lifecycle;
- повторная авторизация через общий mobile auth flow;
- контролируемый переход в web-чат при аварийном отключении native-функции.

### После MVP

- глобальный поиск по сообщениям с переходом в контекст;
- множественный выбор и пакетные действия;
- голосовые сообщения после подключения совместимого нативного audio-модуля и возврата разрешения `RECORD_AUDIO`;
- быстрые реакции по double tap с пользовательской настройкой;
- GIF, аватар группы и расширенный media viewer.

## Макет взаимодействия

### Список диалогов

- Верхняя панель: название раздела, поиск и создание диалога.
- Строка диалога: аватар слева, имя и preview в центре, время и unread справа.
- Непрочитанный диалог выделяется весом текста и счётчиком, а не большим цветным фоном.
- Presence не должен визуально конкурировать с unread.

### Переписка

- Верхняя панель: Back, аватар, имя/статус и меню.
- Входящие и исходящие сообщения отличаются положением и спокойным оттенком пузыря.
- Скругления соседних пузырей уменьшаются со стороны группы; одиночные сообщения имеют полный радиус.
- Время, статус доставки и редактирование занимают стабильное место и не вызывают скачков ширины.
- Вложения получают placeholder известного размера до загрузки превью.
- Композер закреплён над клавиатурой и не перекрывает последнее сообщение.

### Жесты и motion-токены

| Событие | Поведение | Ориентир |
|---|---|---|
| Нажатие | `scale: 0.96` и лёгкая смена фона | 100–150 мс |
| Переход между списком и диалогом | `transform` + `opacity`, прерываемый | 150–220 мс |
| Появление локально отправленного сообщения | короткий сдвиг от композера + opacity | 180–250 мс |
| Реакция/смена статуса | локальная анимация только изменившегося элемента | 150–220 мс |
| Закрытие меню/preview | быстрее открытия | до 150 мс |
| Swipe-to-reply | движение следует пальцу, ограниченный offset, возврат пружиной | без React state на каждый кадр |
| Long press | меню после удержания, haptic один раз | около 420 мс |

Правила motion:

- анимировать преимущественно `transform` и `opacity`;
- не использовать `transition: all` и непрерывные декоративные анимации;
- уважать reduced motion: убирать перемещения, оставляя мгновенную смену состояния;
- не анимировать весь список при каждом realtime-событии;
- точные длительности подтвердить на физическом Android, а не только в эмуляторе.

## Техническая архитектура

### Маршруты и слои

```text
app/(main)/chat/index.tsx                 -> NativeChatInboxScreen
app/(main)/chat/[conversationId].tsx      -> NativeChatThreadScreen
src/screens/chat/                         -> композиция экранов
src/components/chat/                      -> переиспользуемые UI-компоненты
src/chat/                                 -> состояние, merge, lifecycle, WebSocket
src/api/chatApi.ts                        -> типизированные Chat API-вызовы
src/notifications/ + src/files/           -> push/deep link и системные файлы
```

- Не переносить серверную бизнес-логику и проверки прав в APK.
- Не заводить второй формат Chat DTO: mobile-типы должны отражать существующий backend-контракт.
- Существующие `chatSocket.ts` и `chatState.ts` развивать, а не создавать параллельный realtime-контур.
- Новую глобальную state-библиотеку не добавлять, пока локальная модель и текущие утилиты покрывают сценарий.
- Backend менять только для подтверждённого отсутствующего контракта.

### API-контракты, которые нужно сверить в фазе 0

- пагинация сообщений: `before_message_id`, `after_message_id`, metadata/cursor ответа;
- `thread-bootstrap` и `hydrate` для открытия deep link без загрузки всей истории;
- edit/delete/reaction/forward и серверные ограничения прав;
- client message id, ACK и соответствие optimistic-записи серверной;
- состояния upload и формат вложений;
- read cursor, unread, mute/settings и presence;
- типы системных, AI- и служебных сообщений;
- WebSocket sequence/order и восстановление пропущенных событий.

Большая часть этих возможностей уже присутствует в backend. Первая задача — открыть их в типизированном mobile API и зафиксировать тестами, а не проектировать дублирующие endpoints.

### Модель списка и состояния

- `FlatList` с устойчивым `keyExtractor`, мемоизированной строкой сообщения и ограниченным окном рендера.
- Старые страницы добавляются с сохранением видимой позиции; никаких скачков после prepend.
- Сообщения хранятся по `message_id`, порядок вычисляется из серверной последовательности/контракта.
- Повторно полученный WebSocket event идемпотентен.
- Временная optimistic-запись связывается с серверной через client message id.
- Read cursor двигается только вперёд.
- Черновик, reply/edit mode и очередь отправки изолированы по `conversation_id`.
- Крупные изображения декодируются/масштабируются вне критического пути прокрутки.
- `removeClippedSubviews` и более агрессивные оптимизации включаются только после проверки сложных пузырей и вложений на устройстве.

Для первого прохода использовать `FlatList`, `Pressable` и штатный `Animated` с native driver там, где он применим. Reanimated/FlashList добавлять только при воспроизводимом узком месте и сравнении до/после.

## Этапы реализации

### Фаза 0 — контракт, baseline и безопасный переключатель

**Работы**

- Зафиксировать WebView baseline на одном физическом Android: открытие ветки, прокрутка, ввод, получение realtime.
- Составить точную parity-матрицу web ↔ native по текущему коду и backend.
- Сверить API/WS-контракты и дополнить mobile-типы.
- Добавить локальный feature flag/route switch с выключенным native-чатом по умолчанию.
- Обновить документы, где Chat всё ещё объявлен только WebView-разделом.

**Готово, когда**

- есть воспроизводимый benchmark и список обязательных функций;
- известны backend-gap'ы, если они действительно есть;
- переключение между native и web не меняет серверные данные.

### Фаза 1 — нативный read path

**Работы**

- Реализовать inbox и thread на существующих компонентах/токенах.
- Подключить начальную загрузку, пагинацию, realtime merge и unread.
- Реализовать anchor/deep link, loading/empty/error/offline.
- Добавить component/integration-тесты списка и восстановления WebSocket.

**Готово, когда**

- пользователь читает личный и групповой чат без web-перехода;
- prepend/reconnect не создают скачков, дублей и нарушения порядка;
- push открывает правильную ветку и целевое сообщение.

### Фаза 2 — отправка, вложения и взаимодействия

**Работы**

- Композер, optimistic send, retry, reply и edit mode.
- Фото/файлы с progress/error/retry.
- Реакции, edit/delete/forward с учётом серверных прав.
- Swipe-to-reply, long press, контекстное меню и motion-токены.
- Клавиатура, Back, черновики и lifecycle.

**Готово, когда**

- два реальных пользователя проходят двусторонний сценарий text/photo/file;
- offline/reconnect не теряет сообщения и явно показывает неотправленные;
- все жестовые операции доступны через видимое меню.

### Фаза 3 — parity, performance и rollout

**Работы**

- Закрыть согласованные parity-gap'ы: поиск, пересылка, mute и другие обязательные функции.
- Сравнить p50/p95/p99 и frame jank с baseline на одинаковом устройстве.
- Проверить accessibility, большие шрифты, reduced motion и медленную сеть.
- Собрать release APK и провести canary на ограниченной группе.
- После приёмки сделать native route основным, сохранив временный web fallback.

**Готово, когда**

- выполнены критерии ниже;
- нет blocker/critical расхождений с согласованной parity-матрицей;
- rollback проверен без изменения backend и данных.

## Метрики успеха

| Область | Критерий |
|---|---|
| Корректность | 0 дублей, потерянных сообщений и нарушений порядка в автоматизированном reconnect/replay-сценарии |
| Открытие кэшированного диалога | p95 ≤ 500 мс на пилотном устройстве |
| Прокрутка | p95 frame time ≤ 16,7 мс и p99 ≤ 33,4 мс в согласованном тестовом сценарии либо не хуже WebView baseline |
| Ввод | p95 реакции интерфейса на ввод не хуже baseline; тяжёлая работа страницы не выполняется на каждый символ |
| Пагинация | 0 визуальных скачков текущего anchor в тестах prepend |
| Realtime | восстановление после 30–60 секунд offline без ручного обновления и без дублей |
| Навигация | 100% тестовых push/deep links открывают нужный диалог/сообщение после cold и warm start |
| Доступность | основные действия доступны без жестов; touch targets не меньше 44×44; проверен font scale 125% |
| Размер APK | дельта измерена; новая крупная зависимость допускается только с подтверждённой пользой |

Если пилотное устройство не удерживает целевые frame time из-за своего класса производительности, до начала оптимизации фиксируется отдельный реалистичный порог; сравнение с WebView остаётся обязательным.

## Проверки

### Автоматические

- unit: merge, ordering, dedup, read cursor, optimistic reconciliation, пагинация;
- component: inbox, bubble, composer, context menu, loading/empty/error/offline;
- integration: API + WebSocket reconnect, duplicate/reorder, background/resume;
- route tests: `/chat`, `/chat/:id`, push/deep link и fallback;
- mobile quality gates: lint, tests, `expo install --check`, `expo-doctor`, Android build;
- backend Chat regression gate — только если менялся backend-контракт.

### Физический Android

- две учётные записи и два устройства: text, reply, edit, reaction, delete, forward;
- фото и файл: выбор, progress, отмена/ошибка, retry, открытие;
- Wi-Fi ↔ mobile network, airplane mode, 30–60 секунд offline;
- foreground/background, cold/warm push, истёкшая сессия;
- клавиатура, Back, длинный текст, emoji, системный font scale 125%;
- ветки примерно на 100, 500 и 2000 сообщений;
- по возможности 60 Hz и 120 Hz устройства.

## Rollout и rollback

1. Feature flag выключен: APK продолжает открывать web-чат.
2. Internal build: native включён только разработчикам/тестовой группе.
3. Canary: ограниченная группа пользователей, сбор ошибок и performance-метрик.
4. Native становится основным после функциональной и физической приёмки.
5. Web fallback удаляется только после стабильного периода и отдельного решения.

Rollback не требует отката backend: route switch снова направляет `/chat` в существующий `/portal?path=/chat`. Production deployment, публикация APK и включение флага выполняются отдельными действиями после явного разрешения.

## Риски и меры

| Риск | Мера |
|---|---|
| Расхождение native и web-функций | единая parity-матрица и серверные контракты как source of truth |
| Дубли и неверный порядок после reconnect | idempotent merge, sequence/client id и replay-тесты |
| Скачки списка при prepend/media load | anchor tests, стабильные размеры placeholder, device-проверка |
| Конфликт свайпа с горизонтальной навигацией | ограниченный gesture area/threshold и тест на реальном устройстве |
| Зависание клавиатуры или потеря черновика | явная lifecycle-модель по conversation id |
| Тяжёлые анимации | transform/opacity, локальные updates, reduced motion, baseline до оптимизации |
| Лицензионный/визуальный клон Nekogram | использовать только поведенческий референс, не переносить код и assets |
| Невозможность быстро откатиться | route feature flag и сохранённый web fallback |

## Открытые продуктовые решения

- Входит ли глобальный поиск в MVP или в следующую фазу? Рекомендация: поиск по текущему диалогу включить в MVP, глобальный — после.
- Нужен ли double tap на быструю реакцию в первой версии? Рекомендация: отложить до настроек, чтобы не вводить скрытое необратимое действие.
- Какие AI-сообщения и подтверждения обязаны поддерживаться native сразу? Нужно зафиксировать по текущим реальным сценариям.
- Нужны ли управление группой и участниками в MVP? Рекомендация: чтение/отправка в существующих группах — да, администрирование — позже.
- Когда отключать web fallback? Рекомендация: только после стабильного canary и подтверждённой физической приёмки.
