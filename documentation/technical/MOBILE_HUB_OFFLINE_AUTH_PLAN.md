## Решения пользователя (2026-09-30)

1. С сохранённой сессией пускать в приложение **всегда и сразу**, даже если сервер недоступен, на любом телефоне — как Telegram. Защита — только необязательный замок приложения (отпечаток), который уже есть (`AppLockGate`).
2. **Сервер при старте не ждать.** Приложение открывается из кэша мгновенно, сессия проверяется в фоне, при недоступности показывается «Подключение…».
3. Решение отменяет прежнее правило среза 4B `MOBILE_HUB_APK_OPTIMIZATION_ROADMAP.md`: «cached identity не раскрывается до успешного biometric unlock».

## Как работает сейчас (проверено руководителем, код не менялся)

Базовая линия: `npx jest src/auth src/network --runInBand` → 12/12 suites, 77/77 tests.

### Старт

`mobile-hub/src/auth/AuthContext.tsx`, эффект старта ~строки 193–265:

- Читаются только `hasSession` (access token), флаг отпечатка и состояние сети. Сохранённый пользователь намеренно не читается (комментарий у строки 202).
- Android сообщает «сети нет» → `user = null`, `sessionRestoreState = 'unavailable'`, `sessionOfflineMode = true` → `app/index.tsx` отправляет на `/(auth)/login` с текстом «Не удалось проверить сохранённый вход…». Войти можно только кнопкой отпечатка, и только если отпечаток включён.
- Сеть «есть», но сервер недоступен (нет VPN, плохая связь, сервер лежит) → `restoreUserWithRetry` ждёт до `SESSION_RESTORE_TIMEOUT_MS = 12_000` мс (срез 4B обещал 5 с), затем тот же экран входа.

### Хранилище

`src/auth/tokenStore.ts`:

- `hubit_access_token` и `hubit_refresh_token`;
- `hubit_session_user_id`;
- `hubit_session_user_cache_v1` — полный `HubUser` с правами. Записывается после каждого успешного `/auth/me`, проверяется `getCachedSessionUser` (id, username, role, permissions);
- стирается при `clearTokens`.

Фоновая синхронизация уже доверяет этому пользователю (`src/lifecycle/mobileBackgroundSync.ts`). Офлайн-снимки (`src/cache/nativeSnapshotCache.ts`) ключом отпечатка не защищены: `offlineCacheKey` из `biometricAuth` снимками не используется.

### Восстановление связи

`AuthContext.tsx` ~строки 277–320:

- Срабатывает только когда `sessionOfflineMode && connectivityKnownOnline`, делает 4 попытки с паузами 0, 2, 5, 15 с и затихает.
- Эффект перезапускается только при изменении `connectivityKnownOnline`. Если Wi-Fi уже был, а потом включился VPN, значение остаётся `true` → повтора нет.
- `AppLifecycle.tsx` при возврате из фона (`AppState 'active'`) переподключает сокеты, но сессию не восстанавливает.

### Истечение сессии

- 401 и 403 на `/auth/me` при старте и восстановлении стирают токены (`AuthContext.tsx` ~241 и ~300).
- 401 и 403 на `/auth/refresh` вызывают `expireSession` (`src/api/client.ts` ~240).
- Транспортные ошибки сессию не стирают — это верно.

### Проверка ответа `/auth/me`

`src/api/authApi.ts:34` `fetchMe` возвращает `data` без проверки формы.

### Сервер

`AUTH_SECURITY_STACK.md`, строка 142:

- мобильная сессия без биометрического credential подчиняется внешнему password idle 30 минут;
- с активным credential — trusted idle 7 дней (`SESSION_IDLE_TIMEOUT_TRUSTED_DAYS`).

## Целевое поведение

1. Есть сохранённая сессия (токены + валидный кэш пользователя с тем же `session_user_id`) → приложение **мгновенно** открывает домашний экран или отложенный deep link с правами из кэша. Сеть не ждём. Режим — офлайн (только чтение), пока сервер не подтвердит сессию.
2. Проверка `/auth/me` идёт в фоне. Успех → свежий пользователь и права, выход из офлайна, сокеты и очереди догоняют (уже есть в `AppLifecycle`).
3. Переподключение не сдаётся:
   - сразу;
   - при любом событии сети, включая смену транспорта или появление VPN;
   - при возврате приложения на экран;
   - по таймеру с нарастающей паузой 2 → 5 → 15 → 30 → 60 с, дальше каждые 60 с, пока приложение на экране.
4. На экран входа — только при **однозначном** отказе HUB-IT (401 от нашего backend на `/auth/me` или `/auth/refresh`). Офлайн-данные при этом сохраняются по действующему правилу `clearTokens({ clearOfflineData: false })`.
5. Замок приложения (`AppLockGate`), если включён, показывается до контента и работает без сети.
6. Нет кэша пользователя (старая установка, первый запуск после обновления) → прежнее поведение с ожиданием сети, но с общим лимитом 5 с и понятным экраном «Нет связи — повторить».

## Шаг A. Приложение (исполнитель)

Файлы:

- `mobile-hub/src/auth/AuthContext.tsx`;
- `mobile-hub/src/api/authApi.ts`;
- `mobile-hub/src/api/client.ts` — только решение об истечении сессии;
- `mobile-hub/src/lifecycle/AppLifecycle.tsx` — только триггер переподключения при возврате из фона, если это не делается внутри `AuthContext`;
- `mobile-hub/app/index.tsx`, `mobile-hub/app/(auth)/login.tsx` — только тексты и состояния старта;
- общий индикатор «Подключение…»: использовать существующий компонент или баннер автономного режима, если он есть (найти через `rg offlineMode` в `src/components`, `src/navigation`); новый — минимальный;
- тесты: `mobile-hub/src/auth/AuthContext.biometric.test.tsx` (или новый `AuthContext.offline.test.tsx`), `src/api/*.test.ts`, `src/network/*.test.ts` при изменении;
- документация: `documentation/technical/AUTH_SECURITY_STACK.md` (раздел «Mobile client», строки 142–147), `documentation/technical/MOBILE_HUB_APK_OPTIMIZATION_ROADMAP.md` (срез 4B — пометка, что правило заменено этим планом).

A1. **Мгновенный старт из кэша.**
- На старте параллельно читать `hasSession`, `getSessionUserId`, `getCachedSessionUser`, флаг отпечатка и состояние сети.
- Если есть access или refresh токен и кэш-пользователь валиден и совпадает с `session_user_id` → сразу `setUser(cached)`, `setLoading(false)`, `sessionOfflineMode = true`, `sessionRestoreState = 'checking'` и запуск фоновой проверки (A2).
- Ни одного сетевого ожидания до первого рендера shell.
- Нет кэша → прежний путь с общим бюджетом 5 с (исправляет О-4).

A2. **Непрерывное переподключение** (исправляет О-1).
- Один контроллер восстановления сессии. Допустимо переиспользовать `src/network/nativeConnectivityRecovery.ts`, если подходит по смыслу; иначе — локальный.
- Попытки: сразу; на **каждое** событие `subscribeNativeConnectivity` с `connected || online` (включая смену `transport`); на `AppState 'active'`; по таймеру 2, 5, 15, 30, 60 с, далее каждые 60 с.
- Таймер останавливается, пока приложение в фоне.
- Одна попытка в полёте. Гонки с `logout`, повторным входом и `authGenerationRef` — как в существующем коде.
- Успех → `setUser(me)`, `markApiOnline()`, кэш пользователя обновляется.
- Если права изменились, экраны получают новые права без перезапуска (уже через `hasPermission`).

A3. **Однозначное истечение** (исправляет О-3).
- Сессию стирать только если ответ получен от HUB-IT: 401 с JSON-телом (`content-type` содержит `application/json`) на `/auth/me` или `/auth/refresh`.
- 403 на `/auth/me` и `/auth/refresh` — проверить в backend (`WEB-itinvent/backend/api/v1/auth.py`, `api/deps.py`), когда он реально отдаётся (например, для деактивированного пользователя):
  - если это однозначный отказ HUB-IT с JSON `detail` — тоже истечение;
  - любой 401 или 403 без JSON (HTML от IIS, прокси или WAF) — транспортная ошибка, сессия сохраняется, переподключение продолжается.
- Результат проверки backend записать в журнал.
- Логику держать в одном месте, например `isDefinitiveAuthRejection(error)`, и использовать в `AuthContext` и `client.ts`.

A4. **Проверка ответа `/auth/me`** (исправляет О-2).
- `fetchMe` валидирует форму: `id` — целое > 0, `username` и `role` — непустые строки, `permissions` — массив.
- Иначе бросает ошибку, которая считается транспортной: сессия не стирается, `markApiOnline` не вызывается, кэш пользователя не перезаписывается.

A5. **Индикатор связи.** Пока `offlineMode` и `sessionRestoreState === 'checking'` — ненавязчивое «Подключение…» в шапке или баннере. Нет сети — «Нет сети». Без модальных окон и без блокировки навигации. Существующие тексты экранов «Автономный режим: доступны только уже загруженные данные» не ломать.

A6. **Отпечаток и замок.**
- Вход без сети больше не требует отпечатка.
- Кнопка «Войти по отпечатку» остаётся на экране входа для случая истёкшей сессии: credential v2 обновляет сессию онлайн.
- `AppLockGate`, если включён, обязан показываться до контента и при мгновенном старте из кэша: проверить, что первый кадр shell не показывает данные до замка.
- Если это невозможно без переделки `AppLockGate` — остановиться и сообщить руководителю.

A7. **Безопасность смены пользователя.**
- Кэш-пользователь используется, только если `id === session_user_id` и есть токены.
- `logout` и 401 — текущие пути (`endMobileSession`, `clearTokens`).
- Если после восстановления `/auth/me` вернул другой `id`, чем кэш (не должно случаться), — очистить сессию как при 401, без показа чужих данных.

A8. **Документация** (исправляет О-6).
- `AUTH_SECURITY_STACK.md`, «Mobile client»: заменить WebView-строки 144–147 фактическим поведением: мгновенный старт из кэша, режим только чтения до подтверждения, истечение только по однозначному 401/403 HUB-IT, idle-правила сервера без изменений.
- `MOBILE_HUB_APK_OPTIMIZATION_ROADMAP.md`, срез 4B: пометить, что правило «cached identity не раскрывается до biometric unlock» заменено решением от 2026-09-30 со ссылкой на этот план.

A9. **Тесты.**
- Холодный старт без сети с кэшем → shell сразу, без вызова `/auth/me` до рендера; `offlineMode === true`.
- Холодный старт, сеть есть, сервер висит → shell сразу; после ответа `/auth/me` `offlineMode === false` и права обновлены.
- Без кэша пользователя и без сети → экран входа не раньше чем через 5 с (или сразу, если Android сообщает offline), с кнопкой «Повторить».
- Переподключение: 4 неудачи, затем событие сети с тем же `connected: true`, но `transport: 'vpn'` → новая попытка и выход из офлайна.
- Переподключение по `AppState 'active'`.
- После исчерпания коротких пауз попытки продолжаются раз в 60 с (fake timers).
- `/auth/me` вернул HTML со статусом 200 → пользователь из кэша остаётся, офлайн сохраняется, кэш не перезаписан.
- `/auth/me` и `/auth/refresh` вернули 403 без JSON → токены не стёрты; 401 с JSON → истечение, экран входа, офлайн-данные сохранены.

### Приёмка шага A

Без сети приложение с сохранённой сессией открывается сразу, без экрана входа. При появлении сервера (включение VPN, возврат из фона, восстановление сети) приложение само выходит из офлайна без перезапуска. На экран входа попадает только при настоящем отказе HUB-IT. Тесты и lint зелёные.

## Шаг B. Серверный срок сессии — решено: без изменений

Решение пользователя от 2026-09-30: **оставить текущую серверную политику доверия**, серверный код не менять.

### Как работает доверие

Проверено руководителем по коду: `WEB-itinvent/backend/services/session_service.py`, `_idle_timeout_delta`, ~строки 326–337.

Срок простоя сессии — 7 дней (`SESSION_IDLE_TIMEOUT_TRUSTED_DAYS` / `_INTERNAL_DAYS`, минимум 7), если выполнено любое из условий:

1. вход из внутренней сети (`AUTH_2FA_INTERNAL_CIDRS`);
2. сессия создана входом по passkey (`trusted_device_id` из WebAuthn, префикс `trusted:` в `auth_security_service.py`) — обычный код 2FA его **не** выставляет;
3. у установки APK есть активная запись `mobile_biometric_credentials` (включён вход по отпечатку).

Иначе — внешний password idle `SESSION_IDLE_TIMEOUT_MINUTES` = 30 минут.

### Сценарий APK, который подтверждён пользователем как целевой

- Пароль → код 2FA → приложение предлагает включить отпечаток (одноразовый код включения, 5 минут).
- **Включил** → установка доверенная, 7 дней простоя. Токены обновляются молча, отпечаток и 2FA не спрашиваются. Исключение — если включён замок приложения, тогда отпечаток спросит замок.
- **Пропустил** → из внешней сети сессия истекает после 30 минут простоя, при следующем онлайне нужны пароль и 2FA. Из офисной сети — 7 дней.

### Следствия для шага A (добавлено к A1–A9)

- **A10.** Без сети вход мгновенный в обоих случаях. Если при восстановлении связи сервер однозначно ответил 401 (истёк 30-минутный простой у установки без отпечатка):
  - экран входа с понятным текстом «Сессия истекла. Войдите снова» — без сообщения об ошибке сети;
  - офлайн-данные сохраняются по действующему правилу;
  - после повторного входа и 2FA штатный экран предложения отпечатка (`biometric-opt-in`) остаётся как есть.

  Тест: кэш-пользователь без отпечатка, фоновая проверка получает 401 с JSON → экран входа с этим текстом, `clearOfflineData` не вызывается.
- Предложение включить отпечаток после 2FA не убирать и не делать менее заметным: именно оно даёт доверие на 7 дней.

## Проверка на Android (после шага A)

1. Авиарежим → холодный старт → сразу главный экран с данными из кэша, «Нет сети».
2. Wi-Fi без VPN (сервер недоступен) → старт мгновенный, «Подключение…»; включить VPN → без перезапуска переход в онлайн, чат и уведомления подключаются.
3. Свернуть на 5 минут без сети, включить сеть, вернуться в приложение → онлайн.
4. Captive-портал (гостевой Wi-Fi) → остаёмся в приложении, офлайн, сессия не сброшена.
5. Выход из аккаунта → экран входа; холодный старт без сети → экран входа, данные прежнего пользователя не показываются.
6. Включённый замок приложения → замок до контента при старте без сети.
7. Сессия, истёкшая на сервере (> 30 мин без отпечатка, внешняя сеть) → при появлении сети — экран входа «Сессия истекла. Войдите снова», офлайн-данные на месте.
8. Отпечаток включён после 2FA → неделю без использования в пределах 7 дней: приложение открывается и подключается без пароля, 2FA и отпечатка (если не включён замок приложения).

## Риски

- **Разблокированный украденный телефон** открывает HUB-IT и офлайн-данные без проверки. Это принятое решение «как Telegram, всегда». Смягчение — рекомендовать включать замок приложения; сервер по-прежнему проверяет каждую онлайн-операцию.
- **Устаревшие права в офлайне.** Права в офлайне — из кэша и могут быть устаревшими до первой проверки. Изменения данных в офлайне уже запрещены (`nativeOfflinePolicy`), сервер проверяет права при каждой онлайн-операции.
- **Нагрузка от переподключения.** Непрерывные попытки раз в 60 с — только пока приложение на экране; в фоне таймер остановлен.
