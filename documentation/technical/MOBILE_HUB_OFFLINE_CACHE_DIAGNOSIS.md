# HUB-IT: отказ чтения защищённого офлайн-кэша

Дата: 2026-09-05. Область: Expo Android `mobile-hub`, APK 1.1.26 (28), x86_64.

**Дефект: строка Base64 передавалась в Android `AESSealedData.fromCombined`, который принимает `Uint8Array`.** Шифрование и запись файла могли завершиться успешно, но чтение этого же файла возвращало `null`. Исправление декодирует Base64 в байты перед нативным вызовом. Ключи, AAD, формат `.aes`, IV/tag и привязка к пользователю не меняются.

## Доказательства и границы проверки

- Пользователь предоставил результат временных диагностических вызовов на неизменённом APK, Android 16 / API 36: строки длиной 20 и 700000 символов записывались с `true`, чтение возвращало `null`. Прямой вызов `fromCombined(base64)` выдавал исключение; `fromCombined(Uint8Array)` с последующей расшифровкой возвращал исходные данные.
- Названия предоставленных пользователем журналов: `baseline-store-test.log`, `crypto-roundtrip-clean.log`, `synthetic-file-test.log`. Их содержимое на этой рабочей машине отдельно не считывалось. Ранние `synthetic-store-test.log` и `exact-store-test.log` с вмешательством в прототипы не используются как доказательство.
- Локально прочитаны JS, Kotlin и C++ реализации установленных зависимостей. В тесте выполняется настоящая JS-обёртка `expo-crypto`; Android-граница моделируется с проверенным контрактом `ByteArray` → `Uint8Array`. Файлы настоящие, AES-256-GCM выполняет Node crypto, данные синтетические. Это не запуск Android/Hermes.
- Повторный прогон с исходным `nativeSnapshotStorage.ts` из HEAD дал 3 падения: чтение после записи, сохранение частей адресной книги, подготовка данных для чтения после перезапуска. Журнал: `artifacts/offline-cache-diagnosis/baseline.log`. После сравнения рабочий патч восстановлен.
- Исправленный APK в этой задаче не собирался и не запускался. Перезапуск Android-процесса/эмулятора с исправлением и приёмка каждого раздела пока не выполнены.

## Точка отказа

В исходной версии `mobile-hub/src/cache/nativeSnapshotStorage.ts` строки **160** и **173**:

```ts
const sealed = Crypto.AESSealedData.fromCombined(encoded);
```

`encoded` — строка из `File.text()`. Основная и резервная копии имели один и тот же дефект. Сейчас обе используют общий `decryptSnapshotFile`, который вызывает `decodeCombinedBase64` и передаёт результат в `fromCombined` (текущий файл, строка 134).

Подтверждённое пользователем исключение, входной аргумент удалён:

```text
[fromCombined] Cannot convert '[value omitted]' to a Kotlin type.
Value is a string, expected an Object
```

Предоставленный стек APK: `fromCombined (native)` → JS `fromCombined` (`index.android.bundle:1:1280072`) → `?anon_2_readEncryptedNativeSnapshot` (`index.android.bundle:1:2809217`). Это смещения Hermes bundle, не номера строк TypeScript. Код ошибки в предоставленном сообщении не указан.

Исправление не зависит от изменения документации или обновления пакета.

## Вся цепочка

| Этап | Найденное поведение |
|---|---|
| Запрос адресной книги | Экран устанавливает онлайн-данные перед `writeNativeAddressBookSnapshot`; поэтому справочник виден даже при отказе кэша |
| Сериализация | JSON envelope содержит version/userId/savedAt/data; адресная книга делится на части с целевым размером 512 KiB |
| AES | UTF-8 plaintext, AES-GCM, ключ из SecureStore, AAD `hubit-native-snapshot:v2:<user>:<scope>`; encrypt/decrypt строят одинаковый AAD |
| combined/Base64 | Нативный буфер `IV || ciphertext || tag`; стандартные IV 12 байт и tag 16 байт; Android Base64.NO_WRAP |
| `.pending` | Синхронная запись UTF-8 строки, затем асинхронное чтение и сравнение; успешная проверка текста ещё не проверяет входной контракт AES |
| `.aes` | `move(..., { overwrite: true })` поддерживается и возвращает Promise; исходный File меняет URI |
| Повторное чтение | Старый `fromCombined(string)` падает до расшифровки; catch возвращает null и удаляет файлы |
| Части/индекс | Части пишутся до корневого индекса; адресная книга и коллекции сразу перечитывают индекс и части, поэтому сообщают об отказе сохранения |
| Общая готовность | Простые снимки раньше возвращали true сразу после move. Поздний inventory повторно читает их и получает null. Манифест coverage тоже использует тот же дефектный reader |

`Snapshot staging verification failed` и `Empty encrypted snapshot/backup` сами по себе не доказывают этот дефект. По предоставленному результату ранние ошибки контрольного чтения могли быть вызваны перехватчиками. В тестах такие отказы вводятся явно для проверки восстановления и диагностики.

## Минимальный фикс и сопутствующая защита

Основной фикс — настоящее декодирование Base64 → `Uint8Array` перед `fromCombined`. `TextEncoder.encode(base64)` не используется: он дал бы ASCII-байты закодированной строки. Декодер не добавляет зависимостей и работает с прежним форматом `.aes`/`.backup`.

Дополнительно исправлены воспроизведённые тестами ветки в той же цепочке:

- готовая запись подтверждается чтением и расшифровкой `.aes` перед возвратом true;
- читающие и пишущие операции одного файла упорядочены; чтение не попадает в промежуток удаления старого destination и переноса нового;
- очистка использует неизменную ссылку на `.pending`, а ошибка удаления backup после подтверждённой записи не откатывает новую версию;
- после временной ошибки чтения/ключа ciphertext сохраняется для повторного чтения; исправный backup восстанавливается;
- операции адресной книги упорядочены на весь цикл «части → индекс → проверка → очистка», чтобы конкурентное сохранение не удаляло части другой версии;
- `writeNativeSnapshot` ожидает Promise внутри try/catch; раньше return без await пропускал асинхронные исключения мимо catch;
- подготовка и фоновое обновление проверяют boolean записи coverage. Ошибка манифеста больше не даёт успешный статус раздела.

Эти защитные сценарии проверены с введёнными отказами; они не объявляются причинами ошибки конкретного APK. Успешная запись части данных также не означает полноту всех страниц раздела: inventory дополнительно проверяет `has_more`, total и наличие нужных снимков.

## Диагностика

`native_snapshot_error` добавлен в существующий локальный журнал и отчёт «Поделиться диагностикой». Записи упорядочены, чтобы параллельные ошибки не затирали друг друга.

Сохраняются технический раздел без ID пользователя/сущности, этап, тип и допустимый код исключения, очищенное сообщение и стек, длины строк/байтов, наличие и размеры pending/target/backup/legacy. Полные URI, base64, plaintext, ключи, токены и контакты не сохраняются. Неизвестное произвольное сообщение заменяется отметкой об удалении; стек содержит разрешённые имена исходных файлов либо `<source>` и координаты. Диагностика сама не прерывает кэширование.

Перехваты добавлены в storage, сериализацию/чтение collection/envelope, проверку частей адресной книги, coverage и обёртки подготовки/обновления. Ошибки запросов остальных разделов по-прежнему требуют отдельной проверки: в частности, профиль 1С ДО может быть не настроен, запрос может завершиться HTTP-ошибкой, а пагинация — неполными данными.

## Проверки и изменённые файлы

Тесты покрывают малые строки и 700000 символов кириллицы; Unicode/emoji/пробелы; варианты Base64 padding; реальный AES-GCM/AAD; несколько частей адресной книги; повторную и конкурентную запись; готовый файл после сбоя очистки; повреждённую основную копию с исправным backup; отсутствие основного файла при наличии backup; повторное чтение после временного отказа; прежний формат файлов; чтение адресной книги и coverage после перезагрузки JS-модулей с сохранёнными файлами/ключом. Проверка перезапуска использует Node-файлы и модель SecureStore, а не Android Keystore.

Пройдено **148 тестов в 18 наборах**; результат: `artifacts/offline-cache-diagnosis/final-tests.json`. TypeScript: `node node_modules/typescript/bin/tsc --noEmit` — exit 0. `git diff --check` для затронутых файлов — exit 0.

Файлы реализации: `mobile-hub/src/cache/nativeSnapshotStorage.ts`, `nativeSnapshotCache.ts`, `nativeAddressBookSnapshot.ts`; `mobile-hub/src/offline/nativeOfflineCoverage.ts`, `nativeOfflinePreparation.ts`, `nativeReadCacheRefresh.ts`; `mobile-hub/src/diagnostics/diagnostics.ts`, `snapshotDiagnostic.ts`.

Регрессии: `nativeSnapshotStorage.integration.test.ts`, `nativeSnapshotCache.test.ts`, `nativeAddressBookSnapshot.test.ts`, `nativeOfflinePreparation.test.ts`, `nativeReadCacheRefresh.test.ts`, `diagnostics.test.ts`, `mobile-hub/src/test/setup.ts`. Моки `fromCombined` теперь требуют Uint8Array вместо принятия строки, скрывавшего дефект.

Для проверки на Android отдельно нужны сборка и запуск исправленного APK, обычный перезапуск приложения/эмулятора и автономное открытие адресной книги, затем повторная подготовка остальных разделов. В этой задаче APK, версии приложения, lockfile, production и серверные данные не менялись; очистка данных приложения и отключение шифрования не выполнялись.
