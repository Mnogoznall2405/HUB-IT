# Android: совместимость цепочки HTTPS IIS

## Инцидент 09.11.2026

Установленный HUB-IT 1.1.80 (82), Android API 31: HTTP-запросы завершались
`ERR_NETWORK`, хотя сайт работал в Chrome. Отдельный диагностический APK подтвердил:
DNS разрешает опубликованный адрес, TCP соединяется за 34 мс,
`globalSignR46Trusted=false`, `certificate_untrusted` на стадии TLS (91 мс).

IIS отдавал `*.zsgp.ru` → `GlobalSign GCC R46 OV TLS CA 2025`, с опорой на новый
GlobalSign Root R46. Прямой root R46 отсутствует в доверенных CA этого телефона.
При этом проверка современным клиентом, включая HTTP/2, проходит. Успех Chrome
не подтверждает совместимость с системным trust store Android.

Офлайн-модель со старым доверенным GlobalSign R3 отвергает исходную цепочку
(`PartialChain`) и принимает её с официальным cross-сертификатом R46, подписанным R3.
Это подтверждено также read-only проверкой реального TLS IIS: современный профиль
проходит, профиль R3 получает OpenSSL verify code 20 на TLS 1.2 и TLS 1.3.
Доказательства относятся к цепочке; прежние HTTP 404 в журнале IIS — отдельный сбой
публикации и сами по себе не объясняют этот TLS-обрыв.

Проверенные сертификаты, SHA-1 отпечатки для идентификации:

| Назначение | Отпечаток |
|---|---|
| Активный leaf `*.zsgp.ru` | `B3D1AF5755A8A337BB7E5F293F6411B152691348` |
| Intermediate GCC R46 OV TLS CA 2025 | `82F8D711875FA3B9CF9201ABF6224FBAC6712770` |
| Cross R46, подписанный R3 | `B52403B71D0F2457BA45B6E70CA82C83FEB7E615` |
| Старый доверенный Root R3 | `D69B561148F01C77C54578C10926DF5B856976AD` |

Публичные CA-файлы в `scripts/iis/certs/` не содержат приватных ключей.
Cross-сертификат: [официальный каталог GlobalSign](https://support.globalsign.com/ca-certificates/globalsign-cross-certificates),
[официальный DER](https://secure.globalsign.com/cacert/r3r46cross2019.crt).

## Проверка перед/после замены сертификата

```powershell
.venv/Scripts/python.exe scripts/iis/check-mobile-tls.py
# Проверка конкретного узла с сохранением hostname/SNI:
.venv/Scripts/python.exe scripts/iis/check-mobile-tls.py --connect-address 127.0.0.1
```

Проверяются фактически присланная TLS-цепочка, HTTPS hostname, TLS 1.2/1.3 и HTTP
`401` на `/api/v1/auth/me` без токенов. Ожидается exit code 0 и `ok=true` во всех
четырёх проверках. Legacy-профиль содержит только публичный Root R3 и не использует
Windows issuer cache/AIA, поэтому промежуточные сертификаты нельзя незаметно добрать
из кэша компьютера проверяющего. Проверка через loopback не заменяет внешний проход.

Это регрессия конкретного текущего GlobalSign-пути. При смене CA/минимального Android
нужно согласованно обновить доверенный профиль и проверить старейшее поддерживаемое
устройство. Нельзя отключать проверку сертификатов или добавлять произвольные CA
на телефоны вместо исправления серверной цепочки.

После каждой замены leaf, intermediate, root или IIS binding:

1. До переключения проверить сертификат, полную совместимую цепочку и срок действия
   каждого звена. Сохранить предыдущую binding-конфигурацию и порядок отката.
2. После переключения прогнать оба профиля по внешнему имени и по каждому IIS-узлу.
3. Проверить установленный прежний APK на старейшем поддерживаемом Android:
   восстановление входа и открытие рабочего раздела. Отдельно проверить Chrome.
4. Записывать отпечатки реально присланных сертификатов и результаты проверки.
   Контроль срока действия leaf не заменяет проверку совместимости chain.

## Подготовленное исправление этого инцидента

Применено по явному разрешению 09.11.2026 в 23:26 по Екатеринбургу: оба публичных
CA добавлены в LocalMachine/CA, та же HTTPS binding обновлена с прежним leaf.
После изменения `check-mobile-tls.py --connect-address 127.0.0.1` прошёл 4/4 проверки:
современный профиль и legacy R3, TLS 1.2 и TLS 1.3; везде ожидаемый HTTP 401.
Повторное чтение TLS-handshake подтвердило 3 присланных сертификата: leaf,
GCC R46 intermediate и cross R46, подписанный R3; leaf-отпечаток не изменился.
Изменять root-хранилище или перезапускать процессы не потребовалось.
Backup: `artifacts/iis/mobile-tls-chain-20261109-182634-f975c5d9e3fd4f048c51abbd8fc6c876/`.
Проверка на прежнем установленном APK ожидает подтверждения пользователя.

```powershell
# Только план, без изменений:
./scripts/iis/install-mobile-tls-cross-chain.ps1 -RefreshBinding
# Только после явного разрешения менять production-хранилище CA/HTTPS binding:
./scripts/iis/install-mobile-tls-cross-chain.ps1 -Apply -RefreshBinding
```

Скрипт ограничен проверенной binding `hubit.zsgp.ru:443` и leaf-отпечатком выше.
Он добавляет intermediate и cross в **LocalMachine/CA**, сохраняет сведения о binding
и ранее отсутствующих сертификатах в `artifacts/iis/`, опционально обновляет ту же
binding с тем же leaf. Root-хранилище и процессы не меняет. Обновление binding может
кратко затронуть TLS-подключения. Автообновление основного приложения не меняется.

После применения обязательны проверка wire chain и повтор на телефоне. Windows
может продолжить выбирать короткий путь к R46 или держать старую цепочку в кэше.
В таком случае исправление ещё не подтверждено: не отключать root/не перезапускать
IIS/Windows автоматически. Это отдельное расширение операции, требующее разрешения.

Откат первоначальной операции: по сохранённому `state.json` убрать **только** два
сертификата из CA, которых не было до применения, и обновить ту же исходную binding;
root/leaf/приватный ключ и существовавшие CA не удалять. Затем повторить современный
профиль и HTTP-проверку. Для отката также требуется разрешение на названную операцию.

Фактическая публикация на проверенном сервере 09.11.2026:
`Default Web Site` → `C:\inetpub\wwwroot\itinvent`, `/desktop-updates` →
`C:\inetpub\wwwroot\hub-desktop-updates`. Это расходится с прежним описанием прямой
раздачи рабочего frontend `dist/`; при дальнейших релизах проверять effective paths.
Проверочные frontend-сборки всё равно выполнять вне production `dist/`.
