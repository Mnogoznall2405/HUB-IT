# Мониторинг сетевого оборудования

### Надёжность десятисекундного опроса — локально, 22.10.2026

Равномерное расписание, отдельный ICMP executor и учёт бюджета соединений; JSON-история различает отсутствие ответа, ошибку сборщика, пропуск, паузу/backoff и ранние данные неизвестной полноты. График показывает качество наблюдения и продолжает получать дельту при остановке сборщика. Состав, стендовые замеры и открытая PostgreSQL-проверка — [результаты](NETWORK_MONITORING_RELIABILITY_RESULTS_2026-10-22.md). Этот комплект не опубликован.

Первая версия опубликована 15.10.2026, отдельно от МФУ. По последующему запросу пользователя в production подключены все 34 разных адреса со схемы. Можайск остаётся одной целью: текущий адрес опроса `172.16.250.29`, подтверждённый дополнительный адрес того же устройства — `10.105.42.1`.

## Возможности

### Подключение устройства без карточки «Сетей» — локально, 22.10.2026

Форма «Подключить устройство» больше не требует выбирать карточку из раздела «Сети»: нужны название, IP, порт и профиль SNMP. `monitoring_targets.network_device_id` стал необязательным (ревизия `20261022_0143`, снимает только NOT NULL; downgrade блокируется, пока есть цели без карточки). Уже подключённые 34 цели сохраняют связь; при правке цели с карточкой связь не теряется. Endpoint `/monitoring/catalog` оставлен, форма его не вызывает. Не опубликовано. Порядок выкладки: миграция явной командой при релизе → стандартный рестарт backend → сборка frontend, иначе новая форма получит 500 от старой схемы.

### Ускорение опроса и графиков — опубликовано 21.10.2026

Опубликованы независимые очереди ICMP/SNMP, минутное накопление ICMP без ожидания полного SNMP, обработка частичных ответов `ping.exe`, ограниченные кеши истории и независимая загрузка системных и портовых графиков. Завершение опроса сразу будит очередь, без ожидания очередного секундного тика. Тяжёлые JSON/gzip-операции чтения вынесены из API event loop; существующие маршруты и проверки доступа сохранены.

Расписание: ICMP 10 с, короткий SNMP 30 с, полный SNMP 60 с; недоступные цели используют ограниченный backoff. Финальные 40 backend-проверок и 22 браузерных сценария прошли. В коротком рабочем наблюдении центрального узла медиана ICMP — 10,026 с, SNMP — 29,996 с; максимальный ICMP-интервал — 19,025 с, поэтому постоянный максимум 10 с и p95 ≤12 с не подтверждены. У всех 29 целей обновляются ревизии истории; новые минуты центрального узла идут подряд без зарегистрированных потерь пакетов. Сохранены 498 интерфейсов, схема и остальные процессы; миграции не нужны. [Состав выпуска, реальные замеры, ограничения и откат](NETWORK_MONITORING_PERFORMANCE_RELEASE_2026-10-21.md).

Отдельная история задержки с шагом 10 с реализована локально 21.10.2026 и в опубликованный выше комплект не входит. ICMP-точки накапливаются в JSON существующей минутной записи без миграции, график открытого устройства получает только новые точки, а после перезагрузки заново загружает сохранённую историю. Неудачная проверка остаётся разрывом и не подменяется значением `0 мс`; старые минутные записи отображаются с прежним разрешением. Backend-набор — 44 проверки, сценарии графика/дельты/кеша — 4, гонки ответов — 8; изолированная production-сборка проходит. Полный 11-сценарный прогон дошёл до финального состояния удаления устройства, но тестовый Playwright-процесс не завершил cleanup, поэтому общий запуск не считается формально подтверждённым. [Локальные замеры и ограничения](NETWORK_MONITORING_PERFORMANCE_RESULTS_2026-10-21.md).

### Закреплённый интерфейс — опубликовано 16.10.2026

На вкладках «Обзор»/«Графики» рядом с выбором интерфейса доступна булавка: закрепить один порт устройства, заменить другим или открепить. Изменение требует `monitoring.manage`; читатель видит сохранённый выбор. Закреплённый порт определяет мини-график/RX/TX общей карточки и начальный интерфейс подробных графиков после открытия или перезагрузки. При ручном просмотре другого порта закрепление сохраняется. На карточке указаны имя порта и «закреплён». Неисправный/выключенный закреплённый порт не заменяется автоматически работающим.

Выбор хранится в существующем JSON `MonitoringInterface.settings.pinned`; миграция не требуется. Сохранение настроек порта атомарно снимает прежнее закрепление под блокировкой строки устройства. Старые клиенты, не передающие `pinned`, сохраняют выбор. Ответ существующего PUT дополнен `target_summary` для немедленного обновления карточки без перезагрузки всей страницы. При ошибке сохранения предыдущий выбор остаётся. Сигналы о потере линка по-прежнему задаются настройкой «Важный интерфейс»; закрепление не меняет маршрутизатор или правила аварий.

Артефакты реализации — `output/monitoring-pin-20261016/`, публикации — `output/monitoring-release-20261016/`. Изменение опубликовано 16.10.2026 без миграций и удаления production-данных.

Проверено локально: 21 HTTP-сценарий на SQLite, включая две одновременные записи закрепления с проверкой единственного выбранного порта, права/чужой интерфейс, повторный опрос и старый клиент без поля `pinned`. Проверочная production-сборка вне live `dist` успешна; десять прежних браузерных сценариев прошли, новый после уточнения селекторов отдельно прошёл (11,7 с). Он проверяет выбор, обновление карточки, сохранение после reload, смену/снятие и мобильную раскладку. Production-сеанс, Desktop WebView2 и специфические блокировки PostgreSQL отдельно не проверялись.

### Возврат из карточки по Esc — опубликовано 16.10.2026

Esc в открытой карточке возвращает к общей сетке, сохраняет поиск и фильтр и переводит фокус в поле поиска. Открытый диалог или меню сначала обрабатывает Esc самостоятельно; карточка в это же нажатие не закрывается. На общей сетке Esc не меняет выбор. Проверки и артефакты реализации — `output/monitoring-escape-plan-20261016/`; публикация проверена 16.10.2026.

Локальная проверка: сборка вне live `dist` успешна; восемь существующих E2E-сценариев прошли. Новый сценарий Esc после исправления селектора обязательного поля прошёл отдельно: отмена настроек/удаления, приоритет меню, сохранение поиска и фокуса, возврат к началу страницы на desktop/mobile. Временные API/preview остановлены, тестовые порты освобождены. Авторизованный production-сеанс и WebView2 отдельно не проверялись.

### Удаление устройства — опубликовано 15.10.2026

По отдельному выбору пользователя удаление полностью очищает историю мониторинга. В шапке выбранного устройства доступно «Удалить устройство», на телефоне — в меню действий. Подтверждение показывает название/IP и предупреждает об удалении всех измерений, графиков и событий; исходный фокус на «Отмена». При сетевой/серверной ошибке устройство остаётся в интерфейсе, можно повторить запрос. После успешного удаления открывается сетка и фокус возвращается в поиск; поздний ответ обновления не возвращает удалённую карточку.

`DELETE /api/v1/monitoring/targets/{target_id}` требует `monitoring.read` и `monitoring.manage`, возвращает 204, для отсутствующей цели — 404. В одной транзакции под блокировкой строки цели удаляются её raw-измерения, свёртки всех разрешений, события, интерфейсы и сама цель. Карточка `network_devices`, филиал и SNMP-профиль сохраняются. Поздний результат незавершённого опроса не создаёт данные заново; новый цикл больше не включает удалённую цель. Повторное подключение той же карточки создаёт новую цель с пустой историей. Миграция не требуется.

## Архитектура и права

`api/v1/monitoring.py` → `network_monitor_service.py` → `network_monitor_store.py`. Протокольный сбор — `network_monitor_probe.py`; чистые расчёты — `network_monitor_calculations.py`. Таблицы `app.monitoring_*`, ORM `appdb/monitoring_models.py`, миграция `20261015_0135` после `20261014_0134`.

`monitoring.read` даёт просмотр всего раздела без дополнительного `networks.read`; `monitoring.manage` вместе с read — настройки/профили и ручной опрос. Admin имеет оба права, остальные роли получают их индивидуально в существующей карточке пользователя. Manage не даёт права выдавать доступ другим пользователям. Все API проверяют права; профиль с community доступен только на запись, шифруется существующим `MAIL_CREDENTIALS_KEY` и не возвращается даже при ошибке валидации.

Одна цель на `network_device_id`, собственные UUID интерфейсов, история по UUID. Имя/serial/MAC не используются для слияния целей. Смена IP/профиля сбрасывает базу для вычисления скорости, но сохраняет историю. При изменившемся MAC интерфейса запись останавливается до проверки привязки. Сетевые операции выполняются вне транзакции; запись отклоняется, если во время опроса изменили конфигурацию.

Фоновый цикл работает внутри существующего backend: короткие проверки примерно каждые 30 с, полный опрос примерно раз в минуту, обнаружение интерфейсов раз в 15 мин, параллельность четыре устройства, бюджет 8/12 с на короткий/полный SNMP, ограниченный GETBULK. Недоступные устройства опрашиваются с задержкой до 300 с. В первой версии датчики читаются вместе с полным опросом; интервалы заданы в коде, редактора расписаний нет.

PostgreSQL session advisory lock выбирает одного владельца цикла, отдельный lock цели исключает ручной/фоновый параллельный опрос между backend-процессами. Выделенная lock-сессия работает в autocommit, открытая транзакция на время SNMP не удерживается. Потеря владения запрещает запись. На SQLite для локального запуска используется process lock; это не доказательство поведения PostgreSQL при отказе соединения.

## Хранение и очистка

Минутные широкие строки хранятся семь дней; свёртки 5 минут — 30 дней, час — 365 дней. Сохраняется история активных либо важных интерфейсов с включённой историей. Значения по устройству пишутся даже при неудачном полном опросе, чтобы доступность и пропуски ресурсов были видны. Два последовательных снимка необходимы для первой скорости; сброс счётчиков, uptime, смена ifIndex, несовместимая скорость или промежуток более 180 с дают разрыв.

Raw-измерение и обе свёртки записываются атомарно, повтор минуты не удваивает объём. API ограничивает выдачу примерно 1400 точками на серию. При чтении старого произвольного периода берутся только целиком попавшие в него завершённые свёртки; крайние части отражаются отсутствием покрытия, без включения измерений за пределами периода.

Очистка по умолчанию **dry-run**. `MONITORING_RETENTION_APPLY=1` разрешает реальные удаления только после отдельного production-согласования. Владелец цикла запускает её раз в час: до 100 коротких транзакций по 1000 строк с общим бюджетом цикла 20 с. Raw удаляется только при наличии обеих свёрток с соответствующими метриками/min/max; свёртки сохраняются, пока может остаться исходная история их окна. События, настройки, цели и профили автоматически не удаляются. Логи `monitoring_retention` показывают dry-run, допустимые строки текущего пакета и строки без свёрток. Неполный пакет не является общим счётчиком всех просроченных строк; при backlog нужна отдельная оценка объёма.

2. По разрешению выполнить штатную Alembic app-миграцию до `20261015_0135`, передав URL через защищённую переменную `ALEMBIC_DATABASE_URL` по [runbook](../../scripts/pm2/README.md#миграции-бд-при-релизе). Не выводить URL/ключ в команду или отчёт. Код не применяет миграцию в запросах.
3. Проверить наличие действующего серверного ключа шифрования, доступ UDP161/ICMP от HUB, SNMP read-only/разрешённый адрес сборщика на оборудовании. Не менять существующий ключ шифрования ради раздела: он обслуживает другие профили. Выбрать карточки/адреса примерно 20 устройств, внести community через форму профиля. Одну карточку подключить сначала как пилот.
4. По отдельному разрешению задать `MONITORING_BACKGROUND_ENABLED=1`, оставить `MONITORING_RETENTION_APPLY=0`; выполнить штатный backend restart. Для перезапуска только API использовать `scripts/pm2/restart-backend.ps1 -SkipScanRestart`; без этого флага скрипт также перезапускает Scan. Новый процесс PM2 не нужен.
5. По разрешению опубликовать собранный frontend с сохранением IIS `web.config` и rollback. Обычный `npm run build` в рабочем checkout запрещён: live `dist` обслуживает IIS. Проверенный и опубликованный вариант с карточками — `output/monitoring-implementation/frontend-build-cards`; исходники изолированной сборки — `frontend-build-src` рядом с ним.
6. Post-check: readiness/listeners/логи остальных сервисов, новый heartbeat не старше двух минут, новые измерения после двух опросов, графики/права/запрет настроек читателю, отсутствие дублей событий и одного владельца при нескольких backend. Пороги линка и договора WAN задаются по фактическим ожиданиям, текущие 10 Мбит/с без них не объявляются неисправностью.
7. После наблюдения объёма/свёрток отдельно согласовать включение retention apply. До этого данные не удаляются, поэтому сроки хранения не ограничивают рост автоматически.

Rollback: выключить новый сбор согласованным изменением флага и штатным restart, вернуть предыдущие backend/frontend артефакты. Таблицы с накопленной историей оставить. Alembic downgrade удаляет данные раздела и не является обычным production-откатом; он проверен только на временной SQLite.
