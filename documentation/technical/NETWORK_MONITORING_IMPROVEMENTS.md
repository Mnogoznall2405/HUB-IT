# План развития мониторинга сети

Дата: 16.10.2026. Это предложение следующих этапов, а не перечень уже реализованных функций. Источники проверены в интернете на эту дату. Текущий код раздела изучен; работоспособность будущих интеграций на физических MikroTik в рамках этой задачи не проверялась.

Рекомендуемый порядок: **инциденты и уведомления → качество основного/резервного канала → отчёты по простоям → зависимости и схема сети**. Это даст ответы на вопросы «что упало», «с какого времени», «кто занимается», «интернет действительно работает?» и «как часто подводит провайдер».

## Что уже есть

- Прямой SNMPv2c и ICMP из HUB, фоновый сбор без открытой страницы; отдельные права чтения и управления разделом целиком.
- Общая сетка, понятные названия, поиск/фильтр, мини-графики; подробные графики и таблицы, произвольный период, светлая/тёмная тема и мобильная версия.
- Трафик и загрузка интерфейсов, состояние линка, ошибки/отброшенные пакеты, задержка/потери; ресурсы устройства при наличии поддерживаемых OID.
- Роли важных портов, WAN/uplink/VPN, договорные ограничения RX/TX и ожидаемая скорость линка. Есть события потери связи/SNMP/линка, изменения скорости, частых переключений и превышения порогов.
- Дата первого обнаруженного обрыва, длительность, восстановление и последний эпизод. Устаревшие/отсутствующие измерения не подменяются нулями.
- Приостановка опроса и удаление цели вместе с историей. Реестр оборудования, филиал и SNMP-профиль при удалении сохраняются.

Основание: [текущая архитектура](NETWORK_MONITORING.md), `src/pages/Monitoring.jsx`, `src/pages/monitoring/`, `api/v1/monitoring.py`, `services/network_monitor_{probe,service,store,calculations}.py` в соответствующих frontend/backend-каталогах.

Низкий RX/TX показывает малый текущий трафик. Он сам по себе не доказывает снижение пропускной способности интернета. Ping от HUB до MikroTik и проверка доступа в интернет из филиала — разные измерения; в интерфейсе нужно указывать точку проверки.

### Этап 1. Обнаруженная авария становится рабочим инцидентом

1. Создавать инцидент после существующего подтверждения отказа; сохранять время первого неуспешного измерения. В карточке: начало, подтверждение, длительность, последняя проверка, восстановление, причина и источник.
2. Отправлять одно уведомление об открытии и одно о восстановлении. Повторные напоминания — по явной настройке. Устойчивый идентификатор инцидента/доставки предотвращает повторы после рестарта, параллельного опроса и сетевого retry.
3. Действия: «Принять в работу», комментарий, ответственный и «Создать задачу» с обратной ссылкой. Подтверждение человеком не меняет фактическое состояние сети; кнопка задачи не создаёт дубликаты.
4. Первый канал — существующие уведомления HUB, только выбранным получателям с действующим доступом к мониторингу. Email/Telegram — отдельное подключение после выбора получателей и расписания. Недоставленное сообщение остаётся ошибкой доставки, не считается отправленным.
5. Плановые работы имеют начало/окончание, причину и автора. Продолжать измерения и историю, приостанавливать только соответствующие оповещения. После окончания окна проверять текущее состояние и сообщать о продолжающейся аварии один раз.

Подход «обслуживание с сохранением сбора данных» используется в [Zabbix maintenance](https://www.zabbix.com/documentation/current/en/manual/maintenance). Выше описано предлагаемое поведение HUB; устанавливать Zabbix не требуется.

**Приёмка:** последовательность «сбой → подтверждение → рестарт API → восстановление» даёт один инцидент с правильным временем и две логические доставки; нет дублей. Плановое окно не стирает измерения. Пользователь только с чтением не меняет инциденты/настройки, пользователь без доступа не получает раскрывающих данные уведомлений.

### Этап 2. Отличать упавший порт от отсутствия интернета

Паспорт канала связывает существующий порт с филиалом, провайдером, договорной скоростью, назначением «основной/резервный» и связанным VPN. Поля пропускной способности использовать существующие. Несколько IP одного физического устройства остаются его адресами; автоматически объединять оборудование по IP/имени нельзя.

Показывать независимые проверки:

| Проверка | Что означает | Откуда берётся |
| --- | --- | --- |
| Доступность устройства из HUB | HUB видит MikroTik | Уже существующие ICMP/SNMP |
| SNMP | Доступна телеметрия | Уже существующий SNMP; timeout не доказывает выключенную службу |
| WAN-порт | Физический линк/скорость/ошибки | Уже существующие данные интерфейса |
| VPN | Подтверждённое состояние нужного туннеля | Поддерживаемый OID/API после проверки типа VPN; трафик порта сам по себе недостаточен |
| Интернет из филиала | Доступны выбранные внешние узлы и сервисы через нужный WAN | Пробы на самом MikroTik с подтверждённым исходящим маршрутом |
| Резервирование | Основной отказал, резерв принял работу | Результаты проб плюс подтверждение активного пути; не выводить из единичных байтов RX/TX |

Кандидат для проб — встроенный [MikroTik Netwatch](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/netwatch/): ICMP, TCP, DNS, HTTP/HTTPS; расширенный ICMP даёт задержку, потери и jitter. Он исполняется на маршрутизаторе. Для каждого WAN предлагаются несколько независимых контрольных целей и явные пороги, а не зависимость от одного внешнего сайта. Это проектное предложение; параметры пилота выбираются по измеренному качеству конкретной линии.

При выборе исходного адреса дополнительно проверить, что policy routing/VRF действительно направляет пробу через нужный WAN, включая его отказ. Netwatch не является протоколом передачи данных в HUB: способ чтения его результатов нужно проверить отдельно. Доступ по SNMPv2c сам по себе не гарантирует чтение этих показателей. Предварительный вариант — ограниченное чтение RouterOS через доступный защищённый API; окончательный способ выбрать после проверки модели/версии и прав. Результаты последних тестов сохранять в HUB для графиков.

Расширенные типы Netwatch появились в RouterOS 7.4; у старых версий набор другой. Обновление прошивки не включать в этот этап автоматически. [Официальное описание совместимости](https://help.mikrotik.com/docs/spaces/ROS/pages/8323208/Netwatch).

Графики: общий период для трафика, качества и полосы событий; отмечать обрывы, восстановление, переключение резерва и обслуживание. Разрывы связи/сбора оставлять разрывами. Сравнение «сегодня/вчера» и пик/95-й процентиль загрузки считать на одинаковом временном разрешении с указанием покрытия.

**Приёмка:** в пилоте отдельно воспроизведены отключение WAN, потеря внешнего доступа при живом линке, отказ одной контрольной цели и переключение на резерв. Для каждого статуса видно, кто и когда его измерил. Если телеметрия не поступила, показывать неизвестное/устаревшее состояние, а не подтверждённый отказ интернета.

### Этап 2. Отчётность для провайдера

- За 7/30 дней: число подтверждённых обрывов, суммарный/самый длинный простой, начало и окончание каждого эпизода, доля времени с достоверными измерениями, выгрузка CSV.
- Отдельные показатели для устройства, WAN и внешней проверки. Не называть uptime роутера SLA интернета.
- Время делить на «работает / отказ / неизвестно / согласованные исключения». Показывать доступность по наблюдаемому времени вместе с покрытием; при пробелах договорный SLA помечать как неполный. Не считать отсутствие истории доступностью.
- Указывать часовой пояс и расписание услуги; исключения обслуживания учитывать прозрачно. Начало отказа — момент первого наблюдения HUB, точность ограничена интервалом опроса. Для старой истории без достоверного начала не придумывать время.

Раздельные SLO, расписания и исключённые интервалы предусмотрены в [Zabbix SLA](https://www.zabbix.com/documentation/current/en/manual/it_services/sla). Формулы и правила покрытия HUB следует зафиксировать до реализации и проверить на неполной истории.

**Приёмка:** известный набор интервалов, окно обслуживания, смена суток/часового пояса, незавершённый обрыв и пропущенные измерения дают ожидаемые суммы. CSV совпадает с экраном; недостаток истории явно обозначен.

### Этап 3. Схема сети без лавины одинаковых аварий

Сначала задать подтверждённые зависимости центрального узла, VPN и филиалов вручную. При отказе общего узла показывать главный инцидент и список зависимых площадок; их измерения и события сохранять, повторные уведомления подавлять только по подтверждённой зависимости. При устаревших данных о родителе не выдавать предположение за установленную причину. Такой принцип борьбы с каскадом оповещений описан в [Zabbix trigger dependencies](https://www.zabbix.com/documentation/current/en/manual/config/triggers/dependencies).

Дальше добавить подсказки соседей при поддержке устройством. [LibreNMS Auto-Discovery](https://docs.librenms.org/Extensions/Auto-Discovery/) использует LLDP/xDP для обнаружения связей. Для HUB это источник кандидатов: администратор подтверждает связь и соответствие существующей карточке. Поддержку OID на наших моделях проверять отдельно; L2-соседство не определяет всю VPN/WAN-топологию. Новые устройства автоматически не подключать.

**Приёмка:** отказ общего узла даёт одно основное оповещение, вторичные проблемы видны; отдельный отказ филиала остаётся самостоятельным. Циклическая зависимость отклоняется; неактуальная связь не подавляет аварии без объяснения.

### Этап 3. Достоверность самого мониторинга

Показать время последнего успешного опроса, длительность цикла, отставание очереди, heartbeat владельца сбора и ошибки с разделением «нет ответа / недоступны отдельные OID / ошибка сборщика». Глобальная остановка сбора должна делать данные устаревшими, а не объявлять все устройства одновременно упавшими. Пороговые правила дополнять выдержкой времени и разными порогами входа/выхода; существующие события не дублировать новым движком.

Добавить опциональные read-only профили SNMPv3 с аутентификацией и шифрованием, сохранив v2c для текущих устройств. Возможности v3 и ограничения read/write описаны в [MikroTik SNMP](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/snmp/). Сначала пилот совместимых алгоритмов и версии библиотеки, затем поэтапный перевод. Секреты не возвращаются в UI/API и хранятся существующим механизмом шифрования.

Контроль роста истории — объём, возраст и прогноз места. Имеющиеся интервалы свёрток сохранить; автоматическую очистку не включать в рамках этого плана. Для отдельного включения нужны dry-run, границы удаления, метрики и согласование: удалённые измерения обычным откатом кода не восстанавливаются.

## Что оставить на отдельные следующие задачи

| Идея | Польза и ограничения |
| --- | --- |
| «Кто занял канал» | SNMP даёт суммарный трафик порта. Для детализации по IP/портам/потокам рассмотреть NetFlow/IPFIX. У MikroTik Traffic Flow не учитывает аппаратно коммутируемый трафик; потребуются проверка покрытия и отдельное решение приёма/хранения. Новый collector/сервис без прямого согласования не вводить. [MikroTik Traffic Flow](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/traffic-flow/) |
| Проверка доступной скорости | Ограниченный по времени и скорости активный тест по явному запуску в согласованное окно. Он создаёт нагрузку, а CPU отправителя/приёмника может ограничить результат. Постоянный тест на полную скорость не включать. [MikroTik Bandwidth test](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/bandwidth-test/) |
| Wi-Fi, оптика, PoE | Сначала матрица реально доступных OID/датчиков по моделям и версиям. Метрику без поддержки показывать как недоступную, не как 0 |
| Traps/syslog | Дополнить опрос более быстрыми событиями после оценки приёмника и правил сети. Приём событий не заменяет периодическую сверку состояния |
| Конфигурации и изменения | Зашифрованное хранение, скрытие секретов и сравнение версий; отдельный доступ и лимиты. Без автоматического применения конфигураций и перезагрузки |

## Как встроить в HUB

Продолжить существующий путь `router → service → store`, фоновый сбор и PostgreSQL. Интерфейс — текущие MUI-компоненты и тема. Для уведомлений и задач использовать существующие механизмы HUB, предварительно проверив контракт получателей/дедупликации; не добавлять обязательные Redis, Docker или брокер.

Будущие поля инцидента, канала, обслуживания и доставки проектировать отдельными совместимыми Alembic-миграциями после согласования этапа. Физическое оборудование остаётся в `network_devices`; права остаются на раздел целиком. Проверки сети и отправка уведомлений выполняются вне DB-транзакций. Время измерений хранится согласованно, отображается в выбранном часовом поясе.

Каждый этап: локальные HTTP/E2E-проверки реального сценария, изолированная сборка вне live `dist`, upgrade/downgrade на тестовой БД при изменении схемы. Для гонок доставки/инцидентов — параллельная проверка и финальное состояние. Публикация, изменения MikroTik и production-миграции согласуются отдельно; миграции и данные сейчас не изменяются.

## Что уточнить перед соответствующим этапом

Для первого этапа: получатели уведомлений, рабочее расписание, правило повторного напоминания. Предлагаемый старт — уведомления HUB при открытии и восстановлении, без периодической рассылки.

Для каналов: основной/резервный WAN-порт, провайдер, договорная скорость, тип VPN, версии RouterOS, допустимые контрольные цели и возможность ограниченного чтения результатов. Начать с Можайска как одного физического устройства, проверить поведение, затем расширить на остальные площадки. Пароли/community через переписку не запрашивать: использовать существующие защищённые профили/настройки.

Для отчётов: круглосуточный или рабочий график услуги, часовой пояс и согласованные исключения. Для схемы: подтверждённые зависимости центральных узлов/туннелей и филиалов.
