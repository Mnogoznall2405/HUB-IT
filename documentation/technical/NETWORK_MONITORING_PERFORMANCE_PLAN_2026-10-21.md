[Локальные замеры](NETWORK_MONITORING_PERFORMANCE_RESULTS_2026-10-21.md), [выпуск, фактическая частота и ограничения приёмки](NETWORK_MONITORING_PERFORMANCE_RELEASE_2026-10-21.md). Цель: быстро открывать страницу и графики, чаще получать состояние оборудования и отличать сбой устройства от задержки самого сборщика.

Подтверждённые особенности реализации:

- Сборщик ждёт завершения общей группы устройств; ICMP и SNMP занимают общие четыре места в очереди.
- История пишется только при полном опросе; время округляется вниз до минуты. Разрыв линии воспроизведён при всех успешных проверках с интервалом 67 с.
- `ping.exe` ограничен пятью секундами; при превышении этого времени код записывает 100% потерь даже при ответах в частичном выводе. Дефект воспроизведён изолированно. Причина трёх исторических ICMP-сбоев центрального узла остаётся неизвестной.
- Страница сначала получает detail, затем историю; результат устройства и порта применяется вместе через `Promise.all`.
- Изменение `detail.current.checked_at` запускает оба запроса истории, в том числе когда новая минутная точка ещё не появилась.
- В журнале есть общие задержки HTTP и исчерпание пула соединений. Точный вклад авторизации, ожидания потока, соединения и обработки ответа пока не разделён.

Общий план HUB уже содержит работы по счётчикам запросов, event loop и frontend-чанкам. Перед реализацией сверить их фактическое состояние; повторять старые изменения по описанию инцидента не следует.

## 2. Предлагаемая частота и критерии готовности

Это целевые параметры будущей реализации. Рабочая конфигурация сейчас не меняется.

| Данные | Предлагаемое расписание |
|---|---|
| ICMP доступность и задержка | Каждые 10 с для доступных устройств; сохранить группу из трёх пакетов и действующий сетевой таймаут на старте работ |
| Короткий SNMP: идентификация, uptime, состояние портов | Каждые 30 с |
| Полный SNMP: счётчики трафика, ошибки, ресурсы | Каждые 60 с, по собственному расписанию устройства |
| Обнаружение интерфейсов и редко меняющиеся метаданные | Каждые 15 мин |
| Подтверждённо недоступное устройство | ICMP с ограниченным backoff, не реже одного раза в 60 с; тяжёлый SNMP — backoff до 300 с |
| Открытая видимая страница | Текущее состояние примерно каждые 10 с; история — при появлении/изменении минутных данных |

Частые ICMP не должны автоматически ускорять создание аварии. Сохранить настройку `failure_polls` и действующий смысл последовательных контрольных окон примерно по 30 с; при значении 3 это ориентировочно 60–90 с до подтверждения. Внутренняя ошибка сборщика не считается подтверждённым отсутствием ответа устройства. Успешный свежий SNMP по-прежнему подтверждает доступность при заблокированном ICMP.

Цели приёмки, которые нужно подтвердить несколькими сопоставимыми прогонами:

- На стенде с объёмом не меньше текущих 29 целей: p95 интервала ICMP доступного устройства ≤ 12 с; SNMP-счётчиков ≤ 65 с. Отдельно показать p99 и максимальный возраст данных.
- В контролируемом прогоне без внешних отказов и остановок — нет потерянных минут ICMP-истории из-за расписания. Реальные пропуски сборщика видны как «нет измерения».
- Под аутентифицированной тестовой нагрузкой: p95 HTTP истории ≤ 500 мс, p99 ≤ 1 с; сопоставлять с исходным p95 1,24 с и p99 5,35 с на том же сценарии.
- В браузере: p95 первого полезного содержимого списка ≤ 1 с, графиков устройства ≤ 1,5 с; повторное открытие из разрешённого кеша ≤ 300 мс. Холодный вход после полной загрузки сайта измерять отдельно.
- Замедление истории порта на 10 с не задерживает готовые системные графики; ошибка одного запроса не скрывает другой успешный результат.
- Нет новых ошибок пула/очереди, а CPU, соединения, event-loop lag и p95 соседних маршрутов остаются в пределах заранее зафиксированного бюджета стенда.

Интервал 10 с — целевой режим, а не гарантированный результат без нагрузочной проверки. При нехватке ресурсов зафиксировать причину и достигнутые числа; не объявлять цель выполненной по одному удачному запросу.

4. Повторить с одним, пятью и десятью одновременно открытыми клиентами, работающим сборщиком и воспроизводимой соседней нагрузкой. Отдельно записать queue wait и p95/p99 расписания устройств.
5. Если новых стадийных метрик не хватает, добавить их в рамках реализации; включение новой диагностики в production входит только в отдельно согласованную публикацию.

Выход: сопоставимые результаты по стадиям и нагрузке. Прямые 10–12 мс SQL не являются основанием расширять общий пул PostgreSQL или добавлять индексы.

## 4. Этап 1 — независимая и быстрая загрузка страницы

Файлы: `src/pages/Monitoring.jsx`, необходимые компоненты `pages/monitoring/`, существующий `src/api/monitoring.js`.

1. Запрашивать системную историю сразу после выбора цели. Для неё не нужен список интерфейсов из detail. Историю порта запускать после определения выбранного порта.
2. Разделить результаты, loading, error и retry для устройства и порта. Применять каждый успешный ответ сразу; `Promise.all` не должен задерживать готовую секцию.
3. Хранить ограниченный кеш уже открытых историй в памяти текущего клиента: пользователь/права, target, interface, период и разрешение. При повторном открытии сразу показывать сохранённые точки с временем обновления, затем проверять свежесть.
4. Обновление текущего состояния не должно заново скачивать всю историю каждые 10 с. Использовать отдельную ревизию сохранённых минутных данных; не считать `checked_at` признаком новой точки. До появления ревизии допускается ограниченное обновление истории раз в минуту.
5. Перезапрашивать только историю изменившегося порта/периода. Скрытая вкладка не запускает периодические запросы; возврат во вкладку проверяет свежесть.
6. Сохранить защиту от поздних ответов, A → B → A, удаления цели, смены пользователя/прав и завершения ручного probe. Фоновое обновление не очищает готовые графики на время запроса.
7. Разобрать отрисовку отдельно от сети: повторные преобразования одних точек, перерисовку неизменившихся графиков и создание невидимых секций менять только при подтверждении профилем браузера.

Базовый этап сохраняет существующие URL, параметры и поля API. Не добавлять новую библиотеку кеширования. Режим передачи только хвоста истории рассматривать после замера этого этапа: он требует отдельного совместимого контракта для разрешения, заменяемых минут, пропусков и итогового объёма трафика.

## 5. Этап 2 — качество ICMP и независимое расписание опросов

Файлы: `services/network_monitor_probe.py`, `network_monitor_service.py`, `network_monitor_store.py`.

1. Разделить исходы ICMP: подтверждённый ответ, штатное отсутствие ответов, таймаут процесса сборщика и ошибка запуска. Использовать частичный вывод там, где его достаточно для подтверждения ответа; не придумывать 100% потерь без достоверного числа отправленных запросов.
2. Сохранить причины ошибок, время начала/завершения и качество результата. Новые диагностические поля сначала размещать в существующем JSON; изменение схемы БД не предполагается заранее.
3. Вместо ожидания завершения всей группы вести ограниченную очередь заданий с `next_due` для каждого устройства и типа проверки. Следующий срок считать от расписания, а не от завершения предыдущей группы. Просроченные однотипные задания объединять; очередь не растёт бесконечно после паузы.
4. Разделить лимиты лёгкого ICMP и SNMP. Исходный кандидат стенда — до 8 одновременных ICMP и до 4 SNMP; окончательные лимиты выбрать по времени очереди, CPU и нагрузке оборудования. Общие пулы приложения не увеличивать ради достижения цифры.
5. Медленный/недоступный SNMP не удерживает место ICMP. Оставить одного владельца фонового цикла; исключить параллельные одинаковые проверки одной цели между процессами. Для независимых протоколов нужны раздельные времена измерения и атомарное слияние результата.
6. Сохранить проверки версии конфигурации, остановки/удаления цели и потери lease. Старый результат одного протокола не затирает новый результат другого. Ручной probe использует те же ограничения и не создаёт второй параллельный опрос того же вида.
7. Уменьшить подготовительную работу фонового опроса: получать только конфигурацию, текущие измерения и интерфейсы, без пользовательских списков событий/outages; результат фонового collect не требует повторного формирования всей карточки.
8. Вынести discovery и метаданные из частого пути. Повторное использование SNMP engine/transport рассматривать только после замера стоимости создания и проверки корректного закрытия, отмены и отсутствия утечек в установленной версии библиотеки.

Пороговые значения аварий и сетевые таймауты не уменьшать как способ ускорения. Старые настройки целей сохранить; для неизвестного состояния сборщика применять качество «нет данных», а не массовый offline.

## 6. Этап 3 — полная и корректная история

Файлы: `network_monitor_store.py`, `network_monitor_calculations.py`; диагностические поля ответа в существующем `api/v1/monitoring.py` при необходимости.

1. Сохранять минутные ICMP-данные независимо от полного SNMP. Успешные проверки внутри минуты не теряются при переходе границы минуты или неудаче другого протокола.
2. Учитывать все достоверные ICMP-измерения минуты: отправленные/полученные пакеты, задержку и количество проверок. Потери рассчитывать по пакетам, доступность — по определённым успешным/неуспешным проверкам; неизвестные результаты учитывать как отсутствие покрытия.
3. Текущий `_samples` оставляет первую запись минуты и пропускает остальные по детерминированному ID. При разделении опросов необходимо обновление минуты с корректным пересчётом её вклада в 5-минутную и часовую свёртки. Простой повторный вызов существующего метода потеряет новые метрики.
4. Сериализовать обновление одной цели/минуты короткой транзакцией. Повторная доставка, перезапуск и параллельные результаты не удваивают вес, пакетные счётчики или объём трафика; исправление минуты корректно обновляет min/max.
5. Ресурсы и счётчики имеют собственное время измерения: старые CPU/память/трафик не становятся свежими из-за нового ping. RX/TX объём считать только по валидным дельтам счётчиков, а не по каждому повторному ICMP.
6. Реальные пропуски отображать как «нет измерения» с возрастом данных и состоянием сборщика. Первая/последняя незавершённая корзина периода не должна выглядеть подтверждённой аварией.
7. В API истории оставить предел количества точек, совместимость старых данных и отсутствие показателя вместо выдуманного нуля. Ранее сохранённую историю не переписывать по предположению об исправности узла.

Перед реализацией оценить число записей, WAL и размер хранения при новом расписании. Политику retention не менять; новые таблицы/индексы — только при доказанной необходимости, с отдельной Alembic-миграцией и приёмкой.

## 7. Этап 4 — убрать подтверждённое ожидание общего backend

Этот этап зависит от измерений этапа 0 и уже выполненных работ общего плана HUB.

1. Исправлять конкретную найденную стадию: блокирующую работу в event loop, ожидание executor, вложенную выдачу соединения или тяжёлую сериализацию. Не считать свободный пул в момент завершения запроса доказательством отсутствия ожидания раньше.
2. Вложенные операции БД используют существующую сессию; сетевые вызовы и тяжёлые вычисления проходят вне транзакции. Авторизацию и проверку действующей сессии сохранить. Если затрагивается auth-код — предварительно изучить `AUTH_SECURITY_STACK.md` и включить его регрессионные проверки.
3. Для графиков отдавать нужную ограниченную серию с сохранением gzip. Кеш подготовки/сериализации ответа вводить только при подтверждённой стоимости: ограниченный размер, ключ по серии/периоду/ревизии, явная инвалидизация. Проверка доступа выполняется для каждого запроса.
4. Измерить соседние маршруты до/после на той же нагрузке. Ускорение мониторинга не принимается ценой ухудшения работы остальных разделов.

Выход: устранён измеренный источник многосекундного ожидания, а не только улучшен одиночный прямой вызов store.

## 8. Проверки перед приёмкой

Основные сценарии — HTTP через настоящий TestClient и браузер через существующие Playwright-стенды. Внешний опрос и время заменяются только в изолированном контуре.

- ICMP работает при зависшем SNMP; одно медленное устройство не задерживает остальные 28. Проверить смешанный состав, все недоступны, восстановление и возобновление после паузы сборщика.
- Таймаут процесса с частичными ответами, ошибка запуска и штатные три отсутствующих ответа дают разные достоверные результаты. Успех SNMP при заблокированном ICMP сохраняет корректную доступность.
- Повторная запись минуты, конкурирующие ICMP/SNMP, рестарт, потеря lease, ручной/фоновый probe, изменение адреса/профиля и удаление цели сохраняют правильное конечное состояние и агрегаты.
- На нестабильном расписании 59/61/67/90 с нет выдуманных точек; при исправном сборе исчезают искусственные пропуски. Неизвестный интервал не превращается ни в 0%, ни в 100% доступности.
- Медленная/ошибочная история порта не блокирует графики устройства; обратный сценарий работает. Повторное открытие, смена порта/периода, A → B → A и завершение старого probe не подмешивают чужие данные.
- Проверить скрытую вкладку, возврат, одновременный refresh, logout, истечение сессии, отзыв прав, тёмную тему и ширину 390 px. Ограниченный кеш очищается при смене пользователя и прав.
- Прогнать релевантные сценарии `tests/test_e2e_monitoring.py`, `e2e/monitoring.spec.js` и `e2e/audit-monitoring-races.spec.js`; предварительно проверить фактическую изоляцию fixtures и локальные конфигурации.
- Детерминированные проверки планировщика, гонок записи и пересчёта свёрток допустимы отдельно: браузерные E2E не воспроизводят надёжно lease, паузу часов и одинаковый момент конкурентной записи.
- Пробная frontend-сборка только вне `dist`; нагрузочные проверки — на изолированном backend/test PostgreSQL. `EXPLAIN ANALYZE`, искусственные задержки и нагрузочные прогоны на production не выполнять.

В отчёте по этапу: файлы, проверенные сценарии, p50/p95/p99, число SQL и их время, размеры ответов, точность расписания, ресурсы, ошибки, ограничения и остаточные проблемы. Один успешный прогон не закрывает задачу.

## 9. Порядок реализации и отдельная публикация

Порядок: этап 0 → этап 1 → этап 2 → этап 3 → необходимая часть этапа 4 → совместная приёмка. Каждая часть должна быть проверяема самостоятельно; этап 2 с частым опросом и этап 3 с корректной историей выпускаются как согласованный комплект.

Реализация разрешена последующим запросом пользователя «Делай» и выполнена локально. Ещё одним запросом «Делай» после отчёта разрешён согласованный выпуск backend/frontend; он выполнен 21.10.2026. Ни первоначальный план, ни разрешение реализации сами по себе production-согласованием не являлись.

После локальной готовности подготовить конкретный комплект для публикации:

1. Перечень только относящихся к мониторингу файлов/артефактов с хешами, сохранением чужих изменений; результаты тестов и замеров. Для совместимых добавочных полей сначала публиковать backend, затем frontend.
2. Backup backend-файлов и активного frontend, проверка физического пути IIS, сохранение `web.config`/service worker и готовые команды отката. Схема и старые JSON должны оставаться читаемыми прежней версией; несовместимый формат не выпускать без отдельного плана восстановления.
3. Точная команда штатного `scripts/pm2/restart-backend.ps1`. Если она запускает Scan, включить это последствие в согласуемый объём; подходящий `-SkipScanRestart` использовать только после проверки поддержки и выбранного scope.
4. Если потребуется миграция — отдельная подготовка, тест upgrade/downgrade и согласование её применения. Наличие файла миграции не означает её выполнения.
5. После явного разрешения: публикация согласованного комплекта, readiness/listener/PID-проверки, HTTP и браузерная проверка, свежесть данных центрального узла и остальных целей, отсутствие новых ошибок и сохранность других процессов.
6. Сравнение метрик в сопоставимых рабочих окнах после релиза; для минутной истории и редких задержек требуется наблюдение минимум сутки. При регрессии вернуть сохранённые артефакты штатным способом; историю и цели не удалять.

Новая служба, Redis, Docker, брокер, изменения IIS/пулов/авторизации или настроек устройств не являются обязательными частями этого плана. Их необходимость нельзя выводить только из желания увеличить частоту опроса.
