# Надёжность опроса и качество истории — 22.10.2026

Статус: основной выпуск опубликован после согласования «Выкладывай»; [отчёт о публикации и остаточном дефекте](NETWORK_MONITORING_RELIABILITY_RELEASE_2026-10-22.md). Ниже сохранён отчёт о локальном этапе до публикации; его ограничения и формулировки о будущем выпуске относятся к тому моменту. [План](NETWORK_MONITORING_RELIABILITY_PLAN_2026-10-22.md).

## Реализовано

- Старты устройств распределены равномерно по периоду в стабильном порядке идентификаторов. Пробуждение учитывает ближайший срок, а не только секундный тик. Просроченные задания не исполняются задним числом.
- ICMP использует отдельный ленивый executor из 12 потоков: ожидание `ping.exe` не занимает общий executor операций БД. При остановке ожидается завершение ограниченных по времени процессов и закрывается executor.
- Фоновый предел ICMP увеличен до 12 при достаточном бюджете соединений. На PostgreSQL предел уменьшается с учётом конфигурации общего пула: владелец, четыре SNMP lease и резерв для БД/API учитываются отдельно. Три пакета, сетевые таймауты, интервалы 10/30/60 секунд и подтверждение аварий сохранены.
- Слот хранит плановый срок, фактическое начало/окончание, статус ICMP, sent/received, потери, задержку и безопасный код ошибки. Частичный ответ при ошибке процесса сохраняется как свидетельство, но не считается завершённой успешной проверкой. Полные сетевые отказы и внутренние ошибки различаются.
- Запоздавший замер не заполняет окно старой пропущенной проверки. Ручное обновление не стирает результат автоматического опроса. Минутные строки и существующие свёртки сохранены; миграции не нужны.
- Чтение истории различает завершённую проверку, частичные потери, отсутствие ICMP-ответа, ошибку сборщика, пропуск, открытое окно, backoff, явную паузу и раннюю историю с неизвестной полнотой. Паузы сохраняются после возобновления опроса; их журнал ограничен 256 интервалами, усечённая неопределённость явно не объявляется пропуском или успехом.
- Старые минутные данные остаются поминутными. Десятисекундные слоты старого формата читаются с неизвестной полнотой, без выдуманных пакетных счётчиков. История не переписывалась.
- На графике добавлены полоса результатов, текстовая легенда, счётчики полноты и расширенная таблица. При отсутствии всех числовых задержек таблица и качество остаются доступны. Пропуски не соединяются линией успешной связи.
- Для новой истории открытая страница запрашивает дельту каждые 10 секунд даже при застывшем `icmp_checked_at`. Устаревание ICMP определяется по его собственному времени. Отдельное предупреждение показывает устаревший heartbeat сборщика.

## Замеры до/после

Стенд: 29 синтетических целей, модель пула из 25 соединений; реальный код orchestration/collect, заменены только сеть и хранилище. Ускорение времени ×40, три серии по 300 модельных секунд; после прогрева считаются 23 завершённых плановых окна на цель, 667 ожидаемых результатов. Проверяется фактический старт внутри своего окна, а не наличие нарисованного значения.

| Сценарий | Полнота до, три серии | Полнота после | Медиана p95 интервалов ICMP, до → после |
|---|---|---|---|
| Все доступны, группа ping 2,06 с | 100 / 100 / 100% | 100 / 100 / 100% | 10,64 → 10,00 с |
| Смешанные цели, треть групп по 5 с | 77,06 / 77,81 / 77,81% | 100 / 100 / 100% | 20,64 → 10,00 с |
| Дополнительно SNMP 8 с и запись 0,7 с | 67,02 / 67,77 / 66,57% | 100 / 100 / 100% в контрольном повторе | 21,24 → 10,64 с |

Артефакты: `baseline-comparable.json`, `after-final.json`, `after-stress-verified.json`, воспроизводимый `benchmark.py` в указанном output-каталоге. В промежуточном `after-final.json` одна стрессовая серия дала 99,55%; результат сохранён, а не заменён. Контрольный повтор также исправляет стендовое сравнение округлённого ISO-времени с допуском 0,1 мс; сроки производственного кода этим допуском не растягиваются.

Это синтетическая проверка механизма очереди и расписания, не замер реальной SQL/сети. Таймер Windows при таком ускорении ограничивает точность мелких этапов. Общий `stages.queue` содержит также SNMP: его высокие перцентили в намеренно перегруженном SNMP-сценарии нельзя объявлять задержкой ICMP. Цели по реальным SQL, CPU, WAL и соседним API этим прогоном не подтверждены.

Отдельный детерминированный сценарий полного модельного часа проверил для каждой из 29 целей ровно 360 запусков без дубликатов слотов; быстрые/пятисекундные ICMP сочетались с восьмисекундным SNMP. Это проверка алгоритма, а не час наблюдения production.

## Что не подтверждено и выпуск

Изолированный PostgreSQL не запущен: в PATH нет `initdb`/`pg_ctl`/`postgres`, а стандартные каталоги PostgreSQL 16/18 содержат только `data`, без `bin/initdb.exe`. Production не использовался вместо тестовой БД. Поэтому реальные advisory locks, конкуренция общего PostgreSQL-пула, SQL-планы и нагрузка WAL остаются отдельной проверкой до полной приёмки. Модель пула и SQLite не доказывают эти свойства.

Не проверены на production: новые интервалы, суточная полнота, авторизованная страница с реальной историей, p95/p99 соседних API, CPU/WAL и поведение при пиковой нагрузке. Локальная сборка всего checkout является проверочным артефактом, а не изолированным пакетом для публикации: в дереве есть посторонние изменения.

До согласованного выпуска нужны отдельная PostgreSQL-проверка в безопасной среде и подготовка ограниченного пакета со сверкой действующего runtime, резервными копиями и хешами. Затем — отдельно согласованные frontend и штатный рестарт только API с `-SkipScanRestart`, если параметр и объём подтверждены. Общие конфиги и схема не меняются.

Откат: восстановить только согласованные файлы этого выпуска с защитой поздних изменений, сохранить действующие IIS-конфиги/service worker, штатно перезапустить API. Дополнительные JSON-поля не требуют удаления или переписывания истории; старые читатели должны игнорировать незнакомые поля. Post-check: readiness, listener/PID, сохранность остальных процессов, один сборщик, новые реальные проверки и корректное отображение пропусков; затем контрольный час и сутки.

Сборщик остаётся внутри API и не измеряет сеть во время его остановки. Три ping раз в 10 секунд не исключают короткий обрыв между проверками. Новый интерфейс показывает эти границы наблюдения явно.
