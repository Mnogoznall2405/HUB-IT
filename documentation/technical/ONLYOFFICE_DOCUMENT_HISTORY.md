## Поведение

Пункт истории внутри ONLYOFFICE переключает ту же область экрана
на штатную историю редактора. Доступны сохранённые версии, авторы отдельных ревизий
и подсветка изменений при наличии архива правок. История работает только на просмотр.
Рабочий редактор остаётся смонтированным: его iframe, неотправленные правки и соединение сохраняются.
Во время просмотра он скрыт и исключён из клавиатурной навигации. Закрытие истории возвращает
к рабочему документу и восстанавливает фокус без перезагрузки страницы. Дополнительного окна HUB нет.
Во время загрузки или ошибки доступна компактная кнопка возврата; постоянно видны только элементы ONLYOFFICE.
В прежнем выпуске 11:26 история открывалась отдельным диалогом с информационными плашками.

Отдельный экземпляр SDK нужен для сохранности рабочей сессии: `refreshHistory` отключает
совместное редактирование в том экземпляре, где вызван. Метод вызывается только у просмотрщика,
поверх скрытого рабочего редактора. Неотправленные правки не переносятся и не отбрасываются.

Используются `onRequestHistory`, `refreshHistory`, `onRequestHistoryData`, `setHistoryData`,
`onRequestHistoryClose`, `onRequestClose` из [официального контракта](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/document-history/).
Данные авторов берутся из подписанного callback `history.changes`, а не вычисляются по последнему сохранявшему.
Показ подсветки также зависит от совместимости `serverVersion` с Document Server.

История отражает сохранённые в HUB версии. Правки текущей совместной сессии появятся после сохранения;
принудительное сохранение не включалось. Ранее сохранённые файлы доступны для просмотра,
но отсутствующие архивы старых правок не восстанавливаются из XLSX. Такие версии открываются без подсветки;
постоянное уведомление об отсутствии архива убрано.
Это штатная история сохранённых версий; отдельной таблицы аудита «ячейка / было / стало» здесь нет.

## Хранение и корректность

Миграция `20261105_0161` добавляет поля в существующую `app.my_file_versions`:

| Поле | Назначение |
| --- | --- |
| `office_history_json` | Проверенные `serverVersion` и список авторов/времени правок |
| `office_changes_blob_id` | Одна ссылка на архив правок в существующем хранилище блобов |
| `office_changes_size_bytes` | Размер архива для учёта квоты |
| `office_result_blob_id` | Содержимое, к которому относится архив |

Существующая строка версии хранит файл **до** сессии редактирования; архив описывает переход от него
к результату сессии. Сопоставление по номеру версии и `office_result_blob_id` исключает подсветку чужого перехода
после автосохранения или восстановления. Если предыдущая версия уже удалена, подробные правки не показываются.
Версии передаются SDK по возрастанию: контроллер ONLYOFFICE обходит массив в обратном порядке
и определяет предыдущий ключ по соседней записи. Порядок проверен по
[исходникам редактора](https://github.com/ONLYOFFICE/web-apps/blob/master/apps/spreadsheeteditor/main/app/controller/Main.js).

- Архив загружается только по проверенному адресу кеша Document Server из подписанного callback.
  HTTP/проверка ZIP/антивирус/публикация файла выполняются вне транзакции БД.
- При сбое архива сохраняется сам документ. Повтор callback с теми же байтами может дополнить архив
  без создания новой версии. Повторные и параллельные callback не добавляют лишних ссылок на архив.
- Каждый выполняющийся callback публикует архив в свой путь; дедупликация остаётся в БД по владельцу и SHA-256.
  Откат одного callback не удаляет файл, который сохранил другой.
- Архивы учитываются в квоте, освобождаются при сокращении истории, восстановлении и окончательном удалении.
  Если места для архива нет, документ сохраняется без подробных данных правок.
- Ограничения: архив до 32 МиБ, объявленный распакованный объём до 256 МиБ, до 1000 элементов ZIP,
  JSON истории до 2 МиБ/10000 записей. ZIP проверяется без распаковки на диск.
  Существующая антивирусная политика, включая согласованные пропуски архивов, сохраняется.
- После изменения содержимого старые данные правок не подставляются к новому файлу.
  Восстановление версии не приписывает прежние правки тому, кто выполнил восстановление.

## Доступ и API

- `GET /api/v1/my-files/{id}/office/history`: список версий для `refreshHistory`.
- `GET /api/v1/my-files/{id}/office/history/config`: конфигурация отдельного редактора в режиме `view`,
  с другим ключом кеша и без `callbackUrl`.
- `GET /api/v1/my-files/{id}/office/history/{version_no}`: подписанные данные `setHistoryData`
  и `changes_available`. Содержит ссылки на выбранный файл, предыдущий файл и архив при его наличии.
- `GET /api/v1/my-files/office/history/source?t=...`: содержимое для SDK/Document Server.
  JWT действует 600 секунд и привязан к файлу, пользователю, версии, виду данных и конкретному блобу.
  При каждом скачивании повторно проверяются активность пользователя, права, корзина, срок и антивирусный статус.
  Ответы имеют `Cache-Control: private, no-store` и `Referrer-Policy: no-referrer`.

Прежние права владельца, автора библиотеки, администратора и приглашённых сохранены.
API-конфигурация основного редактора дополнена `can_view_history`. Старый backend без этого поля
оставляет прежнюю панель скачивания/восстановления версий. Смена аккаунта или закрытие окна
отменяет запросы истории; запоздавшие ответы и выбор предыдущей версии не меняют текущий просмотр.

Основные файлы: `services/my_files_history_service.py`, `my_files_collab_service.py`, `my_files_service.py`,
`onlyoffice_service.py`, `api/v1/my_files_office.py`, `appdb/models.py`, миграция `20261105_0161`;
frontend `api/myFilesOffice.js`, `components/myFiles/MyFilesOfficeHistoryView.jsx`,
`MyFilesEditorShell.jsx`, `MyFilesEditorSurface.jsx`, `useMyFilesEditorSession.js`.
