## Поведение

- В шапке редактора есть переименование и «Доступ». Они используют полномочия HUB, а не отдельный
  список прав ONLYOFFICE. Открытый iframe не пересоздаётся, неотправленный текст остаётся в нём.
- При переименовании меняется имя в хранилище HUB через существующий `MyFilesService.update_file`:
  сохраняются аудит, формат, содержимое, версии и ключ совместной сессии.
- После завершения транзакции подписанная команда `meta` отправляется на внутренний Document Server.
  `onMetaChange` обновляет шапку HUB и название вкладки у открывших документ пользователей.
- HTTP-запрос к Document Server ограничен пятью секундами. Ответ считается подтверждением только при
  HTTP 200, целочисленном `error=0` и совпавшем ключе документа. Редиректы не разрешаются.
- После доставки имя и ревизия перечитываются. Если конкурирующее переименование или закрытие сессии
  изменило их, отправляется актуальное значение (не более трёх попыток). Сетевые вызовы не держат транзакцию БД.
- Если имя записано в HUB, но `meta` не подтверждена, API возвращает успешную запись с
  `editor_notified=false`. UI показывает предупреждение и сохраняет окно. Команда не является `forcesave`
  и не создаёт версию документа.
- Если ответ на переименование потерян, UI не повторяет изменяющий POST автоматически и предлагает
  проверить имя в «Моих файлах». Двойное нажатие не создаёт параллельный запрос.
- «Доступ» открывает существующий `MyFilesCollaboratorsDialog` с теми же ролями и endpoint.
  Ошибка или неподтверждённая структура списка не превращается в пустой список: сохранение запрещено.
- Смена файла/аккаунта отключает старые обработчики и отменяет ожидающий клиентский запрос;
  поздний ответ не меняет следующий документ. Отмена клиента не означает отмену уже принятой серверной операции.
- На узком экране название занимает свою строку; кнопки сохраняют доступные имена и помещаются на ширине 360 px.

## Права и контракт

Подготовленное изменение 2026-11-05 (ещё не опубликовано): администратор управляет любым файлом,
а автор файла общей папки — его прямыми приглашениями. Роль управляющего библиотекой сама по себе
этого не разрешает. Актуальный подготовленный контракт и проверки: [MY_FILES_ADMIN_ACCESS.md](MY_FILES_ADMIN_ACCESS.md).
Таблица ниже описывает опубликованный этап 2026-11-04.

`GET /api/v1/my-files/{id}/office/config` дополнен полями:

| Поле | Значение |
| --- | --- |
| `can_rename` | Роль `owner`: собственник личного файла либо управляющий библиотекой |
| `can_manage_access` | Только фактический собственник личного файла; управление библиотекой остаётся в окне библиотеки |

UI дополнительно требует `my_files.write` для переименования и `my_files.share` для доступа.
При отсутствии полей в старом backend новые действия скрыты; открытие и восстановление документа работают.
Эти поля управляют отображением, сервер повторно проверяет доступ для каждой операции.

Новый endpoint `POST /api/v1/my-files/{id}/office/rename`:

```json
{ "name": "Рабочий план" }
```

Формат берётся из существующего файла; пути и пустые имена отклоняются. Ответ:

```json
{
  "file": { "id": "...", "original_file_name": "Рабочий план.docx" },
  "editor_notified": true
}
```

`file` имеет существующую полную схему `MyFileResponse`; здесь показаны только два поля.
Endpoint требует `my_files.write`, проверяет origin и полномочия владельца через существующий сервис.
Редакторская роль `edit` сама по себе не даёт права переименования.
