# SCAN: план ускорения OCR и точности (проверен замерами 16–17.09.2026)

Статус: план согласован по объёму, реализация — по команде «запускай».
Файлы проекта НЕ меняются до явного «запускай». Реестр правок — внизу.

## 1. Цель и ограничения

- Цель по скорости: ~1200 файлов/ч **на один OCR-процесс**, т.е. ~3 с/файл при
  текущей параллельности (3600 / 1200 = 3). Базлайн: ~15,5 с/файл (avg OCR).
- Жёсткие инварианты (подтверждены пользователем):
  - Текстовому слою не доверять: он бывает битый, из-за него уже были пропуски.
  - OSD/поворот **оставлять всегда** — это страховка от пропусков.
  - Обязательный OCR первых 3 страниц — политика, не менять.
- Приоритет сейчас: скорость. Точность (DPI 250/300, `rus`) пока не трогать;
  A/B по `rus+eng` / DPI 300/400 — отдельным шагом.

## 3. Честная математика цели «3 с/файл на процесс»

Полный проход страницы (250 DPI) стоит минимум:
OSD 1,34 + full 2,36 + регионы 1,23 + спавн ≈ **5 с/стр**,
файл из 3 страниц ≈ **15 с**. Спавн и рендер — ещё ~1 с.

Вывод: **3 с/файл недостижимы при сохранении всех трёх стадий на всех
3 страницах** — один только full-page OCR трёх страниц стоит ~7 с.
Реалистичный пол при сохранении инвариантов (см. тиры ниже): **~11–12 с/файл**,
т.е. ~300 файлов/ч на процесс; на 10 процессах — **~3 000 файлов/ч системой**
(сейчас ~1 150). Путь к «3 с/файл» существует только через смену политики
(не OCRить страницы с хорошим слоем) — это запрещено инвариантом выше,
поэтому в план не входит.

- OSD (`_detect_osd_angle`) выполняется в пуле параллельно с full-page OCR той же

### Этап 2. Дедуп по content-hash (код, −7…−22 % OCR-нагрузки) — РЕАЛИЗОВАН 2026-09-17, НЕ ЗАДЕПЛОЕН
- Ключ `(sha256 обработанных байт, analysis_version, ocr_profile)`, где
  `ocr_profile = lang|dpi|focused_dpi|max_pages`. Уточнение к исходному проекту
  `(file_hash, version, pattern_set)`: паттерны в ключ НЕ входят осознанно —
  матчинг есть чистая функция текста и на каждый hit пересчитывается свежими
  правилами с фильтром джобы, поэтому смена правил кэш не инвалидирует и hit-rate
  выше. Инварианты сохранены: кэшируются только complete-результаты
  (`ocr_text_ready` с непустым текстом, `ocr_blank`), ошибки/таймауты/partial —
  никогда; текстовый слой идёт свежим всегда; OSD/поворот не тронуты.
- Таблица `scan_ocr_cache` (SQLite DDL + PG ORM `ScanOcrCache` + Alembic
  `20260917_0002_ocr_cache`); методы `get/put/note_ocr_cache_hit`;
  TTL-чистка внутри `cleanup_retention` (`ocr_cache`, `SCAN_OCR_CACHE_RETENTION_DAYS=14`,
  dry-run поддерживается). Первый писатель побеждает (ON CONFLICT DO NOTHING);
  kill-switch `SCAN_OCR_CACHE_ENABLED=0`; кап текста 128 000 символов.
- Метрики: `metrics["ocr_cache"]="hit"|"miss"` в метриках джобы
  (попадают в `scan_jobs` через `job_metrics.update`), `cache_hit` в `metrics["ocr"]`.
- Тесты: новый `tests/test_scan_ocr_cache.py` — 13/13 (roundtrip, first-writer-wins,
