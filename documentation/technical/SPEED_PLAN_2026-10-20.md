# План ускорения HUB-IT (2026-10-20)

Основан на замерах за 20.10 (`request-metrics/local`, `http.slow`, `sql.slow`, изолированный стенд). Выборка после рестарта маленькая: цифры — ориентир, цель каждого пункта подтверждается замером «до/после» на том же сценарии.

## Базовые цифры (до)

| Запрос | p50 | p95 / пик | Причина |
|---|---|---|---|
| `GET warehouse-1c/employee-compare-summary` | 165 мс | 17,6 с | пересборка по запросу: один пакетный вызов 1С 5–15 с; при ошибке результат не кешируется, каждый запрос заново тратит ~1 с |
| `GET warehouse-1c/it-requests` | — | 15 с (1 запрос) | живой запрос в 1С без кеша |
| `GET mail/bootstrap` | 903 мс | 2,2 с | последовательные почтовые вызовы |
| `GET mail/folders/summary` | 701 мс | 917 мс | то же |
| `GET address-book/search` (холодный) | — | 2,2 с | первый запрос после рестарта |
| `POST warehouse-1c/part-no-check` | ~1 с | — | последовательные вызовы 1С |
| `POST equipment/current-acts` | 124 мс (в пике 1,1–1,3 с) | 377 мс | нужен разбор по стадиям |
| `POST my-files/{id}/download-grant` | 8,5 мс в изоляции | 1,1 с в параллельном всплеске на проде | код дешёвый; на проде — конкуренция в БД (см. П6) |
| Остальной трафик (`notifications/poll`, `unread-counts`, `heartbeat`, `unread-count`) | 10–40 мс | 100–200 мс | норма, не трогать |

RTT до app-БД 0,4 мс (БД локальная), поэтому «меньше запросов к PostgreSQL» само по себе почти ничего не даёт.

## Порядок работ

### П0. Наблюдаемость (первым, маленький риск)
- Добавить время в строки `sql.slow` (сейчас без timestamp, лог накопительный, окно не выделить) и correlation id запроса.
- Скрипт-снимок `request-metrics/local` в файл до/после каждой правки (одинаковый сценарий и объём).
- Критерий готовности: можно за любой час получить топ SQL по суммарному времени.

### П1. Сводка сверки с 1С: фоновый прогрев и отрицательный кеш
- Строить `employee-compare-summary` в фоне по расписанию (TTL остаётся), запрос отдаёт готовый кеш; при устаревшем кеше отдавать старый и обновлять в фоне (stale-while-revalidate).
- Кешировать ошибку построения на короткий срок (30–60 с), чтобы цепочка 400/503 не жгла по ~1 с на каждый запрос.
- Цель: p95 < 300 мс на странице «База», 0 запросов с ожиданием 1С из UI.
- Зависимость: файл `warehouse_1c_service.py` ведёт Codex; сначала согласовать (guard лимита 2000 складов должен сохраниться, см. продолжение 54).
- Проверка: тест на кеш/устаревание через `TestClient`, замер p95 до/после.

### П2. `it-requests` и `part-no-check` в 1С
- `it-requests`: кеш с коротким TTL + stale-while-revalidate, таймаут и понятный 503 вместо 15 с ожидания.
- `part-no-check`: один пакетный вызов или параллельные вызовы с ограничением вместо последовательных.
- Цель: p95 `it-requests` < 1 с при тёплом кеше; `part-no-check` — время пропорционально одному вызову 1С.
- Зависимость: те же файлы Codex (`warehouse_1c.py`, `warehouse_1c_service.py`).

### П3. Почта: параллельность и короткий кеш
- `mail/bootstrap` и `folders/summary`: независимые вызовы выполнять параллельно, результат кешировать на 5–15 с на пользователя.
- Цель: p50 `bootstrap` < 400 мс, p95 < 1 с.
- Файлы Codex не затрагивает; можно делать независимо.

### П4. Холодный старт адресной книги
- Прогревать индекс/кеш адресной книги при старте backend, чтобы первый `search` не стоил 2 с.
- Цель: первый `search` после рестарта < 500 мс.

### П5. Frontend
- Чанки больше 500 КБ (предупреждение `vite build`): разбить динамическими импортами по маршрутам, тяжёлые библиотеки (`xlsx`, `qrcode`, редакторы) подгружать по требованию (часть уже так).
- Цель: уменьшение начального JS, замер через пробную сборку вне `dist` и Lighthouse/ресурсы вкладки Network.
- Публикация только по команде владельца (`npm run build` = боевой деплой).

### П6. Счётчики лимитов и сессии (после П0)
- Кандидаты: `auth_runtime_store_service._increment_counter_db` (`SELECT ... FOR UPDATE` на общей строке счётчика IP, синхронный вызов внутри `async`-обработчиков), частые `SELECT` по `app.sessions` и `auth_runtime_items`.
- Варианты: первый уровень счётчика в памяти процесса с периодическим сбросом в БД, вызов через `run_in_threadpool`, кеш проверки сессии на секунды.
- Нельзя ослаблять лимиты и проверки сессии; изменение политики auth — только отдельным решением (`AUTH_SECURITY_STACK.md`).
- Нужен замер под параллельной нагрузкой на стенде с PostgreSQL.

### П7. `current-acts`
- Разобрать по стадиям (пики 1,1–1,3 с при p50 124 мс): что именно ждёт — 1С, SQL Server или сериализация. Правка только после разбора.

## Что не делаем
- Не вводим Redis/брокер/новые сервисы (AGENTS.md).
- `download-grant` не меняем: код и так 8,5 мс (продолжение 56).
- Ничего не выкатываем без явной команды: каждый пункт, меняющий backend, требует штатного рестарта (`restart-backend.ps1`, scan входит), frontend — бэкапа `dist` и сверки `sw.js`.

## Контроль результата
- Для каждого пункта: снимок метрик до и после на том же сценарии, p50/p95/p99, доля ошибок, `event-loop lag` там, где применимо; один прогон не считается доказательством.
- Результат записывать в `AUDIT_PLAN_2026-10-18.md` новым продолжением.
