## 3. Находки

Severity: **P0** — ломает функцию или показывает неверные данные; **P1** — сильный UX-дефект или риск; **P2** — polish и долг. Метка «runtime» — воспроизведено на mock, «код» — подтверждено чтением кода и контракта.

### P0

**V01 — В карточке встречи показывается транскрипт другой встречи** (runtime)

- `VoiceMeetingDrawer.jsx:215-226`. Загрузка транскрипта срабатывает при `tab===1 && !transcript && !transcriptBusy`, без AbortController и без привязки ответа к `base`. Сброс на `:199-213` не сбрасывает `transcriptBusy`.
- Воспроизведение: открыть «Встреча_5» → «Текст разговора» (запрос идёт) → закрыть и открыть «Встреча_6» → дождаться ответа → открыть «Текст разговора» у «Встреча_6». Показаны реплики с меткой `[…Встреча_5]`.
- Условие: детали B приходят раньше транскрипта A. Обратный порядок случайно очищает чужие данные повторным сбросом на `:213`.
- Исправление:
  - хранить транскрипт как `{base, data}` и показывать только при совпадении с текущей встречей;
  - отменять запрос через AbortController при смене `base` и закрытии;
  - сбрасывать `transcriptBusy` при смене `base`.

### P1

**V02 — Цепочки polling накапливаются при возврате на вкладку** (runtime)

- `VoiceVideoPage.jsx:207-240`. `onVisibility` вызывает `tick()`, а `tick` вызывает `schedule()`. `schedule` перезаписывает `timer`, не очищая уже запланированный, поэтому цепочек становится две, три и так далее. `clearTimeout(timer)` при размонтировании очищает только последнюю; остальные останавливаются флагом `stopped` на своём тике.
- Замер: 3 запроса `/jobs` за 13 с в базовом режиме против 13 запросов за 13 с после 5 событий `visibilitychange`.
- Проверка `document.hidden`: при скрытой панели за 32 с ни одного запроса, то есть pause-on-hidden работает.
- Сервер: каждый тик `/meetings` вызывает `store.list_jobs(limit=500)` (`app.py:387-422`).
- Исправление: перед `schedule()` делать `clearTimeout(timer)`, а `onVisibility` должен отменять ожидающий таймер и вызывать `tick()` один раз.

**V03 — Открытие карточки: вечный спиннер и гонка ответов** (спиннер — runtime, гонка — код)

- `VoiceVideoPage.jsx:242-249, 416-419, 481-485`; `VoiceMeetingDrawer.jsx:427-428`.
  - `refreshMeeting` глотает ошибку (`catch {}`). При 500 или 404 карточка показывает бесконечный `CircularProgress` без сообщения и без «Повторить». Подтверждено: 3 с спустя спиннер остаётся, алертов нет.
  - Нет защиты от порядка ответов: открыли A, затем B — поздний ответ A перезапишет B.
  - `onAssigned` вызывает `refreshMeeting(base)` после `await refreshVisible()`. Если пользователь закрыл карточку, она откроется снова.
- Исправление: счётчик запроса (`requestId`) и AbortController; состояние `error` с кнопкой «Повторить»; не открывать карточку, если она закрыта.

**V04 — Состояния списков: ошибка выглядит как «данных нет»** (runtime)

- `VoiceVideoPage.jsx:61, 103, 136, 152, 285-289, 341`; `VoiceMeetingsSection.jsx:206-211`; `VoiceVoicesSection.jsx:98-103`.
  - `sectionLoading` переводится в `true` только при старте и больше никогда: при смене фильтра или страницы индикатора нет, виден старый список.
  - Ошибка meetings показывает красный Alert и одновременно «Здесь появятся готовые протоколы встреч» с кнопкой «Загрузить запись» (скриншот 1440 px).
  - Отдельно, «Сводка» показывает «Готово: 0» и пустой график при неудачной загрузке jobs.
  - Alert ошибки без кнопки «Повторить»; повтор возможен только кнопкой «Обновить» или при следующем polling.
  - `activeError` берётся только по активной вкладке: ошибка jobs при открытых «Протоколах» не видна, а чип очереди устаревает молча.

- Исправление: отдельные состояния `loading / refreshing / error / empty / data`, Alert с «Повторить» и без пустого состояния при ошибке, skeleton для «Голосов», индикатор при перезагрузке страницы.

**V06 — Обратная связь при назначении имён теряется, баннер зависает** (runtime)

Замер на 250–2750 мс: в списке алертов всегда только баннер.

**V07 — «Впереди: N · ~M мин» считается в обратном порядке** (код)

- `VoiceJobsSection.jsx:199-208`. Сервер отдаёт задачи `ORDER BY created_at DESC` (`store.py:118`), а `queuePositions` идёт по списку сверху вниз, считая, что первым идёт самый старый. Для новой задачи получается «впереди 0», для старой — наибольшее число. Очередь FIFO, поэтому значения инвертированы.
- В mock-данных порядок произвольный, поэтому на mock значение «Впереди: 1» выглядело правдоподобно; вывод сделан по коду и серверной сортировке.
- Дополнительно: расчёт опирается на первые 100 задач (`limit: 100`, `VoiceVideoPage.jsx:92`), а оценка времени — на среднее только по завершённым из этих 100.
- Исправление: сортировать копию списка по `created_at` по возрастанию перед подсчётом; учитывать только активные задачи.

**V12 — На протокол нельзя сослаться, публичную ссылку нельзя отозвать** (код + вопрос политики)

### 5.1 UX-архитектура

Объединить задачи с протоколами (рекомендую)** | В «Протоколах» сверху строки «В обработке / В очереди / Ошибка» с прогрессом и действиями; фильтр-чипы «Все / В работе / Нужны имена / Готово / Ошибки»; «Очередь» — вид этого же списка; «Голоса» — вторичный раздел (вкладка или страница «Справочник голосов») | Одно место для «что с моей записью»; убирает переключение вкладок; проще мобильное | Нужно клиентское слияние jobs и meetings (данные уже есть: `jobs` и `_meeting_view` с задачами по base); backend не меняется | L |

### 5.3 UI-план

- **Мобильный (320–390).** Шапка: заголовок, действие «Загрузить» (primary) и «⋯» (обновить, экспорт). Поиск + «Фильтры (N)» → bottom sheet; активные фильтры — чипы под поиском. «Сводка» одной строкой чипов, без графика. Карточка встречи: название в 2 строки (clamp + tooltip), дата, статус-чип, участники; действие — вся карточка как ссылка. Карточка встречи — полноэкранная страница, фиксированная шапка с «Назад».
- **Десктоп (≥1024).** Таблица: «Встреча (название + проект/теги)», «Статус», «Участники/реплик», «Дата», «⋯». Технический `base_filename` — только в деталях. Основное действие — открыть (ссылка в первой ячейке), вторичные — в меню «⋯». Цель касания — 44×44 на устройствах с `pointer: coarse` (порог по типу указателя, а не по ширине; 44 px — требование дизайн-системы, T17).
- **Иерархия действий.** Primary: «Загрузить» (одна на страницу). Secondary: экспорт, обновить. Опасные (удалить, отменить) — только в меню с подтверждением через диалог MUI вместо `window.confirm`.
- **Статус-чипы.** Единый компонент со словарём: queued/processing/done/failed/cancelled/needs-names; иконка + текст (не только цвет); контраст ≥4,5:1 в обеих темах (V24).
- **Пустые состояния.** Четыре варианта: нет данных (CTA «Загрузить»), нет результатов по фильтру («Сбросить фильтры»), ошибка (текст + «Повторить»), нет прав. Skeleton для всех вкладок, включая «Голоса»; индикатор при перезагрузке страницы.
- **Карточка встречи.** Заголовок — `DialogTitle` (V15); вкладки «Участники / Текст / Поручения / Отчёты»; вкладка по умолчанию — «Участники», если есть неопознанные, иначе «Отчёты»; редактор тегов и проекта — inline в «Деталях», не выше вкладок; `maxHeight` на мобильном — 100%.
- **Длинные тексты.** Названия и ошибки задач: clamp на 2 строки + «показать полностью» или tooltip; сообщения об ошибке задач — раскрываемые, полный текст в логе.
- **Типографика и дизайн-система.** Один H1 на страницу (убрать дубль AppBar + H6); отступы и elevation — из `officeUiTokens` (`PageShell`, `getOfficePanelSx`); порядок групп — 8 px внутри, 16+ между.

### 5.5 Что нельзя ломать

- Auth flow и silent refresh (`client.js`: refresh + повтор запроса; для voice-запросов повторный 401 не разлогинивает).
- Polling: интервалы 5 с при активных задачах и 30 с в простое, backoff ×2 до ×4, пауза при `document.hidden` (проверено: 0 запросов в скрытой панели) — с исправлением V02, но без изменения этих значений.
- Deep link `?share=` и однократная очистка параметра из URL.
- Экспорт ZIP (формат имени и содержимого, маршрут `/voice/export/reports.zip`).
- Soft-delete в корзину на 30 дней и подтверждение перед удалением.
- Permission-гейты `voice.read/upload/manage` и `tasks.create/write`; серверные проверки остаются источником истины.
- Существующие тесты: все файлы `pages/voice-video/*.test.*` (сейчас 10 файлов, 140 тестов) остаются зелёными; при переносе действий в «⋮» тесты обновляются под `menuitem`, а не удаляются.
- Логика частей объединённой записи (`mediaParts.js`, `seekMedia`) и единый `<audio>` (`useSingleAudio`).
- Совместимость с Desktop WebView2 (origin/navigation policy) и мобильным браузером; новые маршруты `/voice/<base>` согласовать с политикой навигации Desktop.
- Границы контрактов: `voice_server` API, публичные эндпоинты `/public/<token>`.

## 8. Задачи исполнителю и журнал ревью

Роли: **ревьюер** — ставит задачи, принимает результат, дописывает замечания сюда; **исполнитель** — отдельный агент, меняет код только в рамках выданной задачи. Ревьюер код не правит.

Порядок работы:
1. Исполнитель делает задачи по порядку и после каждой сам меняет её статус в таблице на `выполнено, ждёт ревью`, дописывая ниже в «Отчёте исполнителя» результат (файлы, красный и зелёный прогон, что не проверено, риски).
2. Исполнитель **не ставит** статусы `принято` и `вернуть` — это делает только ревьюер.
3. Ревьюер проверяет задачу, когда владелец скажет «посмотри»: смотрит `git diff` по файлам страницы, сам прогоняет тесты, сверяет с «нельзя ломать» (§5.5). Затем ставит `принято` или `вернуть на доработку` и записывает замечания в журнал ниже.
4. Задача со статусом `вернуть на доработку` исполняется снова по замечаниям журнала; статус после этого снова `выполнено, ждёт ревью`.

Статусы: `не начато` → `выполнено, ждёт ревью` → `принято` | `вернуть на доработку`.

## Фаза 4 — утверждённое задание: карточка протокола как рабочее место с плеером (T28–T35)

Цель владельца: в карточке протокола удобно смотреть запись и **из одного места** переходить по темам, поручениям и репликам, не листая. Черновик исполнителя принят как основа; ниже — решения ревьюера по открытым вариантам и измеримые критерии. Правила прежние: область `pages/voice-video/*` и `src/api/voice*.js`, backend не менять, без коммитов, тест красный до правки, статус ставит исполнитель, приёмку — ревьюер, каждая задача — с замером «до/после» в браузере на 390×844 и 1440×900.

### Что проверил ревьюер перед постановкой (факты кода)

- **Плеер живёт только во вкладке «Текст разговора»** (`{tab === 1 && …}` в `VoiceMeetingDrawer.jsx`): при переходе на «Поручения» или «Участники» `<video>` размонтируется, воспроизведение останавливается, `seekMedia` недоступен. Поэтому «перематывать по поручениям» сейчас невозможно в принципе — это корневая причина, её чиним первой (T28).
- Плеер во вкладке уже `position: sticky`, но занимает до 280 px высоты; в сумме с шапкой, чипами тем и поиском текст разговора начинается глубоко (скрин владельца: видны 4 реплики).
- Темы — чипы, обрезанные на 28 символов (`t.title.slice(0, 28)`), в горизонтальном скролле; таймкоды только в tooltip; активная тема не подсвечивается.
- Поручения: `time` — **строка** «MM:SS» или «H:MM:SS» (`voice_server/pipeline.py`, `meeting_assignments`), а не число; `clip` — имя файла фрагмента. Сейчас клик по времени открывает отдельный диалог фрагмента.
- Темы: `start`/`end` — числа в секундах; реплики: `start`, `start_time_formatted`. Backend-контракты менять не нужно.
- Текст разговора рендерится порциями по 200 реплик (`transcriptLimit`) — переход к теме или поручению в позднюю часть записи упрётся в невыведенные реплики.
- Запись может отсутствовать (`has_media = false`, «Источник удалён») — тогда переходы должны работать по тексту без плеера.

### Решения ревьюера по вариантам из черновика

1. **Компоновка.** Не единый длинный скролл и не прежние четыре вкладки, а **рабочее место из двух колонок на ≥ md**: слева плеер (компактный, закреплён сверху колонки) и текст разговора со своей прокруткой; справа панель с вкладками «Темы · Поручения (N) · Участники (N без имени) · Файлы (N)». На < md: закреплённый компактный плеер сверху, под ним вкладки «Текст · Темы · Поручения · Ещё» (в «Ещё» — участники и файлы). Плеер **общий для всех вкладок** и не размонтируется.
2. **Диалог фрагмента поручения.** Если есть основная запись — клик по времени поручения перематывает основной плеер (1 клик), диалог фрагмента не открывается; «Скачать фрагмент» уходит в «⋮» поручения. Если основной записи нет — диалог фрагмента остаётся как единственный способ послушать.
3. **Поручения из текста.** Маркеры поручений на шкале времени под плеером (T30) обязательны; значок поручения у ближайшей реплики в тексте — желательный (Should), делать после обязательных пунктов.

- **R3 — поиск без отложенного ввода.** Каждая буква фильтрует все реплики и перерисовывает все строки с `<mark>`. Критерий T39 «на 5000 репликах ввод не тормозит (debounce)» **не выполнен — ревьюер принял T39 в «Ревью 11» без замера на большом объёме; ошибка ревью.**
- **R4 — плавная прокрутка за репликой (`scrollIntoView smooth`) на фоне заморозок** даёт рывки; при длинном переходе анимация идёт через весь список.

**Дизайн по снимкам владельца** (общая схема «плеер + текст + панель» верная, тёмная тема аккуратная; мешает следующее):

**Вывод.** Фазы 1–5 остаются принятыми, кроме критерия производительности T39 (переносится в T48). Открыта фаза 6 — сначала производительность (T46–T49), затем дизайн (T50–T54).
