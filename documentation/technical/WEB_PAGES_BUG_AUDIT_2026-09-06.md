## Находки по приоритету

### W1 — Почта: успешная отправка превращается в ошибку при сбое обновления списка

- Приоритет: высокий; возможна повторная отправка пользователем.
- Файл: `WEB-itinvent/frontend/src/components/mail/useMailQuickReply.js:45–94`.
- После успешного `sendMessage` ключ идемпотентности очищается на строке 77. Последующие `refreshList` и `refreshFolderSummary` находятся в том же `try`. Их ошибка возвращает `false` и показывается как ошибка отправки.
- Воспроизведение: отправка успешна, обновление списка отклонено; функция возвращает `false`. Следующая отправка получает новый ключ: `MAIL_SEND_OK_REFRESH_FAIL_RETURNS=false SEND_KEYS=1,2`.
- Последствие: письмо уже отправлено, но UI сообщает об ошибке. Если пользователь повторит тот же текст, новый ключ не защищает от дубля. Фактическая доставка дубля через SMTP не проверялась.
- Исправление: отделить подтверждённую отправку от обновления списков. После подтверждения вызывать успешное завершение независимо от refresh; ошибку обновления показывать отдельно. Добавить тест «send OK, refresh rejected».

### W2 — Инвентарь: поздняя загрузка оборудования применяется к расходникам

- Приоритет: высокий; неверный состав отображаемых данных.
- Файл: `WEB-itinvent/frontend/src/pages/database/useDatabaseEquipmentData.js:210–310`, переключение режима — около строки 345.
- `loadMoreEquipmentPages` после ожидания добавляет результат в `allEquipment` без проверки, что режим и область данных остались прежними. Начальная загрузка `fetchAllEquipment` также применяет результат без такой проверки.
- Воспроизведение: задержать страницу оборудования, переключиться на расходники, затем завершить старый запрос. Вывод harness: `CONSUMABLE_MODE_GROUPS=consumables,equipment`.
- Подтверждено применение устаревшего результата к общему состоянию. Изменение записей БД или утечка между базами этим тестом не доказаны.
- Исправление: идентификатор поколения загрузки с учётом режима и выбранной базы; проверять его перед изменением списка, счётчиков, курсора и loading/error. Старый ответ при необходимости сохранять только в кэш исходной области. Проверить обратный порядок ответов при переключении режимов и базы.

### W3 — Почта: разные быстрые ответы используют один ключ после ошибки

- Приоритет: средний; повторная отправка может блокироваться конфликтом.
- Файл: `WEB-itinvent/frontend/src/components/mail/useMailQuickReply.js:43–76`.
- Единственный `idempotencyKeyRef` сохраняется после ошибки и не привязан к письму, телу, ящику или режиму ответа.
- Воспроизведение: неудачная попытка ответа A, затем ответ B через тот же экземпляр hook. Вывод: `DIFFERENT_REPLY_IDS=A,B KEYS=3,3`.
- Backend намеренно сравнивает hash запроса: `WEB-itinvent/backend/services/mail_send_idempotency.py:334–346`, несовпадение даёт `action="conflict"`. Если первая попытка уже зарезервировала ключ, изменённый запрос будет конфликтовать. Ошибка до резервирования ключа не обязательно вызывает конфликт.
- Исправление: хранить ключ вместе с отпечатком логического черновика; одинаковый повтор сохраняет ключ, другое письмо/содержимое получает новый. Серверную защиту от изменения payload не ослаблять.

### W4 — Лента: старый поиск перезаписывает новый

- Приоритет: средний.
- Файл: `WEB-itinvent/frontend/src/pages/Feed.jsx:129–186`.
- `loadPage` безусловно применяет ответ через `setItems` на строке 156. Debounce отменяет таймер, но не уже отправленный запрос. Проверки поколения запроса нет.
- Воспроизведение: запрос старого поиска A, запрос нового B; ответ B приходит первым, A последним. Вывод: `FEED_QUERY_NEW_SHOWS=old`.
- Последствие: строка поиска/фильтр и показанные публикации расходятся; старый ответ также может повлиять на метаданные списка.
- Исправление: поколение, связанное с query/filter/category/tag; отклонять устаревшие reset и pagination responses. Проверить обратный порядок ответов и пересечение догрузки со сменой фильтра.

### W5 — Задачи: завершение удаления A закрывает открытую позже B

- Приоритет: средний; потеря текущего контекста карточки.
- Файл: `WEB-itinvent/frontend/src/pages/tasks/hooks/useTaskWorkflowActions.js:149–165`.
- После `await deleteTask` условие использует захваченный `selectedTaskId`; `closeTaskDetails` закрывает уже текущую карточку.
- Воспроизведение: подтвердить удаление A, пока запрос выполняется открыть B, завершить удаление A. Вывод: `DELETE_TASK_A_CLOSES=B`.
- Исправление: перед закрытием проверить актуальную выбранную задачу/поколение карточки. Обновление списка после удаления сохранить. Подтверждение удаления является намеренной защитой и должно остаться.
