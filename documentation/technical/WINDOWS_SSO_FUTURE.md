# HUB Desktop: Windows-вход и постоянная сессия

Статус: утверждённое направление для discovery `0.3.0`; реализация требует отдельного вертикального среза и тестового пилота.

## Исходные условия

- часть рабочих станций входит в домен `zsgp.corp`, часть работает вне домена;
- сервер HUB не входит в домен и не может самостоятельно проверить Kerberos/Windows identity;
- Windows-логин доменного пользователя совпадает с `username` уже существующего профиля HUB;
- создавать HUB-пользователя автоматически по имени Windows нельзя;
- браузерная версия и недоменные компьютеры сохраняют обычный вход, passkey и текущую session policy.

`Environment.UserName`, `windowsUsername` из Desktop bridge и результат локальной проверки домена не являются доказательством личности. Они пригодны только для заполнения логина и выбора интерфейсного сценария.

## Решение для текущей инфраструктуры

Для `0.3.0` реализуется не Kerberos SSO, а **привязанная к Windows-профилю повторная аутентификация Desktop**:

1. Пользователь один раз входит в HUB обычным способом, включая действующую 2FA policy.
2. Desktop проверяет локально, что компьютер присоединён к `zsgp.corp`, а имя текущей Windows-учётной записи после нормализации совпадает с `username` вошедшего пользователя HUB.
3. По явному согласию пользователя Desktop создаёт асимметричный ключ для текущего Windows-профиля. Предпочтителен TPM-backed Microsoft Platform Crypto Provider; при отсутствии TPM допускается Microsoft Software Key Storage Provider с неэкспортируемым ключом и явной диагностикой уровня защиты.
4. Backend регистрирует публичный ключ только внутри уже аутентифицированной HUB-сессии. Привязка относится к конкретному `user_id`, Windows SID и устройству; имя пользователя хранится только как диагностический атрибут.
5. Пока WebView2 cookie/refresh-сессия действительна, клиент использует существующий поток без изменений.
6. После истечения сессии backend выдаёт короткоживущий одноразовый challenge. Desktop подписывает его локальным ключом, backend проверяет подпись и выпускает обычную HUB-сессию.
7. Если ключ недоступен, устройство отвязано, пользователь отключён, имя Windows изменилось или компьютер больше не состоит в `zsgp.corp`, показывается обычная форма входа.

Так пользователь обычно не вводит пароль повторно, но на сервере нет бессрочной неотзываемой сессии.

## Почему не Kerberos сейчас

Kerberos/Negotiate требует доверенной точки, которая действительно проверяет доменную учётную запись. Сервер HUB вне домена такой точкой не является. Нельзя принимать от Desktop или общего reverse proxy строки `DOMAIN\\user`, `REMOTE_USER` либо `X-Forwarded-User`.

Настоящий Kerberos SSO остаётся будущим вариантом, если появится доменный identity gateway. Он должен проверять Windows Authentication и выдавать FastAPI короткоживущий, подписанный и одноразовый assertion с точными `issuer`, `audience`, `domain`, `subject`, `iat`, `exp` и `jti`. Общий сайт включать в Windows Authentication нельзя: это сломает смешанный парк и может вызвать системные запросы логина на недоменных ПК.

## Контракт привязки

Предлагаемый отдельный API, не являющийся частью Desktop bridge v1:

- `POST /api/v1/auth/desktop-device/register/options` — только с активной HUB-сессией;
- `POST /api/v1/auth/desktop-device/register/verify` — сохраняет публичный ключ и привязку;
- `POST /api/v1/auth/desktop-device/auth/options` — выдаёт одноразовый challenge по неприватному device id;
- `POST /api/v1/auth/desktop-device/auth/verify` — проверяет подпись и создаёт обычную HUB-сессию;
- `GET /api/v1/auth/desktop-devices` и `DELETE /api/v1/auth/desktop-devices/{id}` — просмотр и отзыв.

Challenge живёт не более 60 секунд, извлекается атомарно один раз и связывается с origin, device id, целью операции и версией протокола. Ответ подписывает canonical payload, а не произвольную строку. Сессионные cookies остаются `HttpOnly`, `Secure` и `SameSite`; C# не читает и не хранит access/refresh token.

## Сопоставление профиля

- нормализовать `zsgp.corp\\Ivanov`, `ZSGP\\Ivanov` и `ivanov@zsgp.corp` до `ivanov` только для проверки возможности регистрации;
- сопоставление регистронезависимое, но должно давать ровно один активный HUB-профиль;
- фактическая привязка создаётся к `user_id` текущей подтверждённой HUB-сессии;
- при несовпадении Windows login и HUB username автоматическая привязка запрещена;
- переименование, блокировка или удаление пользователя отзывает либо делает недействительными все его Desktop-привязки;
- автосоздание и автоматическое объединение профилей запрещены.

## Session policy

- бессрочные сессии запрещены;
- обычные access/refresh TTL и лимит параллельных сессий сохраняются;
- успешная подпись device challenge создаёт или переиспользует обычную серверную сессию через существующий `session_service`;
- logout отзывает текущую сессию; действие «Выйти и отвязать этот компьютер» дополнительно отзывает device key;
- администратор и пользователь могут отозвать привязку с другого устройства;
- inactive user, password/security reset и принудительное завершение сессий должны поддерживать массовый отзыв Desktop-привязок согласно принятой auth policy;
- 2FA не считается автоматически выполненной одним фактом членства ПК в домене. Решение, считать ли зарегистрированный device key вторым фактором, должно совпасть с существующей trusted-device policy.

## Локальная Windows-часть

- статус присоединения и имя домена получать системным `NetGetJoinInformation`, ожидая `NetSetupDomainName` и точное имя `zsgp.corp`;
- Windows SID получать из текущего `WindowsIdentity`, не передавать его через произвольный JavaScript payload;
- закрытый ключ создавать и открывать только в текущем Windows-профиле;
- private key никогда не экспортировать, не помещать в WebView2 profile, реестр в открытом виде, логи, support bundle или installer;
- при доступном TPM предпочитать hardware-backed KSP; software fallback явно отражать в диагностике;
- удаление WebView2 profile не должно удалять ключ без отдельного подтверждения, но должно приводить к обычному повторному входу, если browser binding утерян.

Microsoft документирует `NetGetJoinInformation` как системный способ получить состояние domain/workgroup join, CNG KSP — как хранилище асимметричных ключей, а Platform Crypto Provider — как TPM-backed provider. Это подтверждает техническую реализуемость локальной части без включения HUB-сервера в домен.

## Go/no-go для кода

Начинать реализацию можно только после того, как утверждены:

- срок жизни и схема одноразового challenge;
- canonical signed payload и алгоритм (ECDSA P-256/SHA-256 предпочтителен);
- PostgreSQL-модель привязки, уникальности и атомарной защиты от replay;
- правила отзыва при logout, security reset, inactive user и удалении устройства;
- software-KSP fallback и поведение без TPM;
- UX первого согласия, обычного fallback-входа и удалённого отзыва;
- интеграционные тесты на replay, подмену user/device/domain и потерю ключа.

До выполнения этих условий текущий безопасный результат остаётся прежним: постоянный WebView2 profile, silent refresh и подсказка Windows username.
