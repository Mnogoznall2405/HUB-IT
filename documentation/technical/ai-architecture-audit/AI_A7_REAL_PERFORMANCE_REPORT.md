## 4. JEV

- Модель `typesafe/jev-1.13-20260917`, `MODE=group`, latency p50 ≈ 0.96 с.
- **Кэш эффективно мёртв**: 58/58 miss. Проверено дублирующей отправкой идентичного текста — тоже miss. Причина в коде: `_jev_routing_cache_key` (service.py:1337) включает **4 последних сообщения диалога** — ключ меняется после каждого сообщения, попадание возможно только при retry/дубликате с неизменным контекстом. Органический hit-rate ≈ 0%.
- Точность маршрутизации (разметка 50 помеченных запусков): **41/50 (82%)**.
  - `act` ожидался → 10/10.
  - `read` → 15/21; 6 промахов — это `intent=none` ('-'), и все они на группы инструментов, **недоступные тестовому пользователю** (equipment/inventory не входит в `available=['chat','directory','files','kb','office','self']`). Т.е. JEV корректно не маршрутизировал несуществующие инструменты; фактическая точность на доступных классах выше.
  - `chat` → 16/19: 3 мягких overfire в `act` («план рабочего дня» → `office.workday.summary` — спорно-оправдано; «название рассылки», «поздравление» → act с tools=[] — лишний режим без вызова инструментов, почти безвредно, но добавляет round-trip).
  - `edge` → смешанно, как ожидалось.
- Запрещённых групп: 0. Неверных tool-вызовов с ошибкой: 0. ACT-запросы оформлялись как черновики/карточки либо прямые ответы, необратимых действий не было.
- Замеченный побочный эффект **sticky-групп**: после первого `office` маршрута `sticky=['office','self']` тянется в следующие решения — потенциальный источник bias.

## 7. Причины задержек (по фактам)

1. **Второй LLM-раунд** после результата инструмента: +6.4…13.3 с. Дважды при двух раундах. → 16→32→47 с ступени.
2. **ctx_summary ~8 с**: LLM-саммаризация контекста срабатывает на выросшем диалоге и стоит дороже самого первого ответа модели.
3. **Неконтролируемый рост prompt_tokens** (до 72k): удлиняет каждый LLM-вызов и биллинг.
4. **JEV ~1 с** на каждый run при 0% cache-hit в органическом потоке.
5. chat→act overfire добавляет лишний инструмент+followup-раунд там, где можно было ответить текстом.

## 8. Оптимизации по ожидаемому эффекту

| # | Оптимизация | Ожидаемый эффект | Уверенность |
|---|---|---|---|
| 1 | Устранить/распараллелить второй LLM-раунд: для одиночных READ-инструментов синтезировать ответ без followup-вызова (template/inline) или стримить | **−6…13 с** на ~45% запросов; p50 16→~9 с | Высокая (прямая мерка) |
| 2 | Ограничить контекст: запускать ctx_summary раньше/реже, жёсткий бюджет токенов на историю (например ≤8k) | **−3…8 с** на поздних сообщениях диалога; −50-70% токенов | Высокая |
| 3 | Починить/переосмыслить JEV-кэш (ключ без истории + отдельный ключ с контекстом) либо пропускать JEV при strong-keyword сигналах | −0.7…1.5 с на ~70% запросов | Средняя (кэш-хиты органически редки; безопаснее — пороги/skip) |
| 4 | Поднять порог act для косвенных формулировок (overfire: «название рассылки» → act) | −1 раунд на ~6% запросов | Средняя |
| 5 | Мониторить sticky-groups bias | качество маршрутизации | Низкая-средняя |

## 9. Что не измерено / ограничения

- **CHAT без JEV**: выключение `AI_JEV_ROUTING` в проде запрещено; изолированный контур не поднимался (нет отдельного стенда). Оценка выигрыша — через `tool_routing` стадию (~1 с).
- WS-TTFT: измерено через HTTP-poll; реальный первый токен по сокету не замерен.
- Equipment/inventory-инструменты недоступны `test1` → read-сценарии по технике оценены частично.
- Нагрузка >1 и поведение очереди под конкуренцией — не проверялось (запрет стресс-теста).
- ACT commit-path (реальная отправка письма) — не выполнялась, как и требовалось.
- Выборка 58 < 500 — перцентили ориентировочные; для p99 нужен повторный прогон.
- Reply-детект ±0.8 с (шаг опроса).

## 10. Выводы

- Пользователь ждёт **p50 ≈ 16 с, p95 ≈ 47 с**; отправка и очередь почти мгновенные — всё время уходит в LLM-раунды и сбор контекста.
- JEV точен на доступных классах (~82-90% с поправкой на недоступные группы), стоит ~1 с, кэш не работает по назначению.
- Топ-3 рычага: меньше LLM-раундов, меньше контекста, дешевле роутинг.
