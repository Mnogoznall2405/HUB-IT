## 2. Эксперимент качества поиска KB (измерено — только Python-fallback)

**Область действия результатов — важно.** Скрипт `experiments/kb_search_quality.py` прогоняет реальный `AiKbRetrievalService.retrieve()` на одноразовой SQLite с 13 синтетическими статьями. На SQLite активен **Python-fallback-скоринг** (`retrieval.py:327-371`: подсчёт вхождений подстрок токенов ≥3 символов, без порога релевантности). **Production PostgreSQL FTS-путь (`retrieval_interface.py`, `to_tsvector`/`websearch_to_tsquery`) в этом эксперименте не измерялся** — это другой алгоритм с другим профилем ошибок. Выводы о прод-пути в отчётах основаны на статическом анализе кода, а не на измерении; переносить приведённые цифры на production recall нельзя ни в большую, ни в меньшую сторону.

Набор: 19 запросов — 17 «позитивных» (ожидаемый документ есть в корпусе) по классам paraphrase/colloquial/exact/wordform/typo/attachment/filename/mixed_lang/exact_id/department/ё-варианты и 4 «негативных» (релевантного документа в корпусе нет).

| Метрика | Результат |
|---|---|
| Hit@1 | **12/17** (71%) |
| Hit@3 | **15/17** (88%) |
| Miss | 2/17 — разговорная «учётка» («заблокировалась учётка что делать» → 0 результатов), опечатка «прентер» («подключить прентер» → 0 результатов) |
| Негативные запросы | **ложные срабатывания 3/4** — выдача возвращает документы при отсутствии релевантного: «инструкция по установке photoshop» → статья про Wi-Fi (совпала подстрока «инструкция»), «замена термопасты на сервере» → «Замена картриджа» (подстрока «замена»), «подключение гарнитуры к телефону» → принтеры и 1С (подстрока «подключение»). Пустой результат только для «ремонт кофемашины на кухне» — ни одной общей подстроки |

Разбивка по классам (hit@1 / hit@3-only / miss):

| Класс | 1 / 3 / miss | Комментарий |
|---|---|---|
| exact, exact_id, filename, attachment_name, department, ye_variant | 7/0/0 суммарно | точные формулировки и идентификаторы — сильная сторона подстрокового скорера |
| wordform | 1/1/0 | «заменить картридж в принтере» попал в top-3, но не top-1 (top-1 заняла заявка на закупку) |
| paraphrase | 1/1/0 | «не пускает в домен пароль правильный» — top-3; главный кейс аудита см. ниже |
| mixed_lang | 1/1/0 | |
| typo | 1/0/1 | «катриджа» найдена (подстрока «атридж»), «прентер» — нет |
| colloquial | 0/0/1 | «учётка» — разговорное слово, в документе нет такой подстроки |

Отдельно кейс из задания: **«не могу войти в компьютер после отпуска» → «Порядок разблокировки доменной учётной записи»**.
- Python-fallback (измерено): запрос вернул `['d2', 'd1', 'd5']` — нужный документ **top-2**, не top-1 (top-1 — «Сброс пароля», из-за частотных совпадений токенов «войти/пароль»).
- PG FTS-путь (НЕ измерено, статический анализ): `websearch_to_tsquery` требует все лексемы через AND; после отсечения стоп-слов запрос сводится к `могу & войти & компьютер & отпуска` — целевой документ их не содержит → по правилам FTS результат был бы пустым. Это вывод по семантике websearch_to_tsquery, а не измерение; точный план и выдача на проде не проверялись.

Что эксперимент доказывает: (1) разговорные слова и опечатки вне словаря документа теряются; (2) у скорера нет порога релевантности — 3/4 посторонних запросов получают правдоподобную на вид выдачу, что опаснее промаха: модель получает нерелевантный контекст как «факты»; (3) точные идентификаторы и формулировки работают хорошо — гибридная схема должна сохранить это плечо.

## 3. Производительность и стоимость (оценка по коду — НЕ измерено end-to-end)

Измерений на проде не проводилось (production read-only). Ниже — оценки, выведенные из кода; это гипотезы, а не замеры:

| Величина | Оценка | Основание |
|---|---|---|
| LLM-вызовов на простой вопрос | 1 (+1 memory-planner при write-intent) | `service.py` цикл; `memory.py:286-333` |

| Латентность retrieve (PG-путь) | seq scan вероятен из-за расхождения выражения запроса с индексом (P1-1; план не проверен EXPLAIN) | `retrieval_interface.py` + миграция |

## 5. Что НЕ измерено (честный список)

- Время до первого токена и полное время ответа на проде — NOT RUN (нет доступа к живому контуру; stage-тайминги пишутся в лог, но не агрегируются в метрики).
- Поведение при параллельной нагрузке (>4 одновременных run) — NOT RUN; гонка двух run на один диалог не воспроизводилась.
- Фактическая остановка воркера из-за зависшего инструмента — NOT RUN (риск выведен из кода статически).
- Сравнение Docling/Unstructured vs текущих экстракторов — NOT RUN (нет эталонного набора сканов; установка зависимостей вне scope).
- Векторный прототип vs FTS — NOT RUN (нет embeddings в зависимостях).
- **EXPLAIN плана FTS-запроса на проде — NOT RUN** (production read-only). Вывод о неиспользовании GIN-индекса — статический анализ: PostgreSQL сматчивает индекс только по структурно идентичному выражению, `concat_ws(title, content)` ≠ `COALESCE(title,'') || ' ' || COALESCE(content,'')`; фактический план не наблюдался.
- Успешный эксплойт prompt injection end-to-end — NOT RUN (подтверждена только поверхность атаки по коду, см. GAPS P0-2).

## 6. Выводы по измеренному

1. Тестовая база покрывает права, ретраи, память, роутинг, экстракторы и runtime — 191 зелёный тест. Проблемы аудита лежат в зонах, которые тесты не закрывают: план запроса на проде, порядок ACL-фильтра, PII-путь, инфраструктурные таймауты, prompt-injection.
2. Поиск KB — главное измеренное слабое место **на Python-fallback бэкенде**: промахи на разговорных словах/опечатках + ложные срабатывания без порога релевантности. Утверждения о PG-пути — только статический анализ (строгий AND + отсутствие стемминга предполагают не лучший профиль recall, но это не замерено).
3. Бенчмарк-инфраструктура существует (`eval_questions.json`, 3 скрипта), но не автоматизирована и требует внешнего провайдера — дешёвая точка роста: локальный провайдер (Ollama) + CI.
