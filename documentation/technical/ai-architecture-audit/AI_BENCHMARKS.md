## 2. Эксперимент качества поиска KB (измерено)

Скрипт: `documentation/technical/ai-architecture-audit/experiments/kb_search_quality.py`.
Метод: 12 синтетических статей в изолированной SQLite (реальный `AiKbRetrievalService`, python-fallback-скоринг — тот же код, что используется при недоступности PG и в тестах). 15 запросов: разговорные, синонимы, словоформы, опечатки, инвентарные номера, подразделения, смешанный RU/EN.

| Метрика | Результат |
|---|---|
| Hit@1 | **10/15** (67%) |
| Hit@3 | **13/15** (87%) |
| Промахи | «заблокировали учётку…» (разговорное «учётка» — нет слова в документе), «прентер не печатает» (опечатка) |

Важные оговорки:
- Python-скорер мягче PG-пути: подсчёт подстрок прощает часть словоформ («войти»↔«вход» совпадает подстрокой «вхо»? — нет, но частичные попадания считаются). На проде активен PG-путь с `websearch_to_tsquery` = строгий AND: запрос проигрывает, если хоть одна лексема не совпала. **Реальный recall на проде ниже измеренного.**
- Классический пример аудита («не могу войти в компьютер после отпуска» → «Порядок разблокировки доменной учётной записи»): на PG-пути совпадения почти нет (стоп-слова «не/в/после» отбрасываются `websearch`, остаются `могу & войти & компьютер & отпуска` — документ их не содержит → 0 результатов). На Python-пути — только по слову «компьютер» при совпадении подстроки. **Семантический разрыв подтверждён экспериментом и кодом.**

## 5. Что НЕ измерено (честный список)

- Время до первого токена и полное время ответа на проде — NOT RUN (нет доступа к живому контуру, метрик в коде нет: stage-тайминги пишутся только в лог, не агрегируются).
- Поведение при параллельной нагрузке (>4 одновременных run) — NOT RUN.
- Сравнение Docling/Unstructured vs текущих экстракторов на одинаковых документах — NOT RUN (нет эталонного набора сканов в репозитории; ставить новые зависимости запрещено правилами аудита).
- Векторный прототип vs FTS — NOT RUN (нет embeddings-модели в зависимостях; установка пакетов вне scope).
- EXPLAIN плана FTS-запроса на проде — NOT RUN (production read-only; вывод о неиспользовании индекса сделан статическим анализом выражений — PG сматчивает индекс только по структурно идентичному выражению, `concat_ws` ≠ `||`).

## 6. Выводы по измеренному

1. Тестовая база зрелая: ~189 проверок покрывают права, ретраи, память, роутинг, экстракторы, runtime — и всё зелёное. Проблемы аудита лежат в зонах, которые тесты не закрывают (PG-индекс, ACL-порядок, PII, инфраструктурные таймауты).
2. Поиск KB — главное измеренное слабое место: 33% промахов Hit@1 уже на чистом синтетическом корпусе в мягком бэкенде.
3. Бенчмарк-инфраструктура существует (`eval_questions.json`, 3 скрипта), но не автоматизирована и требует внешнего провайдера — дешёвая точка роста: локальный провайдер (Ollama) + CI.
