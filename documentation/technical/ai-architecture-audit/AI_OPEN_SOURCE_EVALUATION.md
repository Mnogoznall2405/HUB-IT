## Детальные разборы запрошенных инструментов

### 1. pgvector — ВНЕДРЯТЬ (этап B)

**Что есть:** векторного поиска нет нигде (`grep embedding` по backend/shared — 0). FTS `'simple'`+AND доказанно не закрывает разговорные/перефразированные запросы (эксперимент: Hit@1 67% даже на мягком скорере; на PG-пути хуже).
**Что даст:** гибрид `FTS top-50 + vector top-50 → RRF/реранк → top-5` убирает семантический разрыв. `ai_kb_chunks` — идеальная точка внедрения: колонка `embedding vector(1024)`, HNSW-индекс, ACL-фильтр перенести в SQL **до** limit (заодно чинит P1-3).
**Совместимость:** PG 16.15 — поддерживается (pgvector 0.8.x, PG 13–18). Embeddings: локально через fastembed (ONNX, CPU, без новых сервисов) или через уже работающий Ollama (`nomic-embed-text`/`bge-m3`). RouterAI embeddings endpoint не проверялся — NOT RUN.
**Стоимость:** диск ~1024×4B×N чанков (10k чанков ≈ 40 MB + индекс); переиндексация — фоновая джоба.
**Условие:** только после quick-фиксов этапа A (`russian`-конфиг, индекс, ACL). Если после них recall в норме — pgvector можно отложить; решение по eval-метрикам, не по ощущениям.

### 2. Promptfoo — ВНЕДРЯТЬ

**Что есть:** 189+ unit/e2e pytest, 53 eval-вопроса с `expected_groups`, но ручной раннер и нет CI-регрессии качества, нет injection-набора.
**Что даст:** declarative eval-наборы (yaml) поверх HTTP-провайдера → прогон против локального endpoint бэкенда или Ollama; assertions: `contains`, `llm-rubric` (RU-рубрика через свой шлюз), `tool-call` матчинг; `promptfoo redteam` — готовые injection/PII-плагины (с осторожностью: redteam генерирует через внешний LLM — гонять только на синтетике/локальной модели).
**Лицензия MIT**, Node (npx, без установки). Интеграция: nightly-джоб, не блокирующий PR.
**Не подменяет** pytest — покрывает именно качественную регрессию, которой сейчас нет.

### 3. Langfuse — ОТЛОЖИТЬ

**Что есть:** `ai_bot_runs` (status/stage/error/request/result/tool_traces/usage), stage-тайминги в логах, tool-аудит в registry. Дыры: нет корреляции HTTP↔worker (request_id), нет per-call usage, нет результатов tool-вызовов, нет алертов.
**Почему отложить:** self-hosted Langfuse требует PG+ClickHouse+Redis+S3(+worker) — прямое нарушение инварианта «не добавлять обязательные сервисы без инструкции». Облако — утечка PII наружу.
**Что делать вместо:** дешёвые доработки своей наблюдаемости (request_id сквозной, per-call usage в usage_json, эндпоинт run-detail, алерт по running>10мин). Если понадобятся датасеты/плейграунд — OpenTelemetry GenAI + Phoenix (1 контейнер, опционально) как компромисс.

### 4. FastMCP — НЕ НУЖНО

**Сравнение:** свой `AiToolRegistry` уже делает всё, что дал бы MCP-сервер: pydantic-схемы→JSON-schema, фильтрация по правам в 2 точки, аудит-записи, draft-confirm — причём confirm-модель глубже любого MCP-стандарта (атомарный claim, идемпотентность, повтор прав). MCP решает задачу «подключить внешние сторонние инструменты» — таких потребителей сейчас нет.
**Риски миграции:** переписать 100 инструментов на чужой протокол = регрессии без выигрыша; MCP-серверы добавляют network-attack-surface (tool poisoning известная проблема экосистемы).
**Когда пересмотреть:** если появится реальный внешний MCP-клиент (например, дать ассистента в IDE разработчикам) — тогда вариант B: тонкий MCP-адаптер *поверх* существующего реестра, без миграции.

### 5. Docling — ОТЛОЖИТЬ

**Что есть:** два контура — лёгкие экстракторы (15+ форматов, без OCR, vision-LLM ≤3 стр.) и `shared/doc_convert` (structured-vision, всегда force_vision, ≤10 стр.).
**Что даст:** качественный layout/table parsing сканов локально (модели layout+tableformer, опционально EasyOCR/RapidOCR для RU).
**Почему отложить:** тянет PyTorch ~2 GB, ~10–15 с/страницу на CPU для сканов, RU-OCR требует отдельной настройки; ниша — только сложные сканы. Дешевле: RapidOCR (ONNX, Apache-2.0, RU из коробки) как первый локальный OCR-проход + дешёвый `page_has_usable_text`-гейт (уже есть в `shared/doc_convert/render.py:153-183`).
**Когда пересмотреть:** реальный поток сканированных актов/накладных с таблицами — тогда пилот Docling как preprocessor в `doc_convert`, не замена.

### 6. Mem0 — НЕ НУЖНО

**Сравнение:** текущая память сильнее в критичных для корпоративной системы местах: verbatim-доказательства фактов (цитата-источник обязательна), revision-CAS, replay-protection, явные update/forget-операции, серверная изоляция по user_id — всё подтверждено E2E-тестами. У Mem0 этого контроля нет: LLM сам решает add/update/delete без evidence-привязки.
**Что дал бы Mem0:** векторный recall фактов (сейчас кандидаты ограничены 200 новейшими — P2-12). Но pgvector-этап B решает recall дешевле и заодно чинит KB-поиск — одна инфраструктура вместо двух.
**Минусы:** +LLM-вызовы на каждое сообщение (и так есть planner), обход `shared/llm`-инварианта (у Mem0 свои клиенты), известные multi-user-проблемы изоляции.
**Вывод:** оставить свою память; точечно улучшить: векторный recall поверх `ai_user_memories`, TTL/retention-политика, чистка при деактивации пользователя.

## Итоговые вердикты

- **ВНЕДРЯТЬ:** fastembed+pgvector (гибридный поиск, этап B) · bge-reranker-v2-m3 (реранк, этап B) · RapidOCR (локальный OCR) · Promptfoo (eval-регрессия) · pg_trgm (опечатки, сразу).
- **ОТЛОЖИТЬ:** Langfuse, Docling, Phoenix/OTel, Ragas, LiteLLM, DSPy, NeMo, Instructor, sentence-transformers, ParadeDB, vLLM — все «после подтверждающей потребности».
- **НЕ НУЖНО:** FastMCP, Mem0, LangGraph, Outlines, LLMLingua, Unstructured, GPTCache, pg_textsearch.

**Главный ответ:** реальные скачки дают не «модные» агент-фреймворки, а (1) починка собственного FTS — бесплатно, (2) связка fastembed+pgvector+reranker — один фоновый компонент без новых сервисов, (3) RapidOCR — локальный OCR вместо внешних vision-вызовов, (4) Promptfoo — дисциплина качества. Langfuse/MCP/Mem0/LangGraph в текущей системе заменяют уже работающие части на чужие без выигрыша.
