## DVOICE-01 — отмена перезаписывает уже завершённое задание

1. `POST /api/v1/voice/jobs/{id}/cancel` читает `queued` в `app.py:414`.
2. До записи отмены worker успевает провести `queued → processing → done`.
3. Реальный `store.request_cancel` корректно возвращает `False`: его UPDATE разрешён только для `queued/processing` (`store.py:209`).
4. Роутер игнорирует результат и проверяет старый словарь `job`. По старому `queued` он вызывает безусловный `update_job(..., status="cancelled")` (`app.py:419–420`). В `store.py:158` UPDATE ограничен только ID.

Воспроизведение выполнено через настоящий FastAPI `TestClient` и SQLite с логической схемой `voice`. Interleaving задан обёрткой в точке `request_cancel`: SQL переходов и финального UPDATE — реальный код. PostgreSQL `claim_next_job` и ML-подпроцесс не запускались.

**Факт:** HTTP 200, ответ `cancel_requested`; перед отменой `done`, `cancel_update_accepted=False`; после запроса `status=cancelled`, `result.returncode=0`, `cancel_requested=0`.

Это самостоятельная гонка состояния, отличная от DINT-01 с блокирующим чтением stdout. Вариант, где worker ещё выполняется, требует отдельного теста: нельзя по этому воспроизведению заявлять, что реальный процесс уже остановлен или удалён.

**Минимальное исправление:** атомарный переход queued→cancelled с условием текущего статуса; для processing — только запрос отмены. При проигранном переходе вернуть фактический terminal state/конфликт, не перезаписывая его. **Приёмка:** cancel/claim/finish в обоих порядках; завершённый результат не меняется, final state совпадает с реальным исходом выполнения.

## DVOICE-02 — удаление проекта игнорирует активное вспомогательное задание

`labeling.delete_project` проверяет только `project.job_id` (`labeling.py:662–664`). Variant/enroll/calibration/faces операции сохраняются отдельно в `aux_job_id` через `_enqueue_aux_job` (`:719–727`). Затем delete переносит весь каталог проекта в корзину и удаляет строку проекта (`:665–674`), не проверяя и не отменяя aux job.

Через реальные `label_store` и `_enqueue_aux_job` созданы готовая разметка, завершённый основной draft и aux variant. Реальный HTTP DELETE проверен отдельно при **queued** и **processing** aux. Настоящий ML worker не запускался: состояние processing задано тестовыми данными.

**Оба результата:** HTTP 200; строки проекта больше нет; aux job остаётся в прежнем активном состоянии; его `stored_path` больше не существует. Синтетические bytes найдены неизменными в `.trash` — безвозвратная потеря оригинала этим сценарием не доказана. Однако ожидающее задание гарантированно лишается исходного пути; выполняющееся теряет согласованный каталог/метаданные, а запись результата в удалённый проект может ничего не сохранить.

**Минимальное исправление:** запрещать удаление при любых активных заданиях проекта, включая aux; проверку согласовать с конкурентным enqueue. Не считать достаточной только проверку поля последнего aux, если допускаются несколько конкурирующих enqueue. **Приёмка:** queued/processing variant, enroll, calibration и faces → HTTP 409, строка и файлы сохранены; после подтверждённого terminal state удаление успешно; отдельный delete/enqueue race.

## DVOICE-03 — архиватор не продвигается по накопленной очереди

`list_done_jobs` всегда выбирает самые старые `done` по `finished_at`, максимум 20 строк, без курсора (`store.py:243–254`). `archive_cycle` всегда начинает с этой выборки и прекращает цикл после пяти исходов `archived/expired/dry/already` (`archiver.py:155–167`). Состояние завершённой архивной обработки в выборке не исключается.

Воспроизведены две границы одним и тем же реальным `archive_cycle` и SQL:

- **Пять старых expired-заданий без оставшихся файлов и шестой свежий источник.** `_archive_one` всё равно возвращает `expired`, даже когда удалять нечего (`:82–99`). Те же пять строк каждый раз расходуют весь batch. Свежий job входит в SQL-выборку, но до него не доходит цикл.
- **Двадцать недавних done-заданий без hot-файла и 21-й свежий источник.** Старые строки возвращают `skip`, но 21-я строка не попадает в неизменное окно SQL.

**Факт:** по три цикла на каждый сценарий; новый hot-файл остаётся, warm не создаётся; `copied=0`, `errors=0` во всех циклах. Ожидания между элементами отключены только в harness. Реального замера production throughput/p95 не было.

**Минимальное исправление:** курсор/согласованный выбор кандидатов отдельно для переноса и TTL; уже очищенные записи не должны постоянно занимать начало batch. Простого увеличения LIMIT недостаточно. **Приёмка:** 25+ заданий разного возраста, archived/missing/expired и несколько последовательных циклов; все доступные кандидаты достигаются, TTL не блокируется очищенным префиксом, ограничение batch сохраняется. Production cleanup этим аудитом не разрешён.

## DVOICE-04 — сбой отметки архивирования выводит warm-файл из TTL

После копирования `_archive_one` сначала удаляет hot (`archiver.py:132`), затем пишет `archive_path` через `mark_archived` (`:134`). Ошибка отметки логируется, но возвращается `archived` и увеличивается `copied`. Следующий проход ищет warm только через hot filename или сохранённый `archive_path` (`:74–80`). Если hot уже нет, а UPDATE не состоялся, оба пути отсутствуют.

Fault injection заменяет **только** `store.mark_archived` на исключение. Копирование, unlink, последующие чтения строки и повторные `_archive_one` — реальные. До TTL повторный вызов возвращает `skip`. Для проверки истечения TTL только у временной строки сдвинут `finished_at` на восемь дней назад.

**Факт:** первоначальный исход `archived`, `errors=1`, `archive_path=NULL`; hot отсутствует, warm содержит исходные bytes. После TTL функция возвращает `expired`, `expired_deleted=0`; warm остаётся и по-прежнему находится `pipeline.find_source_media`. Сравнены bytes/SHA-256 синтетического файла.

Это отдельный дефект восстановления после частичного commit, а не повтор DVOICE-03: воспроизводится прямым `_archive_one` на одном job, независимо от размера/обхода очереди.

**Минимальное исправление:** не удалять последнюю hot-привязку до надёжной отметки; предусмотреть recovery копии после crash/ошибки UPDATE и идемпотентную сверку существующего warm-файла. **Приёмка:** ошибка/остановка между copy, marker и unlink; повтор восстанавливает согласованную запись; по наступлении TTL источник удаляется по принятой политике без удаления чужих файлов. Production retention требует отдельного разрешения.

Первый запуск harness завершился до HTTP из-за слишком строгого запрета `socket.connect`: Windows asyncio использует внутренний loopback `socketpair`. В harness разрешено только это внутреннее соединение; прикладная сеть и запуск подпроцессов запрещены. После исправления harness выполнен завершённый запуск с результатами выше. Это не дефект приложения.

Существующий профиль:

```powershell
python -m pytest -q tests/test_voice_server.py -k 'archiver or worker' --basetemp output/audit-20261103-continuation/pytest
```

**7 passed, 58 deselected, 2 warnings, 1,10 с, exit 0.** Перед запуском прочитаны fixtures; APP/CHAT/VOICE URL заданы тестовыми SQLite, SCAN и SCAN_TEST URL пустые, live opt-in отключён, worker/archive выключены в окружении. Все файловые fixtures — временные. Этот профиль покрывает штатные отдельные операции, но не четыре найденных сценария.

Не проверены production PostgreSQL/архивная шара/фактические флаги, работающий ML/GPU/ffmpeg worker, физические клиенты и полный пользовательский E2E. PostgreSQL row locks не моделировались: для гонки отмены проверен допустимый порядок SQL-операций между отдельными транзакциями. Полный backend-gate не запускался.
