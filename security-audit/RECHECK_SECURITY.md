## Итог

Предыдущее утверждение «все кодовые находки закрыты» неверно. Из-за слабого активного JWT-ключа и отсутствия проверки принадлежности `session_id` пользователю сохраняется подтверждённый путь к подмене учётной записи. Кодовые исправления и конфигурационные меры не следует считать развёрнутыми на основании локального рабочего дерева.

Рекомендация: не считать инсталляцию production-safe; прежде чем менять действующие секреты или процессы, согласовать окно, порядок ротации и откат. Аудит прицельный: рабочее дерево содержит более 300 изменённых файлов, полного DAST, мобильного runtime и проверки IIS/SQL Server на сетевом уровне не было.

## Critical

### SR-01. JWT-подпись и сессия не связаны с одним пользователем

- Место: `WEB-itinvent/backend/api/deps.py:298-335`, `:196-220`; `WEB-itinvent/backend/services/session_service.py:837-859`; `WEB-itinvent/backend/api/v1/auth.py:492-519`.
- Доказательство: токен определяет пользователя по `user_id`, затем `is_session_active(session_id)` проверяет только существование активной сессии, не сверяя её `user_id` с пользователем токена. В `trusted_device_service.py:288-291` отсутствие `trusted:`-device_id не вызывает отказа. Собственный `session_id` клиент получает при входе.
- Текущая конфигурация: `JWT_SECRET_KEYS` содержит два 10-символьных ключа; первый совпадает с литералом в `tests/test_backend_auth_hardening.py`. `APP_ENV=development`, поэтому `Config.validate()` выходит до проверок (`config.py:582-603`). Значения ключей намеренно не приведены.
- Сценарий: обладатель собственной активной сессии, зная опубликованный слабый ключ, может подписать access-токен с идентификатором другого active user и собственным `session_id`. REST-зависимость принимает сессию без сверки владельца; права берутся из целевого пользователя. Дополнительные IP-ограничения admin применяются отдельно и здесь не оценивались. Это не проверялось запросом в production.
- Исправление: проверять `user_id` сессии при каждом принятии access-токена, в том числе optional-auth, WebSocket и вспомогательных путях, не только при refresh (`auth.py:1430-1439` уже сверяет). Регрессионный тест: токен для user B с действующей сессией user A должен вернуть 401. Затем ротировать все слабые JWT-ключи и закрыть старые сессии согласно согласованному плану.

### SR-02. Ключ шифрования совпадает с опубликованным шаблоном

- Место: `.env:261`, `.env.example` (переменная `MAIL_CREDENTIALS_KEY`), `WEB-itinvent/backend/config.py:582-603`.
- Доказательство: значения идентичны; сам ключ в отчёте не приводится. Ранее аудит описал защищаемые им mail/AD/TOTP/паспорт/VCS/SNMP данные. Совпадение и незакрытый ACL дают доступному к БД/бэкапу локальному пользователю возможность расшифрования данных; наличие фактической утечки не установлено.
- Исправление: согласованная ротация и перешифрование с резервным восстановлением и проверкой читабельности; при признаках компрометации отдельно сбросить зависимые пароли и TOTP. Не менять ключ до готовности миграции шифротекста.

## High

### SR-03. Незащищённые файлы секретов и резервная копия

- Место: `.env`, `tmp/.env.bak-*` (ACL проверены `icacls`).
- Доказательство: у `BUILTIN\Users` есть наследуемое чтение (`RX`) на обоих проверенных файлах; секреты из `.env` и сохранённой копии доступны обычным локальным пользователям. Наличие других копий не исключено.
- Исправление: инвентаризация копий и согласованная замена ACL на сервисный аккаунт и администраторов; удаление копий лишь после проверки необходимости и разрешения на удаление. После закрытия доступа ротировать скомпрометированные ключи.

### SR-04. Агентские ключи не привязаны к агентам в текущем окружении

- Место: `scan_server/app.py` (`_check_agent_key`, `_check_agent_identity`), `inventory_server/app.py` (одноимённые функции), `scan_server/config.py:149-164`, `inventory_server/config.py:77-105`.
- Доказательство: код допускает общий ring-key, а `_check_agent_identity` запрещает чужой `agent_id` только если `_agent_id_for_key` / `_agent_name_for_key` вернули привязку. В локальном `.env` обе карты `SCAN_AGENT_API_KEYS` и `INVENTORY_AGENT_API_KEYS` отсутствуют, общие ключи заданы. Владение общим ключом позволяет заявлять чужую identity. Охват всех внешних прокси и выдача ключей агентам не проверены.
- Исправление: поэтапно выдать уникальные ключи, проверить агентские heartbeat/poll, затем удалить общий ring-key; делать это вместе с обновлением агентов и планом отката.

### SR-05. SQL Server работает без TLS в текущей конфигурации

- Место: `.env:397-399`, `WEB-itinvent/backend/database/connection.py:50-64`, `WEB-itinvent/backend/config.py:593-603`.
- Доказательство: `SQL_SERVER_ENCRYPT=no`, `SQL_SERVER_TRUST_SERVER_CERTIFICATE=true`, `SQL_SERVER_ALLOW_INSECURE_SQL_TLS=1`; предыдущая локальная диагностика установила, что установленный legacy-драйвер `SQL Server` даёт `SECDoClientHandshake` с Encrypt=yes. Поскольку `APP_ENV=development`, fail-closed production-гейт отключён.
- Влияние: шифрование соединения на уровне клиента не требуется; фактическое шифрование по пути не проверялось. Нельзя описывать этот режим как «TLS без проверки сертификата».
- Исправление: установить и опробовать ODBC 17/18, проверить цепочку сертификата и имя SQL-сервера, затем вернуть Encrypt=yes / TrustServerCertificate=no и включить production-валидацию. Сразу менять флаг без проверки нельзя: предыдущая попытка остановила SQL-зависимые функции.

## Medium

### SR-06. Per-database SQL TLS override не валидируется production-гейтом

- Место: `WEB-itinvent/backend/config.py:593-603`, `WEB-itinvent/backend/database/connection.py:40-64`.
- Доказательство: `Config.validate()` проверяет только `self.database`, но `get_database_config(db_id)` затем читает `DB_<ID>_ENCRYPT` и `DB_<ID>_TRUST_SERVER_CERTIFICATE` без такой же проверки. Даже при безопасном global-конфиге отдельную базу можно сконфигурировать с `Encrypt=no`.
- Исправление: проверять итоговую конфигурацию каждого доступного db_id до соединения; явно ограничить любые временные исключения и логировать только имена флагов, не строку подключения.

### SR-07. Ограничения XLSX применяются после основного разбора в UI-потоке

- Место: `WEB-itinvent/frontend/src/lib/excelPreview.js:69-96`, `WEB-itinvent/frontend/src/pages/SharedFile.jsx:401`.
- Доказательство: файл ограничен 25 МБ, но `XLSX.read(buffer)` выполняется синхронно до ограничения числа листов, столбцов и отображаемых строк; Web Worker и таймаута нет. `xlsx@0.20.3` установлен с integrity в lockfile, поэтому старое заключение об уязвимом `0.18.5` уже не относится к текущему lockfile. Реальный путь из публичной share-страницы существует, зависание специально сформированным файлом не воспроизводилось.
- Исправление: перенести parsing в изолированный worker с пределом времени/памяти и отказом при превышении; сохранить текущие лимиты.

### SR-08. Офлайн-выход сохраняет только одну отложенную ревокацию

- Место: `mobile-hub/src/auth/pendingLogoutCleanup.ts:55-69,80-111`, `mobile-hub/src/auth/logout.ts:56-105,135-163`, `mobile-hub/src/lifecycle/AppLifecycle.tsx:197-207`.
- Доказательство: `rememberPendingLogoutCleanup` перезаписывает один `STORAGE_KEY`; `runPendingLogoutCleanup` вызывается при переходе в состояние без пользователя, но не представляет очередь нескольких выходов. При двух неуспешных выходах разных аккаунтов до успешной сети первая ревокация теряется; её серверная сессия/push могут остаться активными до TTL. Сценарий не покрыт текущим `logout.test.ts`.
- Исправление: ограниченная очередь записей с идентификатором аккаунта/устройства и безопасным retry либо блокирование второго входа до завершения ревокации; отдельный тест «A offline logout → B offline logout → сеть восстановлена → обе ревокации».
