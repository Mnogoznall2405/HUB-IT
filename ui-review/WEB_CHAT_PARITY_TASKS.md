# Веб-чат HUB → нативный WPF: 50 задач агенту

Эталон — **текущий веб-чат HUB**, запущенный с тем же набором данных, ролями и настройками. Повторить в нативном WPF функции, расположение панелей, сценарии, состояния и доступность. Кадры Telegram — дополнительный ориентир для визуальной отделки; если сценарии расходятся, приоритет у веб-чата HUB. Вне объёма: почта, остальные разделы портала и функции, которых нет в веб-чате. Не заменять нативную ленту веб-страницей. Использовать существующий серверный контракт и токены WPF.

**Агент отвечает за реализацию и приёмку:** сначала сам воспроизводит веб и WPF, затем исправляет подтверждённую разницу, сам проверяет результат и прикладывает доказательства. Задача не закрывается по наличию команды, теста модели или скриншота без прохода по пользовательскому сценарию. Если веб-функция зависит от флага, роли, аппаратуры или стенда, проверять доступный вариант, а недоступный помечать как блокер, не рисовать кнопку-заглушку.

**Метки:** `Разрыв` — отличие подтверждено чтением кода, воспроизвести перед правкой; `Приёмка` — основа уже есть, повторно не реализовывать без найденного дефекта; `Сверка` — наличие или полнота сценария требуют прохода на стенде; не считать это подтверждённым багом.

## Как агент сдаёт каждую задачу

1. Зафиксировать версии/ревизии веба и WPF, флаги, роль, фикстуру, тему, размер рабочей области и DPI. Для `Разрыв`/`Сверка` сначала получить исходное поведение обоих клиентов. Если функция уже работает так же, записать проверку, не трогать код.
2. Для различий UI сохранить **веб-эталон, WPF до и после**, для новых состояний — итоговую пару веб/WPF. Путь `ui-review/screenshots/after/web-parity/WEB-NN/`; имена вроде `web-dark-1280x720-100.png` и `wpf-after-dark-1280x720-100.png`. Пусто/загрузка/ошибка/отключение — отдельными кадрами там, где это влияет на задачу. Для движения, ввода и звука добавить короткую запись или измерение и шаги, а не выдавать статичный кадр за проверку.
3. Для веба использовать локальный сценарий с тестовыми данными; для WPF — реальное окно `NativeScreenshots`/STA/UI Automation. Различать физический ввод, эмуляцию и фейк; не открывать рабочий портал, не использовать реальные переписки. По завершении изменения прогонять профильные проверки, на итоговой приёмке — `tools\dotnet-sdk-8\dotnet.exe test desktop\Hub.Desktop.sln -c Release` на изолированном стенде.
4. **Внести запись обратной связи в [RESULTS.md](RESULTS.md) под `WEB-NN`:** исходное отличие → что агент сделал (или почему изменений не было) → изменённые файлы → шаги и фактические результаты обоих клиентов → команды тестов и счётчики → ссылки на кадры → непроверенное/блокеры. Дописать итог к этой очереди по ID: `к приёмке`, `проверено без изменений` или `заблокировано`; окончательную приёмку отмечает куратор.

Порядок работы: WEB-01 фиксирует эталон, затем P1 по готовым вертикальным сценариям, P2 — не в ущерб рабочим функциям. WEB-48 → WEB-49 — отдельная ветка со стендом; WEB-50 закрывает программу. Текущая очередь составлена по исходникам и предыдущим артефактам, **не является новым прогоном**.
